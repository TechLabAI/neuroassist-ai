## ⚠️ Correção de premissa (2026-08-20)

A versão original deste issue afirmava que o SSE era do `dash-service` e tratava a escolha
do transporte como decisão em aberto. **As duas coisas estavam erradas.** Verificado no
código:

**Existem dois canais SSE distintos, ambos reais e ambos com propósito próprio:**

| Canal | Endpoint | Escopo | Replay | Serve para |
|---|---|---|---|---|
| **EVNT** | `GET /api/v1/events/stream` | tenant | header `Last-Event-ID` → backfill por `seq` | **alarme** — feed de eventos |
| **DASH** | `GET /panel/stream` | cuidador + tenant | `GET /panel/stream/catchup` | notificação de painel (sessão por cuidador) |

O DASH ainda tem `POST /panel/stream/heartbeat` e um `PanelSessionRegistry`; é dele que sai a
semântica `no_open_session` do `NotificationDeliveryService` (BE `NTF-02`).

**O canal do alarme é o do EVNT, não o do DASH.** Isso já está decidido em
[ADR-005 (EVNT, module-local) — Emergency alarm as a global shell outlet, delivered over a live
channel with polling fallback](../modules/evnt/frontend/adr/ADR-005-global-alarm-outlet-and-live-delivery.md):
o `EvntClient` abre `GET /events/stream` e degrada para polling em `GET /events/active`.
Não há decisão de transporte a tomar — há uma decisão a **cumprir**.

> Nota de leitura: o `SseEventBroadcastNoOpAdapter` do EVNT **não** indica que o canal seja um
> stub. É um `@ConditionalOnMissingBean` que só entra quando o `SseEmitterAdapter` está ausente
> (testes com o port mockado) — fix P8, `EVNT-022`. Em produção o adapter real é o que vale.

## Objetivo

Fazer o alarme chegar ao browser por **SSE real**, cumprindo o ADR-005 do EVNT, e cobrir
também o canal de painel do DASH. Hoje os dois são simulados pelos mock adapters.

## Por que é P1

FE-Flow-03 (gesto → alarme → confirmação) é **a razão de existir do produto**: uma pessoa com
ALS faz um micromovimento e uma cuidadora precisa ser avisada. Todo o resto do sistema — GEST,
EVNT, ACS directory, HIST — existe para alimentar esse push.

O ADR-005 é explícito quanto à garantia de segurança: *"No unconfirmed emergency is ever dropped
silently"*. Enquanto o transporte real não for exercitado, essa garantia não tem prova.

## Estado atual do código

`libs/evnt/src/lib/api/evnt-client-http.adapter.ts` — `openStream()` **erra de propósito**
para forçar o caminho degradado:

```ts
// TODO[FE-EVNT-007]: implement fetch-based SSE with Authorization + X-Empresa-Id headers.
// ...
subscriber.error(new Error('SSE HTTP adapter not yet implemented — degrading to poll'));
```

E `libs/evnt/src/lib/evnt.providers.ts` registra:
`"Resolve FE-EVNT-007 (EventSource + Auth header) before switching to 'http'."`

`libs/dash/src/lib/api/dash-notifications-http.adapter.ts` carrega a mesma ressalva para
`/panel/stream`, e já expõe um fallback de polling em `GET /panel/notifications/poll`.

## O problema de auth do canal — já rastreado

`EventSource` (API nativa) **não** envia headers customizados: nem `Authorization`, nem
`X-Empresa-Id`. O interceptor de `FE-E2E-002` não alcança o SSE.

Isto **não é um achado novo**: está rastreado como **`FE-EVNT-007`** / `INT-FE-EVNT-002`, e o
próprio adapter já enumera as estratégias avaliadas:

| # | Estratégia | Observação registrada no código |
|---|---|---|
| a | `fetch()` streaming + `ReadableStream` | exige CORS + `Sec-Fetch-Mode` |
| b | polyfill `eventsource-parser` com transporte `fetch` | — |
| c | `HttpClient` com `observe:'events'` + `responseType:'text'` | os interceptors carregam o `Authorization` |

Uma quarta opção — **token em query param** — deve ser rejeitada explicitamente: registra JWT
em log de acesso, inaceitável para dados de saúde sob LGPD.

WebSocket também está fora: o ADR-005 já o rejeitou para o MVP (`stack.messaging.enabled = false`;
SSE não exige broker e usa o caminho HTTP/gateway existente).

**Portanto o escopo aqui é escolher entre (a), (b) e (c) — não reabrir o transporte.**
As três são resolvíveis no frontend; nenhuma exige mudança de contrato no backend.
`FE-EVNT-007` é a issue dona da implementação; este issue é a validação ponta-a-ponta.

## Cenários de Validação

### Canal de alarme (EVNT)

| ID | Cenário | Critério |
|---|---|---|
| SSE-01 | Stream aberto ao carregar o app autenticado | `GET /api/v1/events/stream` com `Authorization` |
| SSE-02 | Evento `emergencia` renderiza o AlarmOutlet global | overlay full-bleed sem reload e sem mudar URL |
| SSE-03 | Reconexão após queda | reconecta com backoff; `Last-Event-ID` evita buraco |
| SSE-04 | Backfill por `Last-Event-ID` | eventos com `seq >` valor são reentregues |
| SSE-05 | Hidratação no (re)load | `GET /events/active` antes de abrir o stream re-exibe alarme ativo |
| SSE-06 | Degradação para polling | stream indisponível → `deliveryMode='degraded'` + banner |
| SSE-07 | Recuperação da degradação | stream volta → sai de `degraded` sem duplicar evento |
| SSE-08 | Sessão expirada durante o stream | reautentica ou encerra limpo, **sem loop** |
| SSE-09 | Teardown ao logout / sair da rota | stream fechado; sem vazamento de conexão |
| SSE-10 | Isolamento multi-empresa | cuidador do tenant A **não** recebe evento do tenant B |

### Canal de painel (DASH)

| ID | Cenário | Critério |
|---|---|---|
| SSE-11 | `GET /panel/stream` abre sessão do cuidador | sessão registrada no `PanelSessionRegistry` |
| SSE-12 | `dispatchId` duplicado não renderiza duas vezes (BE `NTF-03`) | uma única notificação na UI |
| SSE-13 | Sem sessão aberta → `no_open_session` (BE `NTF-02`) | notificação não some silenciosamente |
| SSE-14 | `GET /panel/stream/catchup` reentrega o perdido | nada é perdido entre sessões |
| SSE-15 | Fallback `GET /panel/notifications/poll` | degrada sem quebrar a superfície |

## Não fazer

- **Não** reabrir a escolha de transporte: ADR-005 (EVNT) decidiu SSE com fallback de polling,
  e rejeitou WebSocket e polling-puro com justificativa registrada.
- **Não** usar token em query param.
- **Não** tratar os dois canais como um só: escopos e semânticas de replay diferentes
  (tenant + `Last-Event-ID` no EVNT; cuidador + `catchup` no DASH).

## Open items

- Confirmar se o FE deve manter **os dois** streams abertos simultaneamente, ou se o painel
  do DASH pode derivar do `activeEvent` do EVNT. O ADR-005 diz que `activeEvent` é
  *"a single signal reused by Home/DASH"* — o que sugere um único stream de alarme, com o
  DASH consumindo o signal em vez de abrir canal próprio. **Decidir antes de implementar
  SSE-11..15**, para não abrir conexão redundante por cuidador.
- Confirmar o comportamento do EVNT sob `Last-Event-ID` quando o `seq` pedido já foi
  compactado/expurgado.
