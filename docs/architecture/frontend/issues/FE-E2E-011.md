## Objetivo

Fazer o alarme chegar ao browser por **SSE real** vindo do `dash-service`, e não por
um mock adapter simulando push.

## Por que é P1

FE-Flow-03 (gesto → alarme → confirmação) é **a razão de existir do produto**: uma pessoa
com ALS faz um micromovimento e uma cuidadora precisa ser avisada. Todo o resto do
sistema — GEST, EVNT, ACS directory, HIST — existe para alimentar esse push.

Hoje esse transporte **nunca foi exercitado**: o `dash-notifications-http.adapter.ts`
existe, mas o push é simulado pelo mock adapter. É a maior lacuna de risco do plano.

## Cenários de Validação

| ID | Cenário | Critério |
|---|---|---|
| SSE-01 | Conexão SSE estabelecida ao abrir o app autenticado | stream aberto contra o `dash-service` |
| SSE-02 | Alarme emitido pelo EVNT aparece no shell outlet | alarme renderizado sem reload |
| SSE-03 | Reconexão após queda de conexão | reconecta com backoff; sem eventos perdidos |
| SSE-04 | `dispatchId` duplicado não renderiza duas vezes (BE `NTF-03`) | um único alarme na UI |
| SSE-05 | Sessão expirada durante o stream | reautentica ou encerra limpo, sem loop |
| SSE-06 | Teardown ao sair da rota / logout | stream fechado; sem vazamento de conexão |

## Ponto de atenção técnico

`EventSource` (API nativa) **não** envia headers customizados — nem `Authorization`,
nem `X-Empresa-Id`. O interceptor do FE-E2E-002 não se aplica ao SSE.
As opções são:

1. Token via query param (registra JWT em log de acesso — ruim para dados de saúde/LGPD)
2. Cookie de sessão httpOnly
3. `fetch` + `ReadableStream` em vez de `EventSource` (permite headers)
4. WebSocket em vez de SSE

**Esta decisão precisa ser tomada em conjunto com o backend antes de implementar** —
ela afeta o `dash-service`, não só o FE.
