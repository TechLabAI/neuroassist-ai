## FE-Flow-02 — Pareamento + conectividade

```
/edge/device  →  pairing  →  heartbeat  →  chip de conectividade "online"
                                         →  /historico mostra DispositivoPareado
```

**Gate:** o chip reflete o liveness **real** do EDGE; o fact aparece no HIST.

A suíte `edge-e2e` já tem 18 testes ativos cobrindo pairing (happy path, código expirado,
claim sem heartbeat, repair/unpair, freshness derivada, poll falho → unknown) — este issue
é sobretudo migrá-los para o perfil `integrated` com seeds reais, não escrevê-los.

### Checklist

- [ ] `pairing-happy-path` verde em `integrated`
- [ ] `pairing-code-expired` com seed de TTL vencido
- [ ] `connectivity-derived-freshness` contra heartbeat real
- [ ] `connectivity-poll-failure-unknown` → estado `unknown`, não `offline` (são coisas diferentes)
- [ ] `DispositivoPareado` visível no `/historico`

## FE-Flow-04 — LGPD: apagamento e trilha

```
1. remover paciente na UI (PAC)  → erasure
2. /historico do paciente        → PII ausente, metadados de fato preservados
```

**Gate:** nenhuma PII renderizada; a UI **não quebra** com campos anonimizados ou nulos.

O HIST já implementou crypto-shredding LGPD (AES-256-GCM, apagamento de chave por paciente
— commit `19d467d`). O risco no FE é diferente do risco no BE: o backend garante que o dado
sumiu; o frontend precisa garantir que a tela **sobrevive** ao dado ausente.

### Checklist

- [ ] Apagamento pela UI do PAC
- [ ] `/historico` pós-erasure: sem PII, com metadados de fato
- [ ] Nenhum crash, `undefined` renderizado, ou string "null" na tela
- [ ] Verificação de integridade da cadeia continua disponível (BE Flow-04 passo 3)
- [ ] Auditar caches do FE: nenhuma PII sobrevivendo em signal store ou storage do browser

## Atenção

O item mais fácil de esquecer é o último: crypto-shredding no backend não apaga o que o
browser já guardou. Vale confirmar que nenhum store de módulo retém PII do paciente apagado.
