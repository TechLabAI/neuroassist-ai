## Objetivo

Executar o onboarding completo **pelo browser**, atravessando ACS → EDGE → PAC → GEST → HIST.
Espelha BE `E2E-009` / Flow-01, mas dirigido pela UI em vez de por REST client.

## Fluxo

```
/onboarding  →  OnboardingWizardPageComponent
  passo 1  criar empresa            → ACS  POST /api/v1/acs/tenants
  passo 2  cadastrar cuidadora      → ACS  POST /api/v1/acs/caregivers
  passo 3  parear dispositivo       → EDGE POST /api/v1/edge/devices  (composto)
  passo 4  cadastrar paciente       → PAC  POST /api/pac/v1/pacientes (valida device no EDGE)
  passo 5  criar comando            → PAC  POST .../comandos → GEST eligibility + HIST fact
  verificação  /historico           → HIST mostra ComandoPublicado
```

A rota `/onboarding` já existe (fora do shell layout) e o wizard já compõe os passos
de PAC e EDGE no nível de página — `acs-e2e/tenant-onboarding.spec.ts` inclusive tem
um cenário skipped para essa regra de composição.

## Gate

- Todos os 5 passos concluem sem erro
- `/historico` renderiza o `ComandoPublicado` **real** vindo do HIST
- O paciente é criado com o device pareado validado no EDGE (BE `DEV-01`)
- O comando é aceito como elegível pelo GEST

## Checklist

- [ ] Spec E2E do wizard completo no perfil `integrated`
- [ ] Passo 4 exercita a validação real de device (BE `DEV-01`)
- [ ] Passo 5 exercita eligibility real do GEST (depende de FE-E2E-004)
- [ ] Verificação final lê o HIST real (depende de FE-E2E-008)
- [ ] Caminho infeliz: device inexistente → `422` no passo 4 (DEG-06)
- [ ] Caminho infeliz: provisioning de tenant pendente → banner retryable
- [ ] Idempotência: reexecutar o spec não deixa lixo que quebre a próxima rodada

## Relacionado

Espelha BE `E2E-009`. Se o flow BE passa e o FE falha, a causa está no browser
(auth, headers, shape) — não no backend.
