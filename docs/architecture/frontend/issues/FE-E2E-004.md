# FE-E2E-004 — GEST via GWY: GEST_SERVICE_BASE_URL configurável por perfil

**Módulo:** FE E2E Integration
**Fase:** F0 — Habilitação de Transporte
**Prioridade:** P1
**Status:** OPEN
**Criado em:** 2026-08-20
**Plano:** [plan-FE-E2E.md](../plans/plan-FE-E2E.md)

## Objetivo

Fazer o GEST ser consumido através do GWY como todos os outros módulos, em vez de
apontar direto para a porta `8084`.

## Contexto

`libs/gest/src/lib/api/gest-service.config.ts`:

```ts
export const GEST_SERVICE_BASE_URL = new InjectionToken<string>('GEST_SERVICE_BASE_URL', {
  providedIn: 'root',
  factory: () => `http://${window.location.hostname}:8084`,
});
```

O GEST é o **único** módulo cujo adapter constrói URL absoluta. Consequências:

- Requisição cross-origin (`:4200` → `:8084`) exige CORS no `gest-service`.
- Bypassa o GWY: sem validação centralizada de JWT, sem rate limit, sem tracing do gateway.
- O proxy do FE-E2E-001 não tem efeito sobre URLs absolutas.

`EDGE_BRIDGE_WS_URL` (`ws://localhost:8765/live-test`) é caso **diferente e legítimo**:
é a ponte WebSocket do edge-agent local, que por design nunca passa pelo GWY. Não mexer.

## Cenários de Validação

### ⚠️ Revalidação 2026-08-20 — o GWY já tem rota, mas ela não alcança o controller

O `application-docker.yml` criou `gest-service-route` com predicado `/api/v1/gest/**` e
**sem** filtro de rewrite. O `gest-service` serve `/gest-service/{eligibility,detection-profile,
detection-contract,tipo-gesto}` e não declara `context-path`. Logo:

- `/api/v1/gest/eligibility` → GWY encaminha inalterado → `404` no serviço.
- `/gest-service/eligibility` → **nenhuma rota** do GWY casa → `404` no gateway.

É o G8 do plano. O GEST é o caso mais divergente dos 4 afetados, porque o prefixo real
(`/gest-service/`) não tem nada em comum com o normalizado.
