## Objetivo

Escrever do zero os cenários E2E do DASH. Diferente de ACS/HIST — aqui não há sequer stubs.

## Contexto

3 arquivos, cada um com um `test.describe()` **vazio** — literalmente `0 scenarios`:

```
apps/dash-e2e/src/home-status-calm.spec.ts            → describe vazio
apps/dash-e2e/src/notification-delivery.spec.ts       → describe vazio
apps/dash-e2e/src/calibration-writethrough.spec.ts    → describe vazio
```

O cabeçalho declara `0 scenarios (BDD -> Playwright stubs)` — o gerador não encontrou
cenários nos `.feature` correspondentes. Ou as features estão vazias, ou não foram escritas.

O DASH é o módulo de entrada do produto (rota default `/`, mais `/notificacoes` e `/entrada`),
e é o destinatário do alarme no fluxo mais crítico do sistema.

## Passo zero — investigar as features BDD

Antes de escrever specs, confirmar se `frontend/e2e/*.feature` do DASH existem e têm cenários.
Se não têm, os cenários precisam ser derivados do `plan-FE-DASH` / spec do módulo — e isso
é trabalho de especificação, não de teste.

## Checklist

- [ ] Features BDD do DASH localizadas e auditadas (existem? têm cenários?)
- [ ] `home-status-calm` — estado calmo, sem alarme pendente
- [ ] `notification-delivery` — entrega, `no_open_session` (BE `NTF-02`), idempotência de `dispatchId` (BE `NTF-03`)
- [ ] `calibration-writethrough` — write-through de calibração
- [ ] Cenários de degradação: DASH indisponível, liveness `offline`, `304` sem flicker
- [ ] Verde nos perfis `mock` e `integrated`

## Atenção

Um `describe` vazio **passa** no Playwright. As 3 suítes do DASH estão hoje "verdes" e
não testam nada — a mesma armadilha do `test.skip` com asserção vazia, em outra forma.
