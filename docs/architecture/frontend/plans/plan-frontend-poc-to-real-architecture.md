# Frontend — Prototype-to-Real Architecture Status & Plan (for Architecture Team review)

> **Scope:** whole `neuroassist-ai-web` frontend, all 7 business modules
> **Status:** DRAFT — awaiting architecture team review
> **Companion doc:** `docs/architecture/backend/plans/plan-GEST-poc-to-real-architecture.md` covers the GEST module's backend gate-fixing work and the specific PoC→real transition for the calibração screen in detail; this document is the whole-frontend picture that work sits inside of. GEST/PAC composition is referenced here, not re-explained.
> **Research basis:** two independent codebase audits — one of `frontend/design-reference/angular-prototype/` (the mock-first UX prototype, generated by an internal `wireframe-to-angular` tool), one of `frontend/apps/` + `frontend/libs/` (the real Nx workspace) — cross-referenced against `docs/architecture/frontend/standards/nx-boundaries.md` and `docs/architecture/shared/blueprint-core.md`.

## 1. Executive summary

The mental model "port the prototype's mock screens to the real app" turns out to be **only half true**. Three things exist, not two:

1. **The prototype** (`frontend/design-reference/angular-prototype/`) — 6 screens, a working design system, and the UX authority for the product (design principles, data model, wireframe). Mock-data-driven by default; only 2 of its ~10 data ports have been promoted to real HTTP calls (the PoC integration), and only the `calibração` screen has any live backend integration at all.
2. **The real libs** (`frontend/libs/{gest,pac,evnt,edge}`) — already **substantially built independently**, following the FE architect docs (issues/specs), not by porting prototype code: real ports, HTTP+mock adapter pairs, facades, guards, and feature components (catalog/editor, alarm/event-feed, device/pairing, live-test) already exist. This is further along than "porting the prototype" implies.
3. **The real app shell** (`frontend/apps/neuroassist-ai-web`) — **has never actually been scaffolded as an Nx project.** No `project.json`, no `angular.json`, no `main.ts`, no `index.html`, no `app.config.ts`. `app.routes.ts` already does real composition work (lazy-loading all 4 built libs, plus the new GEST↔PAC wiring from this session) — but there is currently no bootstrapping mechanism to actually run any of it.

**The real gap is not "port more screens."** It's: (a) the app shell was never generated, so nothing can run at all; (b) 3 of 7 modules are stubs (one of which, ACS, has a *complete* docs pipeline — 37 issues — and zero code, i.e. planning ran far ahead of implementation); (c) most `shared/*` cross-cutting libs are one-line placeholders; (d) architecture-boundary enforcement is only half-wired (module `scope` is enforced, layer `type` is not); (e) whether the real libs' feature components match the prototype's UX fidelity is unverified.

## 2. The prototype's role and content

### 2.1 UX authority (not to be re-litigated per module)

`wireframe.md` / `ui-concept.md` establish a single, deliberately narrow product stance: a **"silent guardian"** — calm/peripheral almost always, unmistakable only at the moment of a real alarm, explicitly *not* an operational dashboard. Single persona (Jamilly, non-technical family caregiver); the patient (Márcio) has no direct UI interaction; a second "condutor técnico" role exists only for one-time setup. Seven UX principles, each with a concrete verification test (glanceable status, unambiguous alarm, explicit confirmation for critical actions, non-technical calibration, jargon-free history, connectivity never hidden, ≤2 clicks to the most critical action). These principles are the acceptance bar for every module's UI — any real implementation should be checked against them, not just against its own issue's acceptance criteria.

Data model (`wireframe.md §4.3`): `Tenant`, `Paciente`, `Cuidador`, `TipoGesto` (extensible catalog — already reflected in the real GEST/PAC work), `Comando` (N per patient, `rotulo` free text, `urgencia` enum, 1–2 primitives for simple/composite gestures), `Evento`, `DispositivoEdge`. Two documented amendments (command-catalog replacing a 1-per-patient calibration profile; making the gesture-type catalog extensible) show this model evolving live during design — worth checking the real backend's data model still matches, since both amendments predate this session's backend work.

### 2.2 The 6 screens — content, size, and promotion status

| Screen | Lines | Data ports used | PoC/real integration |
|---|---|---|---|
| `entrada` | 44 | none (static) | n/a |
| `home` | 283 | Pacientes, Eventos, Dispositivos, Comandos (all mock) | none |
| `alarme` | 46 | Eventos, Comandos (mock) | none at the route level — see §2.4 |
| `historico` | 164 | Eventos, Comandos, Pacientes (mock) | none |
| `calibracao` | 700 | Comandos (still `localStorage`), TiposGesto (real), + direct gest/evnt HTTP calls | **the only screen with real backend integration** — see below |
| `onboarding` | 206 | Dispositivos, Tenants, Pacientes, Cuidadores (all mock) | none |

`calibração` imports `PocPublicarPerfilService`/`PocTestarGestoService` (real `POST /detection-profile/publish` to gest-service, real `POST /api/v1/reports` to evnt-service) and `PocGestureDetector` — a genuine 368-line client-side MediaPipe FaceLandmarker detector (EAR-based double-blink + blendshape-based single-blink/eyebrow-raise state machines) for a live "test with webcam" button. This is a real, non-trivial browser-side computer-vision concern that predates and is architecturally distinct from this session's GEST work (which builds the *edge-agent* WS bridge as the intended long-term replacement per `ADR-005` — see the companion doc §4). **`PocGestureDetector` and `edge-agent-ws.py` are two different, currently-coexisting answers to "where does the live-test verdict come from"** — the architecture team should be aware both exist, not just the one this session built.

### 2.3 Design system — real but incomplete

Only 5 of the design system's documented components actually exist: `ds-badge`, `ds-button`, `ds-card`, `ds-input`, `ds-kpi` (170 lines total). The prototype's own README documents `tab-bar` and `modal` as components that should coexist in the same folder — **neither exists**. `theme.css` (Tailwind v4 `@theme` block) is real and detailed: a light-default theme (deliberate exception to a dark-only DS convention, justified by the domestic/caregiver context), full token groups for surfaces/glass, brand ramp derived from one hex source, a separate amber "AI/advisory" identity, always-dark sidebar palette, typography, radius, and shadow scales. This token set is the one real, load-bearing design artifact here and should be the literal source of truth for any real app's `theme.css` — worth confirming the real app's copy (`frontend/apps/neuroassist-ai-web/src/theme.css` already exists per the file tree) is actually kept in sync, not forked.

### 2.4 The promotion mechanism, and where it stalled

`core/data-access.ts` is **generated** (header explicitly says so — regenerate via `wireframe-to-angular ... --force`, don't hand-edit) and implements a clean port→mock-adapter→facade triad per aggregate. `POC_HTTP_PROVIDERS` in `poc-http-adapters.ts` demonstrates the intended promotion path: override specific ports from `MockAdapter` to a real `HttpAdapter`, last-provider-wins in Angular DI, facade code never changes. **Only 2 of ~10 ports have been promoted this way** (`TiposGestoPort`, `EventosPort`, both read-only GETs) — `ComandosFacade` still persists to `localStorage` even in the most-advanced screen. The `.build-plans/` folder (6 files, disposable, "implementer reads only this file, not the wireframe") is the generator's contract format — worth knowing about but not something to hand-maintain.

Separately, `ShellComponent` (206 lines, not one of the 6 mapped screens, easy to miss) hosts the actual full-bleed alarm overlay and browser notifications, and injects `PocConfirmarEventoService` (real POST). **The real alarm UX lives partly outside the prototype-map's screen list entirely** — anyone auditing "is EVNT's alarm flow real" needs to look at the shell, not the `alarme` route.

### 2.5 Screens don't map 1:1 to the 7 business modules

This is worth stating explicitly since it affects how "port screen X" backlog items should be scoped:

- **`alarme`** → cleanly EVNT (but the real UI is in the shell, not this route — see above).
- **`historico`** → HIST for read/audit, but the feedback-write action touches EVNT's `Evento.feedback` — a genuine two-module screen.
- **`calibracao`** → PAC (command catalog CRUD) with GEST embedded (TipoGesto catalog, profile publish, live test) — confirmed hybrid, and the only screen this session's work directly extended (see companion doc §3.2).
- **`onboarding`** → a 3-module wizard by design: PAC (tenant/paciente), ACS (invite caregiver), EDGE (device pairing).
- **`home`** → primarily DASH, but reads across PAC/EDGE/EVNT — a cross-module aggregation view, not a single module's screen.
- **`entrada`** → ambiguous; likely ACS-adjacent (login) or pure app-shell; currently has no data bindings at all.

Only `alarme` and, loosely, `calibracao`'s device-facing half map to one module cleanly. Backlog items that assume "screen = module" will misfire for `home`, `historico`, and `onboarding`.

## 3. The real Nx workspace — current state

### 3.1 Per-module maturity

| Module | FE docs pipeline | `project.json` | Code maturity |
|---|---|---|---|
| GEST | complete (34 issues) | yes, `targets: {}` (inferred) | substantially built; this session added the port/adapter/component layer + PAC composition |
| PAC | complete (32 issues) | yes, `targets: {}` | substantially built — largest module (27 files): 3 ports w/ real+mock adapters, 3 facades, guards, catalog/editor/patient-register feature components, own DS kit |
| EVNT | complete (38 issues) | yes, `targets: {}` | substantially built (13 files) — port/adapters, facade, alarm-overlay + event-feed feature components |
| EDGE | complete (34 issues) | yes, `targets: {}` | substantially built (17 files) — device + pairing ports/adapters, two facades, connectivity-chip/device-detail/pairing components |
| ACS | complete (37 issues) | **none** | **stub only** — zero implementation despite a full architect pipeline having already run. Docs ran ahead of code. |
| DASH | **no docs folder exists** | **none** | stub only — hasn't started either track |
| HIST | **no docs folder exists** | **none** | stub only — hasn't started either track |

All four built libs share real hexagonal-ish shape: `<mod>.descriptor/routes/providers/bootstrap.ts`, `api/` (port + HTTP adapter + mock adapter pairs), `access/` guards, `feature-*` components. `project.json.targets` being `{}` across the board means build/test/lint are relying on Nx's `@nx/angular` plugin inference (via each lib's `vite.config.mts`/`ng-package.json`) — present for gest/pac/evnt/edge, absent for acs/dash/hist (which is *why* those three can't even be targeted yet, not just why they're empty).

**Open verification item:** this audit confirmed these libs' feature components exist and follow the right pattern, but did not assess whether their UI matches the prototype's fidelity (real templates, DS component usage, principle-7-compliant UX) or is closer to placeholder-level. Worth a dedicated pass before assuming "substantially built" means "demo-ready."

### 3.2 `libs/shared/*` — mostly not real yet

Only `contracts` has real substance (sourced from backend contract docs, versioned). The other 9 (`ui-tokens`, `ui-components`, `ui-feedback`, `error-model`, `access-http-base`, `access-decision`, `auth-session`, `empresa-context`, `observability`) are explicitly labeled **"Wave-0 stub"** — one or two files each, interface/constant-only. Notably, **`auth-session` being a stub is directly why** the companion doc's blocker #2 exists (no token-attachment on GEST's frontend HTTP calls) — there's no real session/auth infrastructure anywhere in the frontend yet for any module to plug into.

### 3.3 Architecture rules vs. what's actually enforced

`nx-boundaries.md` specifies two independent constraint axes: `scope:*` (module isolation — modules never import each other, only `shared/*`) and `type:*` (layer isolation — `feature→data-access/ui/access/shared`, `data-access→shared/{contracts,access-http-base,empresa-context,error-model}`, etc.). The root `.eslintrc.json` has a **real, active** `@nx/enforce-module-boundaries` config for the `scope:*` axis — but is **missing the `type:*` depConstraints** the standard specifies. So module isolation is enforced; layer isolation (e.g. a feature component reaching past its own facade straight into another layer) currently is not. And since `neuroassist-ai-web`/`acs`/`dash`/`hist` have no `project.json`, `nx run-many --target=lint --all` can't even reach them — enforcement is real for 5 of 11 projects, not workspace-wide.

`blueprint-core.md`'s "Asset-Driven Delivery" principle ("se repete, promova" — promote repeated patterns to `shared/*`) is the intended mechanism for graduating the Wave-0 stubs into real shared infra as the built modules mature — worth keeping in mind as GEST/PAC/EVNT/EDGE work continues, rather than letting each module reinvent auth/error-handling/observability independently.

## 4. Recommended path forward, in priority order

1. **Scaffold the app shell for real** (`nx generate @nx/angular:app neuroassist-ai-web` or equivalent, reconciling with the hand-written `app.routes.ts`/`shell/`/`config/`/`pages/` already in place). Nothing — not GEST's new wiring, not any other module — can actually run in a browser until this exists. This is the single highest-leverage fix in this entire document.
2. **Scaffold `acs`'s `project.json`.** Its docs pipeline already ran (37 issues) — it's shovel-ready and currently blocked on nothing but Nx registration.
3. **Wire the missing `type:*` ESLint boundary constraints** so layer isolation is enforced alongside module isolation, before more feature code accumulates without that guardrail.
4. **Verify real-libs UX fidelity against the prototype** (§3.1's open item) — spot-check PAC/EVNT/EDGE's feature components against the prototype's DS usage and the 7 UX principles before assuming they're demo-ready.
5. **Flesh out `auth-session` and `access-http-base`** out of Wave-0-stub status — this directly unblocks the companion doc's auth-wiring blocker for GEST and will be needed by every other module's real HTTP adapters too.
6. **Decide the `PocGestureDetector` vs. `edge-agent-ws.py` question** — two different live-detection answers currently coexist in the codebase (browser-side MediaPipe in the prototype vs. this session's edge-agent WS bridge). This is the same drift risk flagged in the companion doc §4, from a different angle — worth resolving as one decision, not two.
7. **Build or formally drop `tab-bar`/`modal`** from the design system — currently documented as existing, don't.
8. **Start `dash` and `hist`** (docs + code both) once the above unblocks real end-to-end verification — currently the only two modules with literally nothing started.
9. **Promote `calibração`'s remaining mock port** (`ComandosFacade`'s `localStorage` persistence) to a real adapter, following the same pattern GEST just used — the most natural next PoC-to-real step given the composition work already landed there.
