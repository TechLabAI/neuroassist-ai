# Backend API Cross-Link — ACS (Frontend ↔ `acs-service`)

> Module: **ACS** · Generated by `/fe-architect-specs neuroassist-ai ACS` · 2026-07-29
> **Barrier (source of truth):** `docs/architecture/backend/services/acs-service/contracts/api-contract.md`
> (+ `data-model.md`, `event-contracts.md`). This file freezes which BE endpoints each FE surface consumes and
> where the FE aligns to (or previously diverged from) the barrier.

## 1. Base & headers (BE §1)

- Base paths: `/api/v1/acs` (admin surface) — the `/oauth2` auth surface and `/api/v1/acs/directory` surface
  are **not** ACS-FE resources (see §3). Routed by GWY; discovered via REG. Media: `application/json`; errors
  `application/problem+json`.
- Mandatory request headers wired by FE interceptors:
  - `X-Empresa-Id` — from `@neuroassist/shared/empresa-context`. **ACS is the writer** of this context (FE 05
    §1); the BE derives the acting tenant from the JWT `tenant` claim (authoritative) and never trusts a
    client-sent tenant on writes (BE §1.1).
  - `Authorization: Bearer <JWT>` — from `@neuroassist/shared/auth-session` (ACS holds no auth logic — FE 02 §1).
  - `X-Correlation-Id` — propagated by the shared HTTP base (BE echoes/generates).
  - `Idempotency-Key` — the FE generates one per user-initiated `POST` create (caregiver, tenant).

## 3. Reconciliation with the FE vision (divergence resolved)

| FE vision draft (doc 05 §2) | BE barrier | Resolution in specs |
|---|---|---|
| `POST /cuidadores`, `GET /cuidadores` | URI-versioned `/api/v1/acs/caregivers` | FE clients use the versioned base path (SPEC-04) |
| `POST /vinculos`, `DELETE /vinculos` (flat) | linkage is a **caregiver sub-resource** `/caregivers/{id}/links` (+ `/{linkId}`) | FE `AcsLinkClient` models `link(cid,pid)` → `POST …/links`, `revoke(cid,linkId)` → `DELETE …/links/{linkId}` (SPEC-04) |
| `PATCH /cuidadores/{id}:deactivate` | `POST /caregivers/{id}/deactivation` (soft, idempotent) | FE `deactivate` → `POST …/deactivation`; no hard delete (invariant #7) |
| `POST /tenants` returns an active tenant | provisioning **saga** vs MIG: `201 active` **or** `202 provisioning` | FE `AcsTenantFacade` handles both; writes `empresa-context` only on `active`; `202` holds a provisioning state + retry (SPEC-04) |
| flat `GET /vinculos?paciente={pid}` | no direct per-patient link endpoint on admin surface | FE derives per-patient links **client-side** by joining caregivers' `/links` lists; the authoritative per-patient routing lives in the directory surface (BE §6.2), not the UI |

## 4. Error contract (BE §8 → FE)

All thirteen `ProblemDetail` `type`s in BE §8 are mapped in `SPEC-07-error-handling.md` §1 to an FE surface
(inline/toast/banner/modal) and pt-BR message. Safety-critical mappings: the **last-covering block**
(`409`/`422`) and `422 cross-tenant-link` are **blocking / fail-closed** modals in the UI (ADR-005). The
`/oauth2` credential errors (BE §2) are the shared `auth-session` layer's surface, not ACS's.

## 5. Known gaps (carried to backlog)

- **Coverage-eligibility contract (ADR-005, doc 06 A4).** What counts as "alarm-eligible" for the derived
  `CoverageFacade` (FE) must be identical to the BE re-enforcement and to what EVNT routes to
  (`GET /directory/patients/{pid}/caregivers`, BE §6.2). Until the definition is frozen jointly with EVNT + BE,
  the FE derives coverage from `active` links ⋈ `active` caregivers. **Freeze in scaffold/backlog.**
- **Service-credential shape for directory reads (BE §7.3).** Not an FE concern (directory is service-to-service),
  but the FE-derived per-patient coverage must stay consistent with the directory result once that surface is
  live. **Tracked; out of scope for these specs.**
- **JWT residual window on deactivate (BE §4.4, ADR-005).** A deactivated caregiver's token remains valid until
  its short TTL expires (no server-side session store in MVP). The FE surfaces `status = inactive` immediately;
  it cannot revoke an in-flight token. **Known gap; out of scope for the FE.**
