# SPEC-04 — Data Access — ACS (Frontend)

> Module: **ACS** · Generated by `/fe-architect-specs neuroassist-ai ACS` · 2026-07-29
> **Barrier source of truth:** BE `docs/architecture/backend/services/acs-service/contracts/api-contract.md`.
> Reconciliation note: the FE vision draft (doc 05 §2) sketched simplified endpoints (`POST /cuidadores`,
> `POST /vinculos`, `DELETE /vinculos`, `PATCH …:deactivate`). The BE barrier is **URI-versioned** under
> `/api/v1/acs` and models linkage as a **caregiver sub-resource** (`/caregivers/{id}/links`, soft revoke via
> `DELETE …/links/{linkId}`), with deactivation as `POST …/caregivers/{id}/deactivation`. This SPEC **aligns FE
> to the BE barrier**. All admin calls carry `X-Empresa-Id` (interceptor, ACS-set) + `X-Correlation-Id`; creates
> may carry `Idempotency-Key`. There is **no client-side authentication logic** — token exchange is the shared
> `auth-session` layer's job (FE 02 §1).

## 1. Resource / service / facade master table

| Resource | Endpoint (base `/api/v1/acs`) | Service (client) | Facade | Operations | Cache? |
|---|---|---|---|---|---|
| `Tenant` | `/tenants`, `/tenants/{id}`, `/tenants/{id}/provisioning:retry` | `AcsTenantClient` | `AcsTenantFacade` | create, get, retryProvisioning | write-to-empresa-context; session hold |
| `Cuidador` | `/caregivers`, `/caregivers/{id}`, `/caregivers/{id}/deactivation` | `AcsCuidadorClient` | `AcsCuidadorFacade` | list, get, create, deactivate | fetch-on-nav; reload after mutation |
| `CaregiverPatientLink` | `/caregivers/{cid}/links` (+ `/{linkId}`) | `AcsLinkClient` | `AcsLinkFacade` | listForCaregiver, listForPatient, link, revoke | fetch-on-nav; reload after mutation |
| `Paciente` (PAC-owned, read) | `/api/pac/v1/pacientes` (via GWY) | `PacientesReadClient` | `PacientesReadFacade` | list, get | session hold (names for linkage panel) |

> The BE `/api/v1/acs/directory/**` surface (api-contract §6) is a **service-to-service** read consumed by
> PAC/EVNT/EDGE/DASH/HIST, **not a FE resource**. ACS-FE authors tenant/roster/linkage; it never calls the
> directory surface — every peer resolves routing/scope there server-side.

## 4. Idempotency & optimistic behavior (aligned to BE §1 / §4 / §5)

- **Create (`POST /caregivers`, `POST /tenants`)** — the facade generates an `Idempotency-Key` (UUID) per
  user-initiated create and reuses it across retries of the same draft, so a retried "Convidar"/"Criar empresa"
  does not duplicate a cuidador/tenant.
- **Link (`POST …/links`)** — the BE is **idempotent** on an existing `(cuidadorId, pacienteId)` active link
  (returns `200` with the existing link, api-contract §5.1); the facade treats `200` and `201` identically.
- **Deactivate / revoke** — soft and idempotent server-side (`200` no-op if already inactive/revoked); the
  facade sends no `If-Match` (these are state-machine transitions, not concurrent-edit surfaces).
- **Coverage is never optimistic (ADR-005).** On link/unlink/deactivate the facade **re-derives** coverage from
  a fresh fetch after the mutation resolves — a paciente must never briefly *appear* covered before a link is
  confirmed, nor uncovered before an unlink is confirmed (FE 05 §4).
- **Roster edits** MAY optimistically insert/update a row for responsiveness, reconciled against the server
  response and **rolled back on error** (draft preserved, error toast). The coverage projection is never part of
  any optimistic step.
- **Coverage guard runs client-side before the request** (fast, honest UX) **and** is re-enforced by the backend
  (`409`/`422`) — the FE block is a courtesy, not the security boundary (ADR-005, FE 05 §4).

## Criterios de aceite (EARS)

> Clauses are one clause each and dot-free so the coverage gate extracts them whole; each shares domain nouns
> with a `Scenario:` title in `e2e/`.

- WHEN the coordinator opens the roster, THE SYSTEM SHALL fetch the caregiver list scoped by the empresa header.
- WHEN the coordinator invites a new cuidador, THE SYSTEM SHALL post the draft carrying an idempotency key.
- IF a cuidador invite is retried with the same draft, THEN THE SYSTEM SHALL reuse the same idempotency key so
  no duplicate cuidador is created.
- WHEN the coordinator links a cuidador that is already linked to the paciente, THE SYSTEM SHALL treat the
  idempotent link response as success without creating a duplicate vinculo.
- WHEN a coordinator unlinks the last covering caregiver of a paciente, THE SYSTEM SHALL block the unlink and
  leave the vinculo unchanged.
- WHEN a coordinator deactivates the last covering caregiver of a paciente, THE SYSTEM SHALL block the
  deactivation and leave the cuidador active.
- WHEN a link or unlink resolves, THE SYSTEM SHALL re-fetch and re-derive the paciente coverage rather than
  optimistically flipping it.
- WHEN an optimistic roster edit is rejected by the backend, THE SYSTEM SHALL roll back the optimistic row and
  preserve the draft.
- THE SYSTEM SHALL read paciente names from the PAC read model and never author a paciente record.
- WHEN the tenant provisioning returns not yet active, THE SYSTEM SHALL hold the empresa in a provisioning state
  and not write the active empresa context.
