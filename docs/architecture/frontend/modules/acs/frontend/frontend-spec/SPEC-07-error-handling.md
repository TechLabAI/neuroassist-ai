# SPEC-07 — Error Handling — ACS (Frontend)

> Module: **ACS** · Generated by `/fe-architect-specs neuroassist-ai ACS` · 2026-07-29
> **Barrier:** every `type` below comes from BE `api-contract.md` §8 (RFC 7807 ProblemDetail). Mapping goes
> `ProblemDetail (BE) → AppError (@neuroassist/shared/error-model) → user-facing pt-BR message`. ACS holds **no
> authentication logic** (FE 02 §1): `/oauth2` credential errors are the shared `auth-session` layer's surface,
> not ACS's — ACS handles the admin/linkage/tenant errors below.

## 1. `ProblemDetail` → `AppError` mapping

Each BE error carries `type`, `status`, `detail`, `correlationId`, optional `errors[]`. The shared
`error-model` lib maps it to an `AppError { code, kind, message, retryable, fieldErrors }`. ACS provides the
`type → message + surface` table below.

| BE `type` | HTTP | Surface | User-facing message (pt-BR) | Retry |
|---|---|---|---|---|
| `/errors/validation` | 400 | inline (field) | field-level hint from `errors[]` ("Nome é obrigatório", "Papel inválido") | no |
| `/errors/unauthenticated` | 401 | redirect | redirect to login (delegated to `auth-session`); no toast | no (re-auth) |
| `/errors/tenant-mismatch` | 403 | banner | "Sessão inconsistente com a empresa. Faça login novamente." | no (re-auth) |
| `/errors/insufficient-authority` | 403 | toast | "Você não tem permissão para esta ação." | no |
| `/errors/tenant-not-found` | 404 | route redirect | redirect to roster / not-found; "Empresa não encontrada." | no |
| `/errors/caregiver-not-found` | 404 | route redirect | redirect to roster / not-found; "Cuidador não encontrado." | no |
| `/errors/unknown-patient` | 404/422 | inline (linkage) | "Paciente não encontrado nesta empresa." | no |
| `/errors/login-duplicate` | 409 | inline (login field) | "Este login já existe nesta empresa." | no |
| `/errors/tenant-not-active` | 409 | banner | "A empresa ainda não está ativa. Aguarde o provisionamento concluir." | yes (after retry) |
| `/errors/tenant-suspended` | 409 | banner | "Esta empresa está suspensa. Contate o suporte." | no |
| `/errors/cross-tenant-link` | 422 | **modal (blocking)** | "Cuidador e paciente pertencem a empresas diferentes — o vínculo não é permitido." | no (fix required) |
| **last-covering block** (client guard + BE) | 409/422 | **modal (blocking)** | "Este paciente ficaria sem cuidador responsável — vincule ou ative outro antes." | no (fix required) |
| `/errors/upstream-unavailable` | 502/504 | toast (retryable) | "Serviço temporariamente indisponível. Tente novamente." | yes |

> The BE emits the last-covering block as `409`/`422` when the FE guard is bypassed; the FE also blocks it
> **before** the request (ADR-005). Both paths raise the same blocking modal — the coverage invariant is never
> a silently-dismissible toast (a patient left uncovered is a safety defect, not a cosmetic one).

## 2. Coverage invariant asymmetry (ADR-005) — UI treatment

- **Unlink / deactivate the last covering caregiver** — **fail-closed and blocking**: the FE guard blocks the
  action before the request; if the guard is bypassed, the BE returns `409`/`422` and the UI shows a **blocking
  modal** (never a dismissible toast). Nothing is mutated; the coordinator must first link/activate a
  replacement. Coverage is re-derived from a fresh fetch, never left falsely represented.
- **Cross-tenant link** — **fail-closed and blocking** (`422 cross-tenant-link`): the link is refused with a
  blocking modal; the paciente's coverage is unchanged.
- **Role change removing the last coordinator** — **allowed** (role ≠ coverage, ADR-005): no coverage block —
  losing the last `coordenador_clinica` is an admin concern, distinct from alarm eligibility.

## 3. Toast vs banner vs modal — decision rule

- **Inline (field):** validation/uniqueness errors tied to a specific input (`400 validation`,
  `409 login-duplicate`, `404/422 unknown-patient`) → disable "Salvar"/"Vincular" + hint next to the field.
- **Toast:** transient, recoverable, non-safety (`403 insufficient-authority`, `502/504
  upstream-unavailable`) — auto-dismiss.
- **Banner:** session/tenant-level problems that persist until fixed (`403 tenant-mismatch`,
  `409 tenant-not-active`, `409 tenant-suspended`).
- **Modal (blocking):** a decision the coordinator must consciously resolve — the **last-covering block** and
  the **cross-tenant link** rejection (safety-critical; must not be silently dismissed).

## 4. Retry strategy

- **No auto-retry** on any mutation by default (avoid duplicate invite/link/deactivate effects).
- `502/504 upstream-unavailable` (MIG/PAC/HIST down) and `409 tenant-not-active` (provisioning still in flight)
  are the only **retryable** cases, and only via an **explicit user action** (button) — the tenant retry maps to
  `POST /tenants/{id}/provisioning:retry` (idempotent, api-contract §3.3).
- Roster/linkage `GET` failures offer a manual "Tentar de novo" on the error card (never silent retry loops).
- Every failed mutation preserves the coordinator's draft and leaves coverage re-derived from a fresh fetch —
  nothing is ever marked saved/linked on error, and no paciente's coverage is ever falsely represented
  (FE 05 §5).

## Criterios de aceite (EARS)

> Clauses are one clause each and dot-free so the coverage gate extracts them whole; each shares domain nouns
> (error name + surface) with a `Scenario:` title in `e2e/`.

- IF the backend responds validation for a cuidador field, THEN THE SYSTEM SHALL show the field-level inline
  hint and keep the coordinator draft.
- IF the backend responds login-duplicate, THEN THE SYSTEM SHALL show an inline error on the login field and
  not mark the cuidador saved.
- IF the backend responds insufficient-authority, THEN THE SYSTEM SHALL show a permission toast for the blocked
  action.
- IF the backend responds tenant-mismatch, THEN THE SYSTEM SHALL show a session-inconsistency banner without
  leaking whether the empresa exists.
- IF the backend responds caregiver-not-found for an editar route, THEN THE SYSTEM SHALL redirect to the roster
  not-found view rather than a blank editor.
- IF the backend responds cross-tenant-link on vincular, THEN THE SYSTEM SHALL block the link with a blocking
  modal and leave the paciente coverage unchanged.
- IF the last-covering guard is bypassed and the backend blocks the unlink, THEN THE SYSTEM SHALL show a
  blocking modal and leave the vinculo unchanged.
- IF the last-covering guard is bypassed and the backend blocks the deactivation, THEN THE SYSTEM SHALL show a
  blocking modal and leave the cuidador active.
- IF the backend responds tenant-not-active during provisioning, THEN THE SYSTEM SHALL show a retryable empresa
  banner and not report the empresa active.
- IF the backend responds upstream-unavailable, THEN THE SYSTEM SHALL show a retryable toast and not mark the
  action done.
- IF any cuidador or vinculo mutation fails, THEN THE SYSTEM SHALL preserve the draft and re-derive the paciente
  coverage from a fresh fetch.
