## 1. Canonical name and prefix
- **Prefix:** `EDGE`
- **Canonical name:** `edge`
- **Service:** `edge-service` (Java 21 / Spring Boot backend module)

## 2. Problem the module solves
The gesture detection engine runs on a local edge agent on the patient's own device. The backend
must know **which physical device is watching which patient** and **whether it is actually alive
right now** — because for a safety product, a monitoring device that silently went offline is a
danger, not a neutral state. EDGE owns the device identity, its pairing to a patient, and the
liveness signal (heartbeat) that every other module trusts to mean "monitoring is really running".

## 3. Personas

## 4. MVP scope (in)
- **Device registration** — an edge agent obtains a backend identity (`DispositivoEdge`) and
  credentials it uses to authenticate every subsequent call.
- **Pairing** — binding a registered device to exactly one `Paciente` (one active device per patient
  in the MVP), via an explicit, operator-driven claim, and unpairing when a device is replaced.
- **Heartbeat & liveness** — periodic pull-based heartbeat from the edge; EDGE derives `online` /
  `offline` from heartbeat freshness (staleness threshold), records `ultimaSincronizacao` and the
  agent `versao`, and exposes device liveness to DASH/PAC.
- **Detection-profile delivery** — on heartbeat/pull, EDGE hands the paired device the current
  detection-profile *version pointer* owned by GEST, and reports back the version the device is
  actually running (drift detection). EDGE transports; GEST authors.

## 5. Out of scope (MVP)
- Computer-vision detection itself (webcam, landmarks, classification) — the edge deployable, a
  separate non-Java process (GEST ADR-005 local: edge/cloud split).
- Authoring the detection profile / primitive catalog / detectability lifecycle — that is **GEST**.
- Patient and command-catalog data (`Paciente`, `Comando`) — **PAC**; caregiver identity & roles — **ACS**.
- Event generation, alarm orchestration, notification — **EVNT**; immutable audit trail — **HIST**.
- Over-the-air update of the edge agent binary itself (only *version reporting* is in scope, not
  pushing a new agent build).
- Any video/image/landmark leaving the edge device (hard privacy invariant, inherited from GEST doc 02).

## 6. Mandatory external integrations
- **Edge agent** — a separate deployable on the patient's device; it is the only client of EDGE's
  registration, pairing-claim and heartbeat endpoints. Communicates over REST/HTTPS (sync, no broker).
  It is an in-product edge process, not a third-party API.
- **No third-party APIs** in the MVP (no push-notification vendor, no MDM). Device credentialing uses
  the project's own auth (OAuth2 resource-server, shared across services via GWY).

## 7. Hub / TechLab AI dependencies & inter-module contracts
- **TechLab AI services:** none. `ai.hasAi = false`.
- **Messaging:** disabled (`stack.messaging.enabled = false`) → all inter-module calls are synchronous
  REST between independent services, routed via GWY and discovered via REG. No event bus in the MVP;
  EDGE cannot fan-out a "device offline" event and instead exposes liveness on a queryable/pollable
  endpoint that DASH reads. This is a named risk (doc 06) to revisit if a broker is later enabled.
- **Consumed by:**
  - **PAC** — resolves `paciente.dispositivo_edge_id` against EDGE (`EdgeDevicePort`) at write time to
    validate a pairing reference (cross-service reference, not a DB FK).
  - **GEST** — EDGE pulls the active detection-profile *version pointer* from GEST and delivers it to
    the paired device; reports back the running version for drift detection.
  - **DASH** — reads device liveness (`online`/`offline`, `ultimaSincronizacao`, `versao`) to render
    the caregiver's "monitoring status" and to raise a stale-device warning.
  - **EVNT / HIST** — a recognized-command report carries the reporting `dispositivo_edge_id`; EDGE is
    the authority that this id maps to a real, paired, live device.

## 8. Domain anchor event
- **"Heartbeat recebido"** (the paired edge device reports in, refreshing its liveness and its running
  profile version). It is the recurring core of the module: pairing is the enabling precondition, and
  the derived **`online → offline`** transition (heartbeat went stale) is the safety-critical signal
  EDGE exists to make trustworthy.
