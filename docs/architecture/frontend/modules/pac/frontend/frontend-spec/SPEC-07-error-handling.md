## 1. `ProblemDetail` → `AppError` mapping

Each BE error carries `type`, `status`, `detail`, `correlationId`, optional `errors[]`. The shared
`error-model` lib maps it to an `AppError { code, kind, message, retryable, fieldErrors }`. PAC provides the
`type → message + surface` table below.

| BE `type` | HTTP | Surface | User-facing message (pt-BR) | Retry |
|---|---|---|---|---|
| `/errors/validation` | 400 | inline (field) | field-level hint from `errors[]` ("Rótulo é obrigatório", "Tempo mínimo deve ser menor que o máximo") | no |
| `/errors/missing-tenant` | 400 | banner | "Sessão sem empresa ativa. Faça login novamente." | no (re-auth) |
| `/errors/unauthorized` | 401 | redirect | redirect to login; no toast | no |
| `/errors/insufficient-scope` | 403 | toast | "Você não tem permissão para esta ação." | no |

## 2. Emergency-gate asymmetry (ADR-005, BE §4.6) — UI treatment

- **`urgencia = emergencia`** — a failed gate (`422 emergency-not-detectable` or `503
  eligibility-gate-unavailable`) is **fail-closed**: the publish is blocked, the comando stays `validated`,
  and the UI shows a **blocking modal** (never a dismissible toast that could be ignored on a safety channel).
- **`urgencia = rotina`** — the gate is **advisory**: publish succeeds `200` and the response `warnings[]`
  drive a non-blocking warning banner ("Este gesto pode não ser bem detectado ainda") gated by the
  `pac.emergencyGateAdvisoryHint` flag.

## 3. Toast vs banner vs modal — decision rule

- **Inline (field):** validation errors tied to a specific input (`400 validation`, `422
  duplicate-active-mapping`) → disable "Salvar" + hint next to the field.
- **Toast:** transient, recoverable, non-safety (`403 insufficient-scope`, `409 invalid-lifecycle`,
  `503 gate-unavailable` for `rotina`) — auto-dismiss.
- **Banner:** session/tenant-level problems that persist until fixed (`400 missing-tenant`,
  `403 tenant-mismatch`, advisory `rotina` warnings).
- **Modal (blocking):** a decision the caregiver must consciously resolve — `409 conflict-precondition`
  (reload+reapply) and the **emergency gate failure** (safety-critical; must not be silently dismissed).

## 4. Retry strategy

- **No auto-retry** on any mutation by default (avoid duplicate lifecycle effects).
- `503 eligibility-gate-unavailable` and `409 conflict-precondition`/`idempotency-mismatch` are the only
  **retryable** cases, and only via an **explicit user action** (button), after a state reload where needed.
- Catalog `GET` failures offer a manual "Tentar de novo" on the error card (never silent retry loops).
- Every failed call preserves the caregiver's draft — nothing is ever marked saved/active on error (FE 05 §5).

## Criterios de aceite (EARS)

> Clauses are one clause each and dot-free so the coverage gate extracts them whole; each shares domain nouns
> (error name + surface) with a `Scenario:` title in `e2e/`.

- IF the backend responds validation for a comando field, THEN THE SYSTEM SHALL show the field-level inline
  hint and keep the caregiver draft.
- IF the backend responds missing-tenant, THEN THE SYSTEM SHALL show a session banner prompting
  re-authentication.
- IF the backend responds insufficient-scope, THEN THE SYSTEM SHALL show a permission toast for the blocked
  action.
- IF the backend responds tenant-mismatch, THEN THE SYSTEM SHALL show a session-inconsistency banner without
  leaking whether the empresa exists.
- IF the backend responds not-found for a comando, THEN THE SYSTEM SHALL redirect to the catalog not-found
  view rather than a blank editor.
- IF the backend responds conflict-precondition on a stale ETag, THEN THE SYSTEM SHALL show a blocking modal
  asking the caregiver to reload and reapply the edit.
- IF the backend responds invalid-lifecycle-transition, THEN THE SYSTEM SHALL show a toast and leave the
  displayed comando estado unchanged.
- IF the backend responds duplicate-active-mapping, THEN THE SYSTEM SHALL show an inline error on the gesture
  selection and not mark the comando saved.
- IF the backend responds emergency-not-detectable on publicar, THEN THE SYSTEM SHALL block the publish with a
  blocking modal and leave the emergency comando validated.
- IF the backend responds eligibility-gate-unavailable on publicar, THEN THE SYSTEM SHALL show a retryable
  toast and not mark the emergency comando published.
- WHERE a rotina comando publish response contains advisory warnings, THE SYSTEM SHALL show a non-blocking
  advisory banner and still complete the publish.
- IF any comando mutation fails, THEN THE SYSTEM SHALL preserve the draft and not mark the comando saved or
  ativo.
