# SPEC-04 — Data Access — PAC (Frontend)

> Module: **PAC** · Generated by `/fe-architect-specs neuroassist-ai PAC` · 2026-07-28
> **Barrier source of truth:** BE `docs/architecture/backend/services/pac-service/contracts/api-contract.md`.
> Reconciliation note: the FE vision draft (doc 05 §2) sketched a simplified `remove(id) DELETE` client. The
> BE barrier has **no DELETE** — the `Comando` lifecycle is history-preserving (ADR-006): `drafted →
> validated → published → (recalibrated ↻) → retired`. This SPEC **aligns FE to the BE barrier**: "remove"
> becomes `:retire`. All calls carry `X-Empresa-Id` (interceptor) + `X-Correlation-Id`; mutations carry
> `If-Match` (ETag); creates may carry `Idempotency-Key`.

## 1. Resource / service / facade master table

| Resource | Endpoint (base `/api/pac/v1`) | Service (client) | Facade | Operations | Cache? |
|---|---|---|---|---|---|
| `Paciente` | `/pacientes`, `/pacientes/{id}` | `PacPacienteClient` | `PacPacienteFacade` | list, get, create, update | fetch-on-nav; session hold |
| `Comando` | `/pacientes/{pid}/comandos` (+ `/{cid}`, `:validate`, `:publish`, `:recalibrate`, `:retire`) | `PacComandoClient` | `PacComandoFacade` | list, get, create, updateDraft, validate, publish, recalibrate, retire | fetch-on-nav; reload after mutation |
| `TipoGesto` (GEST-owned, read) | `/api/gest/v1/tipos-gesto` (via GWY) | `TiposGestoReadClient` | `TiposGestoReadFacade` | list, get, requestNew | session hold; refresh after add |

> `catalogo-ativo` (BE api-contract §5) is a **service-to-service** read surface consumed by GEST/EVNT, **not
> a FE resource** — PAC-FE reads the plain `Comando` list and joins EDGE device-ack for `syncState`.

## 4. Idempotency & optimistic behavior (aligned to BE §1 / §4)

- **Create (`POST`)** — the facade generates an `Idempotency-Key` (UUID) per user-initiated create and
  reuses it across retries of the same draft, so a retried "Salvar" does not duplicate a comando/paciente.
- **Lifecycle transitions & edits** — always send `If-Match` = the ETag last read for the resource. On a
  stale ETag the BE returns `409 /errors/conflict-precondition`; the facade reloads and surfaces a "recarregue
  e tente de novo" message (SPEC-07).
- **Optimistic insert** — on `save` the facade MAY optimistically insert/update the row in `_catalog` for
  responsiveness, then reconcile against the server response; **on error it rolls back** and preserves the
  draft (FE 05 §4). The `syncState` flag is **never** part of any optimistic step — it flips to `synced`
  only on EDGE device-ack.

## Criterios de aceite (EARS)

> Clauses are one clause each and dot-free so the coverage gate extracts them whole; each shares domain nouns
> with a `Scenario:` title in `e2e/`.

- WHEN the caregiver opens the catalog, THE SYSTEM SHALL fetch the comando list for the active paciente scoped
  by the empresa header.
- WHEN the caregiver saves a new comando, THE SYSTEM SHALL post the draft carrying an idempotency key.
- IF a comando save is retried with the same draft, THEN THE SYSTEM SHALL reuse the same idempotency key so no
  duplicate comando is created.
- WHEN the caregiver saves an edit to an existing comando, THE SYSTEM SHALL send the last-read ETag as the
  If-Match precondition.
- WHEN an optimistic comando save is rejected by the backend, THE SYSTEM SHALL roll back the optimistic row
  and preserve the draft.
- THE SYSTEM SHALL request a new tipo de gesto from GEST and select only the returned primitivo id.
- WHILE editing identity fields of a comando that is not drafted, THE SYSTEM SHALL route the caregiver to
  recalibrar or retirar-e-recriar instead of a draft edit.
- THE SYSTEM SHALL reload the comando list after a successful lifecycle transition so the catalog reflects the
  authoritative server state.
