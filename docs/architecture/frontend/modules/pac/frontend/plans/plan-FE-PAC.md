## 1. Resumo do projeto

O módulo PAC é o **system of record** para Paciente e Catálogo de Comandos da plataforma NeuroAssist AI. No frontend, PAC implementa três features routed: `CommandCatalogComponent` (visão geral de todos os comandos do paciente com KPIs de sincronização), `CommandEditorComponent` (autoria draft-first de comandos com ciclo de vida completo) e `PatientRegisterComponent` (composto dentro do wizard ACS — não routed pelo PAC).

A característica central do FE PAC é o **honest-state de sincronização** (ADR-005): nenhum comando é marcado como "ativo no dispositivo" sem device-ack do EDGE — um contrato que ainda não existe no MVP e é coberto pelo stub `EdgeDeviceAckStubAdapter` (INT-FE-PAC-001), mantendo todos os comandos em `'pendente de sincronização'` até que o contrato EDGE seja implementado.

Adicionalmente, o **emergency gate** (ADR-005 BE / SPEC-07) é safety-critical: a publicação de um comando `urgencia=emergencia` é fail-closed na UI — 422 `emergency-not-detectable` resulta em modal bloqueante (não dismissível via ESC/click externo), garantindo que nenhum comando de emergência seja publicado para um gesto não detectável.

#### Objetivo

Criar os 6 arquivos `.spec.ts` para facades e guards — itens cujo comportamento existe no código mas não possui nenhuma verificação automatizada. P2 e P5 foram marcados estruturalmente prontos, mas suas Definitions of Done exigem `npx nx test pac PASS`; esse contrato nunca foi cumprido.

#### Problema identificado

- **0 arquivos `.spec.ts`** existem no módulo (confirmado: `find frontend/libs/pac -name "*.spec.ts"` → vazio).
- O peso "Tests (unit)" na rubrica de maturidade vale **20 pts**; com 0% de cobertura, o módulo não pode avançar de Parcial (51/100) para Consistente (60+).
- P8 (Observability) e P9 (e2e Playwright) dependem de que os contratos internos das facades e guards estejam verificados antes de serem estressados em cenários de integração.
- Regressões em `syncState` (ADR-005), `hasPatient()` e `pacCommandWriteGuard` seriam indetectáveis sem spec.

#### Correcoes mandatorias

1. Criar `pac-comando.facade.spec.ts`:
   - Substituir injeção real de port por mock via `TestBed.overrideProvider(PAC_COMANDO_PORT, { useValue: mockPort })`.

#### Instrucao para implementador

Criar os 6 arquivos `.spec.ts` nos caminhos exatos listados em "Arquivos-alvo". Para cada spec:
1. Usar `TestBed.configureTestingModule({ providers: [...] })` com `overrideProvider` para os ports/facades.
2. Estruturar como `describe('<NomeDaClasse>', () => { describe('<metodo/comportamento>', () => { it('deve ...', ...) }) })`.
3. Usar `jest.fn()` para mocks e `rxjs/testing` (`of`, `throwError`) para simular observables dos ports.
4. Para guards funcionais (`CanActivateFn`): usar o helper `runInInjectionContext(injector, () => guard(route, state))`.
5. Executar `npx nx test pac` ao final de cada spec criado — nao acumular todos antes de testar.
6. **Nao alterar** nenhum arquivo `.ts` de producao durante P6; P6 e exclusivamente de criacao de specs.

**Definition of Done P6:** `npx nx test pac` PASS com 6 novos arquivos `.spec.ts`; cobertura de facades >= 70% (happy paths + ADR-005 syncState contrato + degradacao de error); guards 100% de funcoes cobertas; zero erros de lint.
