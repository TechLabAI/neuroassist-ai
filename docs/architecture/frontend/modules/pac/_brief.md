## 1. Canonical name and prefix
- **Prefix:** `PAC`
- **Canonical name:** `pac`
- **Service:** `pac-service` (Java 21 / Spring Boot backend module)

## 2. Problem the module solves
For a patient whose only channel to the world is a small residual facial movement, the meaning of that
movement is not universal — it is defined by the family. PAC is where a family **registers the patient**
and **authors the command catalog**: it maps a gesture (a single primitive, or a composite of two) to a
free-text need the family chose ("quero água", "chamar a cuidadora"), and calibrates each command
independently — its **sensitivity**, its **minimum/maximum gesture duration**, and its **urgency**
(`emergencia` | `rotina`). PAC is the **authoring source of truth for what each patient's gestures mean
and how sensitively they should be detected**; everything downstream (GEST detection profiles, EVNT
events, DASH panel) reads from the catalog PAC owns.

- **Indirect — Márcio Amaral (patient):** the person the catalog is for; never a system user, but the

## 4. MVP scope (in)
- **Patient registration**: create and maintain the `Paciente` record (identity, the caregiving
  `Tenant`/empresa it belongs to, references to its `DispositivoEdge` and responsible caregivers) —
  PAC is the system of record for `Paciente`.
- **Command catalog authoring**: create/edit/retire a `Comando` for a patient — the mapping of a
  gesture (principal primitive + optional secondary, referencing `TipoGesto` owned by GEST) to a
  free-text family label and a `necessidade`.
- **Independent per-command calibration**: each `Comando` carries its own `sensibilidade`
  (`baixa|media|alta`), `tempoMinGestoMs`/`tempoMaxGestoMs` timing window, and `urgencia`
  (`emergencia|rotina`) — editable per command without side effects on siblings.
- **Emergency eligibility gate**: before a `Comando` with `urgencia = emergencia` becomes active, PAC
  validates with GEST that every referenced primitive is `supported` (genuinely detectable), so an
  emergency is never mapped to a gesture the engine cannot recognize.
- **Catalog publication for detection**: expose the patient's active, calibrated command set so GEST
  can snapshot its calibration params into an immutable `DetectionProfile` version pulled by the edge.

## 5. Out of scope (MVP)
- Computer-vision detection, the primitive vocabulary/detectability lifecycle and detection-profile
  publication — that is `TipoGesto` + `DetectionProfile`, owned by **GEST**. PAC *references* primitives
  and *authors* the per-command params GEST snapshots; it never runs detection.
- Turning a recognized command into a business event, urgency-tiered notification, or false-positive
  feedback — owned by **EVNT** (which snapshots the command's label/urgency at event time).
- Caregiver/user identity, authentication, roles and access grants — owned by **ACS** (`Cuidador`,
  `Tenant`). PAC references the responsible caregiver(s) by id.
- Device pairing, credential issuance and heartbeat monitoring of the edge agent — owned by **EDGE**
  (`DispositivoEdge`). PAC references the device by id.
- Immutable audit ledger *storage* (**HIST**) and panel/history/calibration UI rendering (**DASH**).
- Any asynchronous broker / event bus (messaging disabled MVP) and any biometric/image/landmark data —
  PAC stores only catalog metadata and primitive ids, never pixels.

## 6. Mandatory external integrations
- **GEST** (`gest-service`) — resolve `TipoGesto` primitives by id and validate detectability
  (`supported`) for the emergency-eligibility gate; GEST later snapshots PAC's per-command calibration
  params into a `DetectionProfile`. Synchronous REST (routed via GWY, discovered via REG).
- **ACS** (`acs-service`) — resolve the `Tenant` (empresa) and the responsible `Cuidador`(es) a patient
  is linked to; PAC stores the reference, ACS owns the identity.
- **EDGE** (`edge-service`) — resolve the `DispositivoEdge` a patient's detection runs on; PAC stores
  the reference, EDGE owns pairing/heartbeat.
- **Consumers of PAC:** GEST (reads command calibration to build detection profiles), EVNT (reads
  `Comando` label/urgency to build and snapshot events), DASH (renders the patient + catalog + calibration
  screens).

## 7. Hub / TechLab AI dependencies & inter-module contracts
- **TechLab AI services:** none. `ai.hasAi = false`; command meaning and calibration are explicit family
  authoring decisions, not inference.
- **Messaging:** disabled (`stack.messaging.enabled = false`) → all inter-module calls are synchronous
  REST between independent services (routed via GWY, discovered via REG). No event bus in the MVP.
- **Owns / produces:** `Paciente`, `Comando` (+ its calibration). **Consumes:** GEST `TipoGesto`
  detectability, ACS `Tenant`/`Cuidador`, EDGE `DispositivoEdge`. **Read by:** GEST, EVNT, DASH.

## 8. Domain anchor event
- **"Comando publicado" (command published into the patient's active catalog)** — the moment a gesture
  is mapped to a family-defined need, calibrated (sensitivity, timing, urgency) and — for emergencies —
  validated as detectable, becoming part of the patient's active, downstream-consumable catalog. PAC
  owns the `Comando` lifecycle from drafted → validated → published → recalibrated → retired, plus the
  `Paciente` it belongs to.
