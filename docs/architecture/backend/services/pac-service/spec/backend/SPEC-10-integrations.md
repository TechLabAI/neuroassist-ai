# SPEC-10 — Integrations (`pac-service`)

> Module: **PAC** · Service: `pac-service` · Package: `com.neuroassist.pac`
> Transport: synchronous REST via GWY/REG (Eureka) · No message broker
> Generated by `/be-architect-specs-validate neuroassist-ai PAC` · 2026-07-28

---

## 1. Objective

Specify the integration contracts of `pac-service` with its upstream and downstream services: REST client shapes, port interfaces, resilience policies, and failure semantics for each dependency.

---

## 2. Scope

**In scope:**
- `GestDetectabilityPort` → GEST (`gest-service`)
- `AcsDirectoryPort` → ACS (`acs-service`)
- `EdgeDevicePort` → EDGE (`edge-service`)
- `HistFactPort` → HIST (`hist-service`)
- Service discovery (Eureka / Spring Cloud LoadBalancer)
- Header propagation on all outbound calls

**Out of scope:**
- What GEST/ACS/EDGE/HIST do internally
- Inbound consumers of PAC (GEST/EVNT/DASH read PAC — that is their integration with PAC, not documented here)

---

## 3. Common outbound conventions

All outbound calls share:

| Concern | Implementation |
|---|---|
| Service discovery | Eureka / Spring Cloud LoadBalancer (`lb://gest-service`, etc.) |
| Client | Spring Boot 3 Feign (or `WebClient` async equivalent) |
| Auth token | OAuth2 `client_credentials` (SPEC-06 §6) |
| Headers forwarded | `X-Correlation-Id`, `X-Empresa-Id`, `Authorization` |
| Media type | `application/json` |

THE SYSTEM SHALL propagate `X-Correlation-Id` and `X-Empresa-Id` on every outbound call.

## 4. `GestDetectabilityPort` → GEST (`gest-service`)

**Critical dependency.** Used for primitive resolution (`:validate`) and the emergency-eligibility gate (`:publish`/`:recalibrate`). See SPEC-03 for full gate specification.

### 4.1 Port interface

```java
package com.neuroassist.pac.application.port;

public interface GestDetectabilityPort {
    TipoGestoRef resolveTipoGesto(UUID tipoGestoId);          // used at :validate
    SupportedResult isSupported(UUID tipoGestoId);             // used at emergency gate
}
```

### 4.2 REST shapes

| Operation | HTTP | Path |
|---|---|---|
| `resolveTipoGesto` | GET | `lb://gest-service/api/gest/v1/tipos-gesto/{id}` |
| `isSupported` | GET | `lb://gest-service/api/gest/v1/tipos-gesto/{id}/detectability` |

Response:
- `resolveTipoGesto`: `{ "id": "…", "nome": "…", "estado": "…" }` — `404` if unknown
- `isSupported`: `{ "supported": true|false }`

### 4.3 Resilience policy

| Config | Value |
|---|---|
| Connect timeout | 1 s |
| Read timeout | 2 s |
| Retry on emergency path | 1 automatic retry (transient network only) |
| Circuit breaker | Resilience4j; OPEN → fail-closed for `emergencia`, advisory-pass for `rotina` |
| Thread pool | 2 threads, queue 10 (bounded; slow GEST does not block main pool) |

EARS:
- WHEN publishing a `Comando` with `urgencia = emergencia`, THE SYSTEM SHALL call `isSupported` for every primitive and SHALL proceed only if all return `supported = true`.
- IF `GestDetectabilityPort` times out or errors WHILE `urgencia = emergencia`, THEN THE SYSTEM SHALL fail closed with `503`.
- WHERE `urgencia = rotina`, THE SYSTEM SHALL treat a non-`supported` result as advisory.

## 5. `AcsDirectoryPort` → ACS (`acs-service`)

Used when creating or updating a `Paciente` to resolve tenant (`Empresa`) and caregiver references.

### 5.1 Port interface

```java
package com.neuroassist.pac.application.port;

public interface AcsDirectoryPort {
    EmpresaRef resolveTenant(UUID empresaId);
    CuidadorRef resolveCuidador(UUID cuidadorId);
}
```

### 5.2 REST shapes

| Operation | HTTP | Path |
|---|---|---|
| `resolveTenant` | GET | `lb://acs-service/api/acs/v1/empresas/{id}` |
| `resolveCuidador` | GET | `lb://acs-service/api/acs/v1/cuidadores/{id}` |

Responses: `{ "id": "…", "valid": true }` and `{ "id": "…", "empresaId": "…" }` respectively. `404` if unknown.

### 5.3 Resilience policy

| Config | Value |
|---|---|
| Connect / Read timeout | 2 s / 3 s |
| Retry | 1 (idempotent GET) |
| On ACS unreachable | Reject write with `503` (patient creation is not safety-critical — caller should retry) |

EARS:
- WHEN a `Paciente` is created/updated with caregiver references, THE SYSTEM SHALL resolve each against ACS and reject with `422` if any is unknown or belongs to another empresa.
- IF ACS is unreachable during a patient write, THEN THE SYSTEM SHALL reject the write with `503`.

## 6. `EdgeDevicePort` → EDGE (`edge-service`)

Used to resolve `DispositivoEdge` references on patient create/update.

### 6.1 Port interface

```java
package com.neuroassist.pac.application.port;

public interface EdgeDevicePort {
    DispositivoEdgeRef resolveDispositivo(UUID dispositivoId);
}
```

### 6.2 REST shape

`GET lb://edge-service/api/edge/v1/dispositivos/{id}` → `{ "id": "…", "pacienteId": null|"…", "empresaId": "…" }`. `404` if unknown.

### 6.3 Resilience policy

Same as ACS (2s/3s timeout, 1 retry, fail-write-with-503 on unreachable).

EARS:
- WHERE `dispositivoEdgeId` is supplied on a patient write, THE SYSTEM SHALL resolve it against EDGE and reject with `422` if unknown or bound to another empresa.

**Known gap (from handoff):** No `EdgeDevicePort.confirmSync` contract exists. The FE "pendente de sincronização" UX has no backend confirmation source. Tracked as a future backlog item, out of scope for these specs.

## 7. `HistFactPort` → HIST (`hist-service`)

Used to record domain facts synchronously at the end of successful lifecycle transitions. Non-critical path (retry outbox is the fallback).

### 7.1 Port interface

```java
package com.neuroassist.pac.application.port;

public interface HistFactPort {
    void record(DomainFact fact);   // throws HistUnavailableException on failure
}
```

### 7.2 REST shape

`POST lb://hist-service/api/hist/v1/facts` with the fact payload (SPEC-09 §4). Response `201` on success; any `5xx` → `HistUnavailableException` → caller enqueues to outbox.

### 7.3 Resilience policy

| Config | Value |
|---|---|
| Connect / Read timeout | 2 s / 5 s |
| Retry | 2 automatic retries (idempotent POST — HIST deduplicates) |
| On failure after retries | Throw `HistUnavailableException` → enqueue to local outbox (SPEC-09 §5) |
| Circuit breaker | Not applied (low call rate; outbox is the safety net) |

EARS:
- WHEN a `Comando` transition commits, THE SYSTEM SHALL call `HistFactPort.record` synchronously within the same request.
- IF HIST is unreachable, THE SYSTEM SHALL NOT roll back the lifecycle transition; it SHALL enqueue the fact for retry.
- THE SYSTEM SHALL include `calibracaoVersao` in the fact so HIST/EVNT can reconcile the active tuning version.

## 8. Integration summary

| Dependency | Port | Type | On failure |
|---|---|---|---|
| GEST (`gest-service`) | `GestDetectabilityPort` | Outbound sync REST | Fail-closed (emg) / advisory (rotina) |
| ACS (`acs-service`) | `AcsDirectoryPort` | Outbound sync REST | Reject write with 503 |
| EDGE (`edge-service`) | `EdgeDevicePort` | Outbound sync REST | Reject write with 503 |
| HIST (`hist-service`) | `HistFactPort` | Outbound sync REST + retry outbox | Lifecycle stays committed; fact retried |

---

## 9. Acceptance criteria

- THE SYSTEM SHALL resolve every caregiver reference against ACS before persisting a patient.
- THE SYSTEM SHALL resolve every device reference against EDGE before persisting a patient.
- THE SYSTEM SHALL resolve every primitive reference against GEST at `:validate`.
- THE SYSTEM SHALL apply the emergency gate via GEST at `:publish` and on urgency-raising `:recalibrate`.
- THE SYSTEM SHALL record each domain fact to HIST within the same request thread after a successful transition.
- THE SYSTEM SHALL NOT roll back a lifecycle transition if HIST is unavailable; it SHALL enqueue to the outbox instead.
- THE SYSTEM SHALL propagate `X-Correlation-Id` and `X-Empresa-Id` on every outbound call.
