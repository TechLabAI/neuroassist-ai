# SPEC-03 — Emergency Eligibility Gate (`pac-service`)

> Module: **PAC** · Service: `pac-service` · Package: `com.neuroassist.pac`
> ADR ref: ADR-005 (emergency-eligibility gate — fail-closed / advisory asymmetry)
> EARS guide: `docs/architecture/backend/standards/ears-notation.md`
> Generated by `/be-architect-specs-validate neuroassist-ai PAC` · 2026-07-28

---

## 1. Objective

Specify the emergency-eligibility gate in full: when it runs, what it checks, how it reacts to GEST responses and failures, and what asymmetry exists between `urgencia = emergencia` (fail-closed) and `urgencia = rotina` (advisory). The gate is a safety-critical component — a miscalibrated emergency command mapped to an undetectable gesture is a safety defect for Márcio Amaral.

---

## 2. Scope

**In scope:**
- Gate invocation points (`:publish`, `:recalibrate` when urgency changes)
- GEST call shape (`GestDetectabilityPort.isSupported`)
- Fail-closed semantics for `emergencia`
- Advisory semantics for `rotina`
- Timeout, circuit-breaker, retry policy
- Error codes (`emergency-not-detectable`, `eligibility-gate-unavailable`)

**Out of scope:**
- General command lifecycle — see SPEC-02
- GEST internal detectability mechanics (GEST owns `TipoGesto`)
- Caregiver/user authorization — see SPEC-06

---

## 3. Technical decision (ADR-005)

An emergency command (`urgencia = emergencia`) SHALL NOT become active if the gesture it maps is not genuinely detectable by GEST. Fail-closed: any doubt (GEST down, timeout, unknown result) MUST block the publish. The asymmetry: a `rotina` command is allowed to proceed with a non-supported primitive because the worst outcome is a missed low-priority request, not a missed emergency.

---

## 4. Gate invocation points

| Trigger | Condition to run gate |
|---|---|
| `POST …/comandos/{cid}:publish` | Always for `emergencia`; advisory for `rotina` |
| `POST …/comandos/{cid}:recalibrate` | If `urgencia` field changes to `emergencia`, OR if already `emergencia` and a primitive field changes (none allowed, but guard re-checks) |

The gate does **not** run at draft creation or at `:validate` (primitive existence is confirmed at `:validate`; detectability is the harder gate at `:publish`).

---

## 5. Gate specification

### 5.1 Scope of check

For each `Comando` being gated:
1. `primitivoPrincipalId` — always checked.
2. `primitivoSecundarioId` — checked if non-null (composite command).

Both must be `supported = true` for an emergency command.

### 5.2 GEST call contract

```
GestDetectabilityPort.isSupported(tipoGestoId: UUID): SupportedResult
  → { supported: boolean }
```

REST shape against GEST: `GET /api/gest/v1/tipos-gesto/{id}/detectability` → `{ "supported": bool }`.

Called once per primitive (not batched in MVP). Total gate calls = 1 or 2 per publish.

### 5.3 Result interpretation

| GEST result | `urgencia = emergencia` | `urgencia = rotina` |
|---|---|---|
| `supported = true` | PASS — proceed | PASS |
| `supported = false` | BLOCK — `422 emergency-not-detectable` | WARN — `200` with `warnings[]` entry |
| Timeout (> 2s) | FAIL-CLOSED — `503 eligibility-gate-unavailable` | WARN — advisory pass |
| Connection error | FAIL-CLOSED — `503 eligibility-gate-unavailable` | WARN |
| Circuit breaker OPEN | FAIL-CLOSED — `503 eligibility-gate-unavailable` | WARN |
| Unknown/unexpected response | FAIL-CLOSED — `503` | WARN |

---

## 6. Resilience policy (SLA)

- **Connect timeout:** 1 s
- **Read timeout:** 2 s (hard cap — gate must surface a retry-able error to the operator, not hang)
- **Retry on emergency path:** 1 automatic retry on transient network error (not on `503` from GEST itself). Second failure → fail-closed.
- **Circuit breaker:** standard Resilience4j CB configured on `GestDetectabilityPort`. When OPEN → fail-closed for `emergencia`, advisory pass for `rotina`. CB opens after 5 consecutive failures within a 10s window; half-open after 30s.
- **Thread isolation:** gate calls run on a bounded thread pool (2 threads, queue 10) to prevent a slow GEST from exhausting the main request pool.

---

## 7. EARS invariants

- WHEN publishing a `Comando` with `urgencia = emergencia`, THE SYSTEM SHALL call `isSupported` for every referenced primitive and SHALL proceed only if all return `supported = true`.
- IF any referenced primitive is not `supported`, THEN THE SYSTEM SHALL reject publish with `422` (`type=/errors/emergency-not-detectable`) and SHALL leave `estado = validated`.
- IF `GestDetectabilityPort` times out, errors, or returns an unknown result WHILE `urgencia = emergencia`, THEN THE SYSTEM SHALL fail closed: reject with `503` (`type=/errors/eligibility-gate-unavailable`), SHALL NOT publish, and SHALL surface a retry-able error.
- WHERE `urgencia = rotina`, THE SYSTEM SHALL treat a non-`supported` result as **advisory**: produce a `warnings[]` entry in the `200` response but SHALL NOT block publish.
- IF a recalibration raises `urgencia` to `emergencia`, THE SYSTEM SHALL re-run the emergency gate before persisting.
- THE SYSTEM SHALL NOT alter `estado` on a gate failure — the command remains in its pre-publish/pre-recalibrate state.

## 8. Response contract on gate failure

### Emergency gate block (`422`)
```json
{
  "type": "/errors/emergency-not-detectable",
  "title": "Emergency command references a non-detectable gesture",
  "status": 422,
  "detail": "TipoGesto {id} is '{estado}' in GEST; an emergency command cannot be published.",
  "instance": "/api/pac/v1/pacientes/{pid}/comandos/{cid}:publish",
  "correlationId": "…",
  "errors": [{ "field": "primitivoPrincipalId", "code": "not-detectable" }]
}
```

### Gate unavailable (`503`)
```json
{
  "type": "/errors/eligibility-gate-unavailable",
  "title": "Emergency eligibility gate is unavailable",
  "status": 503,
  "detail": "GEST detectability check timed out or failed; retry after 30s.",
  "instance": "…",
  "correlationId": "…"
}
```
Response also carries `Retry-After: 30` header.

### Advisory warning (`200` with warnings)
```json
{
  "estado": "published",
  "calibracaoVersao": 1,
  "warnings": [
    {
      "code": "primitive-not-supported",
      "detail": "TipoGesto {id} is not supported; detection may not trigger for this command."
    }
  ]
}
```

## 10. Edge cases

| Scenario | Behaviour |
|---|---|
| Composite emergency: principal OK, secondary `pending-training` | BLOCK `422` |
| Composite emergency: both `supported` | PASS |
| Routine command, GEST unreachable | `200` with `warnings[]`; `estado = published` |
| Emergency command, GEST circuit breaker OPEN | FAIL-CLOSED `503` |
| `:recalibrate` lowers urgency from `emergencia` to `rotina` | Gate NOT re-run (lowering is always safe) |
| `:recalibrate` on already-`emergencia` command (no urgency change) | Gate IS re-run (tuning change could affect detectability indirectly; confirmed at design review) |

---

## 11. Acceptance criteria

- THE SYSTEM SHALL BLOCK an emergency publish if any primitive is `pending-training`.
- THE SYSTEM SHALL FAIL-CLOSED (503) if GEST is unreachable during emergency publish.
- THE SYSTEM SHALL PASS (with warnings) a routine publish even if GEST is unreachable.
- THE SYSTEM SHALL NOT alter `estado` on any gate failure — the command retains its pre-attempt state.
- THE SYSTEM SHALL include `Retry-After` header on every `503` gate-unavailable response.
- THE SYSTEM SHALL re-run the gate on recalibration that raises urgency to `emergencia`.
