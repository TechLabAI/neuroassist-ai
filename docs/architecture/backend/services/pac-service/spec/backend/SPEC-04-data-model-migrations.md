## 1. Objective

Specify the persistence layer of `pac-service`: owned tables, their DDL, migration plan, schema routing, and the implementation contracts that enforce data model invariants not expressible as DB constraints (cross-service references, state machine transitions).

---

## 2. Scope

**In scope:**
- Tables owned by PAC (`paciente`, `paciente_cuidador`, `comando`, `tipo_gesto_ref`)
- Schema routing (`-- schema: empresa` for all PAC tables)
- Migration file plan delivered to MIG service
- Trigger for `updated_at` / `row_version`
- EARS constraints not in DB schema (cross-service ref validation, lifecycle transitions)

**Out of scope:**
- GEST's `tipo_gesto` / `DetectionProfile` tables (GEST owns them)
- MIG service mechanics — MIG applies; PAC does not run embedded Flyway
- Global-schema objects (PAC has none)

---

## 3. Schema design principles

- **Schema-per-tenant:** every PAC table is in a per-empresa Postgres schema. MIG applies migrations to each empresa schema.
- **No cross-service FKs:** `primitivo_*_id`, `dispositivo_edge_id`, `cuidador_responsavel_id` are UUID references resolved at write time via ports, not DB foreign keys.
- **Row version for ETag:** all mutable tables carry `row_version integer NOT NULL DEFAULT 0` — bumped by the `pac_touch_row` trigger, backing `ETag` / `If-Match`.
- **Soft-delete only for `Comando`:** `retired` state is terminal; no `deleted_at` on `paciente` (LGPD suppression handled at tenant/ACS level).

## 6. `updated_at` / `row_version` trigger

```sql
CREATE OR REPLACE FUNCTION pac_touch_row() RETURNS trigger AS $$
BEGIN
    NEW.updated_at := now();
    NEW.row_version := OLD.row_version + 1;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

Applied `BEFORE UPDATE` on `paciente` and `comando`.

EARS: `row_version` is monotonic per row; it is the `ETag` value returned and consumed as `If-Match`. IF an `UPDATE` statement is attempted with a `WHERE row_version = $expected` and affects 0 rows, THEN THE SYSTEM SHALL reject with `409` (`type=/errors/conflict-precondition`).

## 8. Acceptance criteria

- THE SYSTEM SHALL enforce the `ck_paciente_nome_nonempty` CHECK at the DB level — a blank `nome` row is not writable.
- THE SYSTEM SHALL enforce the `ux_comando_active_mapping` partial index — a second active mapping of the same gesture+need for the same patient raises a DB-level unique violation, surfaced as `422`.
- THE SYSTEM SHALL increment `row_version` on every update via the `pac_touch_row` trigger.
- THE SYSTEM SHALL apply migrations to the per-empresa schema only (no global tables for PAC).
- IF a write targets a `row_version` that no longer matches the current DB row, THEN THE SYSTEM SHALL reject with `409`.
