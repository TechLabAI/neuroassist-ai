# SPEC-09 — Messaging Architecture (`pac-service`)

> Module: **PAC** · Service: `pac-service` · Package: `com.neuroassist.pac`
> Messaging: DISABLED in MVP (`stack.messaging.enabled = false`)
> Generated by `/be-architect-specs-validate neuroassist-ai PAC` · 2026-07-28

---

## 1. Objective

Specify the messaging architecture (or its deliberate absence) in `pac-service`, and document the synchronous domain-fact-recording mechanism that replaces bus events in the MVP.

---

## 2. Scope

**In scope:**
- Rationale for no-broker decision in MVP
- Synchronous domain fact recording to HIST (audit trail)
- Local retry outbox for HIST facts when HIST is unavailable
- Reevaluation trigger for future broker adoption

**Out of scope:**
- Any Kafka / RabbitMQ / Artemis topic definitions (none exist)
- Async event consumers in PAC (none — PAC only produces facts)

---

## 3. No-broker decision

NeuroAssist AI MVP is a pilot with a small, controlled patient population. The synchronous REST model is sufficient for:
- GEST pulling the catalog on demand (pull-based)
- EVNT reading the command label/urgency at event time
- DASH rendering patient + catalog

Reevaluation trigger (from `04-backend-architecture-direction.md`): if the pilot grows to many simultaneous patients/edge agents, synchronous pull becomes a bottleneck — that is the first candidate for a broker (RabbitMQ, with `ComandoPublicado` / `ComandoRecalibrado` topics replacing the GEST pull polling).

---

## 4. Domain facts (synchronous, bus-less)

PAC produces three domain facts at the end of successful lifecycle transitions, recorded to HIST via `HistFactPort` (synchronous REST POST):

| Fact | Emitted when | Transport |
|---|---|---|
| `ComandoPublicado` | `:publish` succeeds | POST `/api/hist/v1/facts` (sync, best-effort-with-retry) |
| `ComandoRecalibrado` | `:recalibrate` succeeds | same |
| `ComandoAposentado` | `:retire` succeeds | same |

Payload (all facts):
```json
{
  "fact": "ComandoPublicado",
  "empresaId": "…",
  "pacienteId": "…",
  "comandoId": "…",
  "rotulo": "chamar a cuidadora",
  "urgencia": "emergencia",
  "calibracaoVersao": 3,
  "occurredAt": "2026-07-28T14:03:00Z",
  "correlationId": "…"
}
```

EARS:
- WHEN a `Comando` transition commits, THE SYSTEM SHALL record the corresponding domain fact to HIST synchronously with the same `correlationId` as the request.
- THE SYSTEM SHALL include `calibracaoVersao` in the fact so HIST/EVNT can reconcile which tuning version was active.

---

## 5. Local retry outbox (HIST unavailability)

HIST is not in the critical path — the lifecycle transition commits first, then the fact is recorded.

EARS:
- IF HIST is unreachable at fact time, THEN THE SYSTEM SHALL NOT roll back the already-committed lifecycle transition; it SHALL enqueue the fact to a local retry outbox and retry.

### Outbox design

- A `fact_outbox` table (global schema or empresa schema) stores failed facts with `(id, fact_payload jsonb, retry_count int, next_retry_at timestamptz, status text)`.
- A scheduled Spring `@Scheduled` task retries facts at `next_retry_at` using exponential backoff (initial 30s, max 5min, max 5 retries).
- After 5 retries the fact status is set to `DEAD_LETTER` and a `PAC_HIST_FACT_LOST` alert is emitted (SPEC-07).
- **Idempotency on HIST side:** HIST deduplicates on `(comandoId, fact, calibracaoVersao, occurredAt)` so retries are safe.

---

## 6. Catalog pull (replaces publish/subscribe)

GEST polls `GET .../catalogo-ativo` to detect when a re-snapshot is needed. PAC signals change by bumping `catalogoVersao` — GEST uses `If-None-Match` to avoid redundant reads.

EARS:
- THE SYSTEM SHALL expose `catalogo-ativo` as the single authoritative pull source; PAC SHALL NOT push catalog changes to any consumer.
- WHEN any command of a patient is published, recalibrated or retired, THE SYSTEM SHALL bump the patient's `catalogoVersao` so GEST can detect that a re-snapshot is due.

---

## 7. Future broker path

If/when messaging is enabled:

| Current (MVP) | Future (broker) |
|---|---|
| Synchronous REST to HIST | `ComandoPublicado` event on `pac.commands` topic |
| GEST polling `catalogo-ativo` | Subscribe to `pac.catalog.updated` topic |
| Local retry outbox | Transactional outbox pattern → broker |

No broker infrastructure is provisioned in the MVP. The outbox table is the only persistence artifact for event-adjacent concerns.

---

## 8. Acceptance criteria

- THE SYSTEM SHALL NOT attempt to connect to any message broker on startup (no RabbitMQ, Kafka, or Artemis dependency in MVP).
- WHEN a lifecycle transition commits, THE SYSTEM SHALL call `HistFactPort` synchronously within the same request thread.
- IF HIST is unavailable, THE SYSTEM SHALL store the fact in the local outbox and retry; the lifecycle transition SHALL remain committed.
- THE SYSTEM SHALL expose `catalogoVersao` as an ETag so GEST can use `If-None-Match` to avoid redundant catalog reads.
