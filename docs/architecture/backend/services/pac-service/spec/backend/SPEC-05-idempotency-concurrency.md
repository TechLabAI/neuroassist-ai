# SPEC-05 — Idempotency & Concurrency (`pac-service`)

> Module: **PAC** · Service: `pac-service` · Package: `com.neuroassist.pac`
> EARS guide: `docs/architecture/backend/standards/ears-notation.md`
> Generated by `/be-architect-specs-validate neuroassist-ai PAC` · 2026-07-28

---

## 1. Objective

Specify the two idempotency mechanisms in PAC — `Idempotency-Key` for create retries and `If-Match`/ETag for lifecycle mutations — plus the concurrency model that prevents lost updates on calibration.

---

## 2. Scope

**In scope:**
- `Idempotency-Key` header: deduplication window, storage, collision semantics
- `If-Match` / ETag: optimistic locking for every mutable resource
- Lifecycle idempotency (replayed transitions on stale or terminal state)
- Concurrent recalibration: two caregivers editing the same `Comando` simultaneously

**Out of scope:**
- Pessimistic locking or SELECT FOR UPDATE (not used — optimistic model only)
- HIST fact deduplication (see SPEC-09/SPEC-10)
- Distributed transactions (none — single service, single DB)

---

## 3. `Idempotency-Key` (create deduplication)

### 3.1 Scope

`POST /pacientes` and `POST .../comandos` (create-draft) accept an optional `Idempotency-Key` header. Lifecycle transitions (`:validate`, `:publish`, `:recalibrate`, `:retire`) and `PUT` updates do NOT use `Idempotency-Key` — they are idempotent via `If-Match`.

### 3.2 Semantics

- **Key format:** UUID v4, provided by the caller.
- **Deduplication window:** 24 hours from the first request with that key (per tenant + resource type).
- **Same key, same body:** THE SYSTEM SHALL return the original resource with `200` (not `201` again). `Location` is not re-echoed — the caller must store the original `201` `Location`.
- **Same key, different body:** THE SYSTEM SHALL return `409` (`type=/errors/idempotency-mismatch`).
- **Expired key:** treated as a new request (key not found).

### 3.3 Storage

Idempotency keys are stored in a small DB table `idempotency_key` (global schema):

| Column | Type | Notes |
|---|---|---|
| `key` | `text` | PK: `{tenant_id}:{resource_type}:{key}` |
| `resource_id` | `uuid` | Created resource id |
| `body_hash` | `text` | SHA-256 of request body (for mismatch check) |
| `created_at` | `timestamptz` | TTL: rows older than 24h eligible for purge |

A daily cleanup job (or lazy purge on lookup) removes expired entries.

EARS:
- WHEN a `POST` carries an `Idempotency-Key` matching an unexpired prior request with the same body, THE SYSTEM SHALL return `200` with the original resource.
- IF a `POST` carries an `Idempotency-Key` matching an unexpired prior request with a **different** body, THEN THE SYSTEM SHALL return `409` (`type=/errors/idempotency-mismatch`).

## 4. `If-Match` / ETag (optimistic concurrency)

### 4.1 Every mutable resource carries a version

`paciente.row_version` and `comando.row_version` are integer monotonic counters managed by the `pac_touch_row` trigger (SPEC-04).

**ETag format:** quoted integer string — e.g. `ETag: "3"`.

### 4.2 Read path

`GET` responses return an `ETag` header. `GET .../catalogo-ativo` returns `ETag: "<catalogoVersao>"`.

### 4.3 Write path (mutation)

All `PUT` and lifecycle `POST` (`:validate`, `:publish`, `:recalibrate`, `:retire`) require `If-Match`.

Implementation pattern:
```sql
UPDATE <table>
SET <fields>, row_version = row_version + 1, updated_at = now()
WHERE id = $id AND tenant_id = $tenant AND row_version = $expected_version
```
If `rowsAffected = 0` → another writer updated it concurrently → return `409 /errors/conflict-precondition`.

EARS:
- IF `If-Match` is missing on a mutation, THEN THE SYSTEM SHALL reject with `409` (`type=/errors/conflict-precondition`).
- IF `If-Match` is stale (row version has advanced), THEN THE SYSTEM SHALL reject with `409` (`type=/errors/conflict-precondition`).

### 4.4 Conditional GET (`If-None-Match`)

`GET .../catalogo-ativo` supports `If-None-Match` for poll-based staleness detection by GEST:
- If `If-None-Match` matches current `catalogoVersao`, respond `304 Not Modified` (empty body).
- THE SYSTEM SHALL support conditional GET via `If-None-Match` on `catalogoVersao`, returning `304` when unchanged.

## 5. Concurrent recalibration scenario

**Scenario:** two caregivers open the calibration UI for the same `Comando` (e.g. `calibracaoVersao = 2`, `row_version = 5`). Both submit a recalibrate:

1. Caregiver A's request arrives first: `If-Match: "5"` → `UPDATE … WHERE row_version = 5` → 1 row affected → `calibracaoVersao = 3`, `row_version = 6`. Returns `200`.
2. Caregiver B's request arrives with stale `If-Match: "5"` → `UPDATE … WHERE row_version = 5` → 0 rows affected → `409 /errors/conflict-precondition`.
3. Caregiver B must `GET` the current resource (receives `row_version = 6`, `calibracaoVersao = 3`) and re-submit.

No deadlock risk: there are no DB-level locks held across the HTTP call.

---

## 6. Lifecycle transition idempotency

Transitions are **not** idempotent by design — two concurrent transitions on the same `Comando` produce exactly one winner (the first to match `row_version`) and one `409` for the loser. The caller must re-GET before retrying.

Exception: replaying a transition that was already applied (e.g. `:retire` after the row is already `retired`) always returns `409 /errors/invalid-lifecycle-transition`, regardless of `If-Match`.

---

## 7. Edge cases

| Scenario | Behaviour |
|---|---|
| `If-Match` absent on `PUT` | `409 /errors/conflict-precondition` |
| `If-Match` on `GET` | Ignored (no write; ETag is returned only) |
| `If-Match` stale because concurrent recalibrate | `409 /errors/conflict-precondition` |
| `Idempotency-Key` from a different tenant | Treated as a distinct key (tenant is part of the key namespace) |
| Duplicate `Idempotency-Key` on a `POST` after the resource was retired | Still returns `200` with the original resource (dedup is on creation, not current state) |

---

## 8. Acceptance criteria

- WHEN a `POST` with `Idempotency-Key` matches an unexpired identical request, THE SYSTEM SHALL return `200` with the original resource (not create a duplicate).
- WHEN a `POST` with `Idempotency-Key` matches an unexpired request with a different body, THE SYSTEM SHALL return `409 /errors/idempotency-mismatch`.
- IF a mutation's `If-Match` does not match the current `row_version`, THE SYSTEM SHALL return `409 /errors/conflict-precondition` and apply no change.
- THE SYSTEM SHALL return `304` on `GET .../catalogo-ativo` when `If-None-Match` matches the current `catalogoVersao`.
- THE SYSTEM SHALL never apply a concurrent update that would silently overwrite a prior caregiver's calibration.
