# PAC — Data Model (`pac-service`)

> Module: **PAC — Pacientes e Catálogo de Comandos** · Service: `pac-service` · Package: `com.neuroassist.pac`
> Project: NeuroAssist AI · Persistence: PostgreSQL, schema-per-empresa · Migrations: centralized (MIG)
> Generated by `/be-architect-specs neuroassist-ai PAC` · 2026-07-28
> ADR refs: ADR-004 (authoring source), ADR-005 (emergency gate), ADR-006 (versioned-retire).

PAC is the system of record for `Paciente` and `Comando`. Both are **tenant data** — they live in each
empresa's schema, never in `neuroassist_global`. `TipoGesto` (GEST) and `DetectionProfile` (GEST) are
**not owned** by PAC; they appear here only as a **reference contract** and an optional **read-model
projection** for convenience. Migrations ship to the MIG service (centralized Flyway); PAC does not run an
embedded migrator.

---

## 1. Conventions

- **PK strategy:** UUID v4, application- or DB-generated (`uuid_generate_v4()`), never natural keys.
- **Timestamps:** `timestamptz`, UTC, `created_at`/`updated_at`; `updated_at` maintained by trigger.
- **Optimistic concurrency:** every mutable table carries a `row_version integer` bumped on update; it
  backs the HTTP `ETag`/`If-Match` contract in `api-contract.md`.
- **Soft-delete / history-preserving:** no hard delete of a `comando` (ADR-006). Lifecycle is a state
  column, `retired` is terminal, rows are kept indefinitely.
- **Encoding:** UTF-8; text columns are `text` with `CHECK` on non-empty where required.
- **Cross-service references** (`primitivo_*_id`, `dispositivo_edge_id`, `cuidador_responsavel_id`) are
  **not** FKs — they point at rows owned by GEST/EDGE/ACS across a service boundary. Integrity is enforced
  by synchronous resolution at write time (ports), never by a DB constraint.
- **Schema routing:** each `sql` block's first line carries `-- schema: empresa` (per-tenant, applied to
  every empresa schema by MIG) or `-- schema: global`. PAC has **no** global-schema tables.

## 2. Entities

### 2.1 `paciente` [empresa]

The patient the catalog is for. Owned by PAC. `tenant_id` mirrors the empresa schema for defense-in-depth
(a row physically in schema `t_<x>` must also carry `tenant_id = <x>`), so a schema-resolution bug cannot
silently cross tenants. `dispositivo_edge_id` and `cuidador_responsavel_id` are cross-service references
resolved at write time, not FKs.

```sql
-- schema: empresa
CREATE TABLE paciente (
    id                    uuid         NOT NULL DEFAULT uuid_generate_v4(),
    tenant_id             uuid         NOT NULL,
    nome                  text         NOT NULL,
    dispositivo_edge_id   uuid         NULL,
    row_version           integer      NOT NULL DEFAULT 0,
    created_at            timestamptz  NOT NULL DEFAULT now(),
    updated_at            timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (id),
    CONSTRAINT ck_paciente_nome_nonempty CHECK (length(btrim(nome)) > 0)
);

CREATE INDEX ix_paciente_tenant ON paciente (tenant_id);
CREATE INDEX ix_paciente_dispositivo ON paciente (dispositivo_edge_id);
COMMENT ON TABLE paciente IS 'PAC-owned patient (system of record). Tenant data, per-empresa schema.';
COMMENT ON COLUMN paciente.dispositivo_edge_id IS 'Cross-service reference to EDGE DispositivoEdge (not a FK).';
```

**Invariantes:**
- `nome` não-vazio (CHECK). `tenant_id` deve casar com o schema (garantido em serviço + trigger, §2.4).
- `dispositivo_edge_id` resolvido via `EdgeDevicePort` no write; integridade não é do banco.

### 2.2 `paciente_cuidador` [empresa]

A patient's responsible caregivers, referenced by id (ACS owns `Cuidador`). Many-to-many; the caregiver id
is a cross-service reference, not a FK.

```sql
-- schema: empresa
CREATE TABLE paciente_cuidador (
    paciente_id             uuid        NOT NULL,
    cuidador_responsavel_id uuid        NOT NULL,
    created_at              timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (paciente_id, cuidador_responsavel_id),
    FOREIGN KEY (paciente_id) REFERENCES paciente (id) ON DELETE CASCADE
);

CREATE INDEX ix_pac_cuidador_paciente ON paciente_cuidador (paciente_id);
COMMENT ON TABLE paciente_cuidador IS 'Responsible caregivers (ACS Cuidador ids, cross-service refs).';
```

**Invariantes:** cada `cuidador_responsavel_id` resolvido via `AcsDirectoryPort` no write.

### 2.3 `comando` [empresa]

Item do catálogo: gesto (primitivo principal + secundário opcional) mapeado a um rótulo livre e uma
necessidade, calibrado independentemente. State machine `drafted → validated → published → retired`
(recalibração é in-place com bump de `calibracao_versao`). History-preserving: `retired` é terminal, sem
hard delete (ADR-006). `catalogo_versao_paciente` não fica aqui — é derivado (§2.5).

```sql
-- schema: empresa
CREATE TABLE comando (
    id                     uuid         NOT NULL DEFAULT uuid_generate_v4(),
    paciente_id            uuid         NOT NULL,
    rotulo                 text         NOT NULL,
    necessidade            text         NOT NULL,
    primitivo_principal_id uuid         NOT NULL,
    primitivo_secundario_id uuid        NULL,
    sensibilidade          text         NOT NULL,
    tempo_min_gesto_ms     integer      NOT NULL,
    tempo_max_gesto_ms     integer      NOT NULL,
    urgencia               text         NOT NULL,
    estado                 text         NOT NULL DEFAULT 'drafted',
    calibracao_versao      integer      NOT NULL DEFAULT 0,
    row_version            integer      NOT NULL DEFAULT 0,
    created_at             timestamptz  NOT NULL DEFAULT now(),
    updated_at             timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (id),
    FOREIGN KEY (paciente_id) REFERENCES paciente (id) ON DELETE RESTRICT,
    CONSTRAINT ck_comando_rotulo_nonempty CHECK (length(btrim(rotulo)) > 0),
    CONSTRAINT ck_comando_necessidade_nonempty CHECK (length(btrim(necessidade)) > 0),
    CONSTRAINT ck_comando_sensibilidade CHECK (sensibilidade IN ('baixa','media','alta')),
    CONSTRAINT ck_comando_urgencia CHECK (urgencia IN ('emergencia','rotina')),
    CONSTRAINT ck_comando_estado CHECK (estado IN ('drafted','validated','published','retired')),
    CONSTRAINT ck_comando_timing CHECK (tempo_min_gesto_ms > 0 AND tempo_min_gesto_ms <= tempo_max_gesto_ms),
    CONSTRAINT ck_comando_distinct_primitives CHECK (
        primitivo_secundario_id IS NULL OR primitivo_secundario_id <> primitivo_principal_id
    )
);

CREATE INDEX ix_comando_paciente ON comando (paciente_id);
CREATE INDEX ix_comando_paciente_estado ON comando (paciente_id, estado);

-- One active mapping (gesture-set + need) per patient; retired rows are exempt so history is preserved.
CREATE UNIQUE INDEX ux_comando_active_mapping
    ON comando (paciente_id, primitivo_principal_id, coalesce(primitivo_secundario_id, '00000000-0000-0000-0000-000000000000'::uuid), necessidade)
    WHERE estado <> 'retired';

COMMENT ON TABLE comando IS 'PAC-owned command catalog item. Per-command calibration (ADR-004). History-preserving (ADR-006).';
COMMENT ON COLUMN comando.primitivo_principal_id IS 'Cross-service reference to GEST TipoGesto (not a FK).';
COMMENT ON COLUMN comando.calibracao_versao IS 'Monotonic; +1 on each in-place recalibration of a published command.';
```

**Invariantes:**
- Timing: `tempo_min_gesto_ms > 0` e `<= tempo_max_gesto_ms` (CHECK).
- Composto: primitivos distintos (CHECK). Enums garantidos por CHECK.
- Unicidade: no máx. 1 mapeamento ativo (gesto+necessidade) por paciente — `retired` isento (índice
  parcial) para não colidir com comandos aposentados.
- Emergency gate (ADR-005) **não** é constraint de banco — `primitivo_*_id` aponta para GEST através da
  fronteira; a checagem de `supported` é síncrona no serviço, no publish/recalibrate.
- Transições de estado e bump de `calibracao_versao` são aplicados no `application` layer (state machine),
  não por trigger.

### 2.4 `tipo_gesto_ref` [empresa] — read-model / reference cache (opcional)

Projeção **read-only** de `TipoGesto` (owned by GEST) que PAC referencia, para render de rótulo em
listagens sem um fan-out a GEST por linha. É um cache derivado, **nunca autoritativo**: `supported`
verdadeiro é sempre confirmado ao vivo por `GestDetectabilityPort` no gate. Pode ser omitido no MVP se a
resolução ao vivo for suficiente.

```sql
-- schema: empresa
CREATE TABLE tipo_gesto_ref (
    tipo_gesto_id  uuid         NOT NULL,
    nome           text         NOT NULL,
    supported      boolean      NOT NULL DEFAULT false,
    synced_at      timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (tipo_gesto_id)
);

COMMENT ON TABLE tipo_gesto_ref IS 'Read-only projection of GEST TipoGesto (display cache). NOT authoritative for the emergency gate.';
```

**Invariantes:** `supported` neste cache é **advisory** para UI; o gate lê GEST ao vivo (ADR-005).

### 2.5 `updated_at` / row_version trigger

```sql
-- schema: empresa
CREATE OR REPLACE FUNCTION pac_touch_row() RETURNS trigger AS $$
BEGIN
    NEW.updated_at := now();
    NEW.row_version := OLD.row_version + 1;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tg_paciente_touch BEFORE UPDATE ON paciente
    FOR EACH ROW EXECUTE FUNCTION pac_touch_row();
CREATE TRIGGER tg_comando_touch BEFORE UPDATE ON comando
    FOR EACH ROW EXECUTE FUNCTION pac_touch_row();
```

**Invariantes:** `row_version` monotônico por linha; sustenta o contrato `ETag`/`If-Match` (409 em stale).

## 3. DetectionProfile — read-model contract (GEST-owned, NOT persisted by PAC)

`DetectionProfile` é o snapshot imutável que **GEST** materializa a partir do `catalogo-ativo` de PAC
(ADR-004). PAC **não** persiste `DetectionProfile`; é documentado aqui apenas como o formato de leitura que
o endpoint `GET …/catalogo-ativo` (ver `api-contract.md` §5) alimenta. Estrutura conceitual do que GEST
snapshota por comando publicado:

| Campo do profile (GEST) | Origem em PAC |
|---|---|
| `comandoId` | `comando.id` |
| `primitivoPrincipalId` / `primitivoSecundarioId` | `comando.primitivo_*_id` |
| `sensibilidade` | `comando.sensibilidade` |
| `tempoMinGestoMs` / `tempoMaxGestoMs` | `comando.tempo_*_gesto_ms` |
| `urgencia` | `comando.urgencia` |
| `calibracaoVersao` | `comando.calibracao_versao` |
| `profileVersion` | `catalogo_versao` do paciente (derivado, §4) |

- WHEN GEST reads `catalogo-ativo`, THE SYSTEM SHALL expose only `published` commands with their current
  `calibracao_versao` (PAC autora, GEST materializa — nunca o inverso).

## 4. Relações (ASCII)

```
paciente (1) ──< (N) comando          [FK paciente_id, ON DELETE RESTRICT]
paciente (1) ──< (N) paciente_cuidador [FK paciente_id, ON DELETE CASCADE]

cross-service references (NOT FKs, resolved via ports at write time):
  paciente.dispositivo_edge_id        ─→ EDGE  DispositivoEdge
  paciente_cuidador.cuidador_resp_id  ─→ ACS   Cuidador
  paciente.tenant_id                  ─→ ACS   Tenant (empresa)
  comando.primitivo_principal_id      ─→ GEST  TipoGesto
  comando.primitivo_secundario_id     ─→ GEST  TipoGesto

catalogo_versao (per patient) = derived: MAX over the patient's published commands of a
  monotonically-bumped counter (bumped on publish/recalibrate/retire). Materialized in-service.
```

`catalogo_versao` do paciente é derivado no application layer (ex.: coluna `catalogo_versao integer` em
`paciente`, incrementada nas transições de publish/recalibrate/retire); pode ser adicionado como coluna se
o read-surface exigir `ETag` estável no `catalogo-ativo`. Adicionado via migração incremental se necessário
(faixa V0004+).
