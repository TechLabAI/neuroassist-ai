# PAC — Event & Integration Contracts (`pac-service`)

> Module: **PAC — Pacientes e Catálogo de Comandos** · Service: `pac-service` · Package: `com.neuroassist.pac`
> Project: NeuroAssist AI · **Messaging: DISABLED** (`stack.messaging.enabled = false`)
> Generated by `/be-architect-specs neuroassist-ai PAC` · 2026-07-28
> ADR refs: ADR-004 (authoring source), ADR-005 (emergency gate), ADR-006 (versioned-retire).

## 0. Messaging status — N/A (no broker in the MVP)

There is **no message broker / event bus** in the NeuroAssist AI MVP. PAC **publishes no asynchronous
events and consumes none.** All inter-service interactions are **synchronous REST**, routed through the API
Gateway (GWY) and discovered via the Service Registry (REG/Eureka). This document therefore has no
Kafka/Artemis/RabbitMQ topic definitions; instead it freezes:

1. The **outbound REST integrations** PAC depends on (GEST / ACS / EDGE), as ports.
2. The **synchronous domain-fact recording** to HIST (audit ledger) that replaces bus events.
3. The **pull-based catalog propagation** to GEST (read surface), which replaces a publish/subscribe fan-out.

Reevaluation trigger (doc 04): if the pilot grows to many patients/edges, the pull/synchronous model is the
first candidate to move behind a broker (RabbitMQ) — a known future decision, **not** MVP work.

---

## 1. Domain facts (recorded synchronously to HIST, not published to a bus)

PAC owns the `Comando`/`Paciente` lifecycle and produces three audit-worthy **domain facts**. With
messaging disabled these are **not** bus events — PAC records them to **HIST** (`hist-service`) via a
synchronous REST call at the end of the successful transaction, carrying the correlation id.

| Domain fact | Emitted when | Recorded to | Delivery |
|---|---|---|---|
| `ComandoPublicado` | `:publish` succeeds (§4.6 api-contract) | HIST | synchronous REST, best-effort-with-retry |
| `ComandoRecalibrado` | `:recalibrate` succeeds (§4.7) | HIST | synchronous REST |
| `ComandoAposentado` | `:retire` succeeds (§4.8) | HIST | synchronous REST |

**Fact payload (recorded to HIST):**
```json
{
  "fact": "ComandoPublicado",
  "empresaId": "…",
  "pacienteId": "…",
  "comandoId": "…",
  "rotulo": "chamar a cuidadora",
  "urgencia": "emergencia",
  "calibracaoVersao": 3,
  "occurredAt": "2026-07-28T14:03:00Z",
  "correlationId": "3b9f…"
}
```

**EARS — fact recording**
- WHEN a `Comando` transition (`publish`/`recalibrate`/`retire`) commits, THE SYSTEM SHALL record the
  corresponding domain fact to HIST synchronously with the same `correlationId` as the request.
- IF HIST is unreachable at fact time, THEN THE SYSTEM SHALL NOT roll back the already-committed lifecycle
  transition; it SHALL enqueue the fact to a local retry outbox and retry (the catalog state is
  authoritative; the audit trail is eventually consistent — a lost fact is a monitoring alert, not a data
  corruption).
- THE SYSTEM SHALL include `calibracaoVersao` in the fact so HIST/EVNT can reconcile which tuning version
  was active.

> **Snapshot boundary (ADR-006):** EVNT snapshots `rotulo`/`urgencia` at *event* time, not from these
> facts. PAC's facts are an audit trail, not the source EVNT reads — EVNT reads the live `Comando` (or the
> catalog) when an event occurs and snapshots it itself.

## 2. Outbound REST integrations (ports)

All three are **outbound synchronous** dependencies, implemented as REST-client adapters over Eureka/GWY in
the `infrastructure` package (doc 04). Correlation (`X-Correlation-Id`) and tenant (`X-Empresa-Id`) headers
propagate on every call.

### 2.1 `GestDetectabilityPort` → GEST (`gest-service`) — **critical, fail-closed**

| Operation | REST shape | Used by |
|---|---|---|
| `resolveTipoGesto(id)` | `GET /api/gest/v1/tipos-gesto/{id}` → `{id, nome, estado}` | `:validate` (existence) |
| `isSupported(id)` | `GET /api/gest/v1/tipos-gesto/{id}/detectability` → `{supported: bool}` | `:publish`/`:recalibrate` emergency gate |

**EARS — emergency gate integration (ADR-005)**
- WHEN publishing a `Comando` with `urgencia = emergencia`, THE SYSTEM SHALL call `isSupported` for every
  referenced primitive and SHALL proceed only if all return `supported = true`.
- IF `GestDetectabilityPort` times out, errors, or returns unknown WHILE `urgencia = emergencia`, THEN THE
  SYSTEM SHALL fail closed (HTTP `503 /errors/eligibility-gate-unavailable`) and SHALL NOT publish.
- WHERE `urgencia = rotina`, THE SYSTEM SHALL treat a non-`supported` result as advisory (warning, no
  block).
- **Resilience:** connect/read timeout ≤ 2s; no automatic retry on the emergency path beyond one (a slow
  gate must surface as a retry-able error to the operator, not hang). Circuit breaker OPEN → fail-closed for
  emergencies, advisory-pass for routine.

### 2.2 `AcsDirectoryPort` → ACS (`acs-service`)

| Operation | REST shape | Used by |
|---|---|---|
| `resolveTenant(empresaId)` | `GET /api/acs/v1/empresas/{id}` → `{id, valid}` | patient write, tenant validation |
| `resolveCuidador(id)` | `GET /api/acs/v1/cuidadores/{id}` → `{id, empresaId}` | patient write (caregiver refs) |

**EARS**
- WHEN a `Paciente` is created/updated with caregiver references, THE SYSTEM SHALL resolve each against ACS
  and reject with `422` if any is unknown or belongs to another empresa.
- IF ACS is unreachable during a patient write, THEN THE SYSTEM SHALL reject the write with `503` (patient
  creation is not safety-critical; it is safe to make the caller retry rather than persist an unvalidated
  reference).

### 2.3 `EdgeDevicePort` → EDGE (`edge-service`)

| Operation | REST shape | Used by |
|---|---|---|
| `resolveDispositivo(id)` | `GET /api/edge/v1/dispositivos/{id}` → `{id, pacienteId, empresaId}` | patient write (device binding) |

**EARS**
- WHERE `dispositivoEdgeId` is supplied on a patient write, THE SYSTEM SHALL resolve it against EDGE and
  reject with `422` if unknown or bound to another empresa.
- **Known gap (from vision handoff, assumption A1):** an EDGE *device-ack* signal that confirms the edge
  has pulled the latest `DetectionProfile` is **not yet contracted**. PAC's read surface is pull-based, so
  no ack is required for correctness in the MVP; the FE draft-first "pendente de sincronização" UX (FE
  ADR-005) currently has no backend confirmation source. Tracked as a backlog item for a future
  `EdgeDevicePort.confirmSync` contract — **out of scope for these specs**.

## 3. Inbound integration (read surface, pull-based)

PAC is **read by** GEST, EVNT and DASH over synchronous REST (see `api-contract.md` §5). No push; consumers
pull.

| Consumer | Reads | Endpoint | Propagation replaces |
|---|---|---|---|
| GEST | active calibrated catalog → snapshots into immutable `DetectionProfile` (ADR-004) | `GET …/pacientes/{pid}/catalogo-ativo` | a `ComandoPublicado`/`ComandoRecalibrado` bus event |
| EVNT | live `Comando` label/urgency at event time (snapshots itself) | `GET …/pacientes/{pid}/comandos/{cid}` | — |
| DASH | patient + catalog + calibration for rendering | `GET …/pacientes/{pid}`, `…/comandos` | — |

**EARS — pull propagation**
- WHEN a command is published, recalibrated or retired, THE SYSTEM SHALL bump the patient's
  `catalogoVersao`, allowing GEST to detect (via `ETag`/`If-None-Match`) that a `DetectionProfile`
  re-snapshot is due — this replaces an asynchronous publish/subscribe notification.
- THE SYSTEM SHALL expose `catalogo-ativo` as the single authoritative pull source; PAC SHALL NOT push
  catalog changes to any consumer (no bus).

## 4. Idempotency & versioning (bus-less)

Because there are no bus messages, idempotency/versioning concerns live on the REST surface, not on payload
envelopes:

- **Create idempotency:** `POST` creates honor an optional `Idempotency-Key` header (SPEC-05); a repeated
  key with an identical body returns the original resource, with a different body returns `409
  /errors/idempotency-mismatch`.
- **Lifecycle idempotency:** transitions are guarded by `If-Match` (ETag) — a replayed transition against a
  stale version returns `409 /errors/conflict-precondition`; against the terminal `retired` state returns
  `409 /errors/invalid-lifecycle-transition`.
- **Fact versioning (HIST):** each domain fact carries `calibracaoVersao` and `occurredAt`; HIST dedups on
  `(comandoId, fact, calibracaoVersao, occurredAt)`.
- **Payload evolution:** REST DTOs are versioned by base path (`/v1`); a breaking change opens `/v2`, it is
  not signaled by an event schema registry (none exists — no broker).

## 5. Summary

| Concern | MVP answer |
|---|---|
| Async events published by PAC | **none** (messaging disabled) |
| Async events consumed by PAC | **none** |
| Audit facts | `ComandoPublicado` / `ComandoRecalibrado` / `ComandoAposentado` → HIST, **synchronous REST** |
| Outbound deps | GEST (fail-closed gate), ACS, EDGE — synchronous REST via GWY/REG |
| Downstream propagation | **pull-based** (`catalogo-ativo` + `catalogoVersao` ETag), no push |
| Future | broker (RabbitMQ) only if patient/edge count grows (doc 04 reevaluation trigger) |
