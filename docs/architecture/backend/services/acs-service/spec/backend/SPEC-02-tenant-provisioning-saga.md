# SPEC-02 — Tenant Provisioning Saga (`acs-service`)

---

## 1. Objective

Specify the **tenant provisioning saga** (ADR-004): the synchronous, fail-closed flow by which ACS
creates a `Tenant` and requests its per-tenant schema from MIG (`neuroassist-ai-migrations`). A tenant
is considered `active` **only** after MIG confirms the schema — no half-open tenant is ever returned
as `active`.

---

## 2. Scope

**In scope:**
- Provisioning flow: `POST /api/v1/acs/tenants`
- MIG integration (`MigProvisioningPort`) and timeout handling
- Tenant status lifecycle: `provisioning → active | (stuck at provisioning)`
- Retry flow: `POST /api/v1/acs/tenants/{id}/provisioning:retry`
- `TenantProvisionado` fact recording to HIST on success

**Out of scope:**
- Tenant suspension / off-boarding (post-MVP)
- Authorization model (`acs.tenant.provisionar`) — see SPEC-06
- Data model DDL — see SPEC-04

---

## 3. Technical decisions

- **ADR-004:** ACS delegates schema DDL to MIG via `MigProvisioningPort`; it does not run Flyway directly.
- Provisioning is **fail-closed**: if MIG fails, the tenant stays `provisioning` and is never presented as `active`.
- The provisioning response is `201 Created` (with `active` snapshot) on MIG success or `202 Accepted` (with `provisioning` snapshot) on MIG failure/timeout.

---

## 4. Provisioning flow (happy path)

```
Client → POST /api/v1/acs/tenants
  ACS:
    1. Validate request (nome, tipo)
    2. Persist Tenant with status = 'provisioning', schema_name = NULL
    3. Call MigProvisioningPort.requestTenantSchema(tenantId, 't_<tenantId>')
    4. On MIG 2xx → set status = 'active', schema_name = 't_<tenantId>'
    5. Record TenantProvisionado to HIST (best-effort)
    6. Respond 201 Created with active snapshot
```

---

## 5. EARS invariants — tenant provisioning

- WHEN `POST /api/v1/acs/tenants` is received with valid `nome` and `tipo`, THE SYSTEM SHALL persist
  the `Tenant` with `status = 'provisioning'` and `schema_name = NULL` before calling MIG.
- WHEN MIG responds `2xx` to the schema request, THE SYSTEM SHALL atomically set `status = 'active'`
  and `schema_name = 't_<tenantId>'` and SHALL respond `201 Created` with the `active` snapshot.
- IF MIG responds with an error or times out (timeout ≤ 5s), THEN THE SYSTEM SHALL leave the tenant
  `status = 'provisioning'`, respond `202 Accepted` with the `provisioning` snapshot, and SHALL NOT
  set `status = 'active'` — invariant #8 (no half-open tenant).
- THE SYSTEM SHALL never return a `Tenant` with `status = 'active'` and `schema_name IS NULL` at any
  API boundary (enforced by DB constraint `ck_tenant_active_needs_schema`).
- IF `tipo` is not `familia | clinica`, THEN THE SYSTEM SHALL respond `400 Bad Request`
  (`type: /errors/validation`).
- WHERE the caller lacks `acs.tenant.provisionar`, THE SYSTEM SHALL respond `403 Forbidden`.

**Retry**
- WHEN `POST /api/v1/acs/tenants/{id}/provisioning:retry` is received and `status = 'provisioning'`,
  THE SYSTEM SHALL re-call `MigProvisioningPort` idempotently and transition to `active` on success.
- IF the tenant is already `active`, THE SYSTEM SHALL respond `200 OK` with the current snapshot and
  SHALL NOT call MIG (idempotent no-op).
- IF the tenant is `suspended`, THE SYSTEM SHALL respond `409 Conflict`
  (`type: /errors/tenant-suspended`).

**Fact recording**
- WHEN the tenant transitions to `active`, THE SYSTEM SHALL record the `TenantProvisionado` domain
  fact to HIST synchronously, best-effort (HIST unavailability SHALL NOT block the `201` response).
