## 1. Objective

Specify the ACS data model: table structure, constraints, index strategy, schema-tier mapping, and
migration bands. This SPEC is the binding contract for JPA entity annotations, Flyway scripts contributed
to MIG, and any queries that touch ACS-owned tables.

---

## 2. Scope

**In scope:**
- Four ACS tables: `tenant` (global), `signing_key` (global), `cuidador` (empresa), `caregiver_patient_link` (empresa)
- Schema-tier assignment (global vs. per-tenant empresa)
- Migration band allocation (non-colliding with other modules)
- Primary-key strategy, timestamp columns, soft-delete and enum constraints
- Index strategy for hot query paths (routing, scope, signing-key lookup)
- Cross-schema logical FK conventions (PS.003)

**Out of scope:**
- Provisioning saga mechanics — see SPEC-02
- Caregiver-patient link invariants — see SPEC-05
- JWT signing mechanics — see SPEC-03
- Application-layer query patterns (see doc 04 §Aggregates)

---

## 3. Technical decisions

- **Schema-per-empresa (ADR-003 shared):** `cuidador` and `caregiver_patient_link` live in per-tenant `t_<tenantId>` schemas.
- **Global tier:** `tenant` and `signing_key` live in `neuroassist_global` (exist before any tenant schema; platform-wide).
- **No hard deletes (invariant #7):** deactivation/revocation are `status` transitions; no `DELETE` in application code.
- **Surrogate UUIDs (PS.001):** `uuid_generate_v7()` for time-ordered, globally unique PKs.
- **LGPD hard rule:** no biometric, image, landmark, or clinical data in any ACS table; credentials stored as `credential_hash` only (bcrypt/argon2).

| Table | Schema tier | Applied | Times applied |
|---|---|---|---|
| `tenant` | `neuroassist_global` | At platform boot | Once |

## 5. Migration band allocation

ACS reserves two non-colliding bands in the centralized MIG set:

| Band | Scripts | Schema | Purpose |
|---|---|---|---|
| `V0200..V0249` | `V0200__acs_global_identity_schema.sql` | `neuroassist_global` | Create `tenant`, `signing_key`, extensions (`uuid-ossp`, `pgcrypto`) |
| `V0250..V0299` | `V0250__acs_initial_schema.sql` | `t_<tenantId>` | Create `cuidador`, `caregiver_patient_link` per tenant |

Non-colliding with: EVNT (`V0001..V0099`), GEST (`V0400..V0499`), EDGE (`V0700..V0799`),
PAC (`V0300..V0399`), HIST (`V0500..V0599`), DASH (`V0600..V0699`).

## 6. EARS invariants — data model

**Global tables**
- THE SYSTEM SHALL apply the global band (`V0200..V0249`) exactly once at platform bootstrap;
  subsequent deployments SHALL be no-ops for this band (Flyway idempotency).
- IF `tenant.status = 'active'` AND `schema_name IS NULL`, THEN THE SYSTEM SHALL reject the write
  (`ck_tenant_active_needs_schema`) — no half-open tenant is ever persisted.
- IF `tenant.tipo` is not `familia | clinica`, THEN THE SYSTEM SHALL reject the write (`ck_tenant_tipo`).
- THE SYSTEM SHALL keep at most one `signing_key` with `status = 'active'` at a time
  (`ux_signing_key_single_active`).
- THE SYSTEM SHALL never expose `signing_key.private_key_enc` through any read API, log, or error body.

**Empresa tables**
- THE SYSTEM SHALL apply the empresa band (`V0250..V0299`) to every newly provisioned `t_<tenantId>`
  schema as part of the MIG provisioning response (ADR-004).
- IF `cuidador.papel` is not `cuidadora | coordenador_clinica`, THEN THE SYSTEM SHALL reject the write
  (`ck_cuidador_papel`).
- IF an `active` `cuidador` with the same `lower(login)` already exists in the tenant, THEN THE SYSTEM
  SHALL reject the insert (`ux_cuidador_login_active`) — API `409 login-duplicate`.
- THE SYSTEM SHALL store `cuidador.credential_hash` as a non-null bcrypt/argon2 hash;
  the raw credential SHALL never reach the persistence layer.
- IF an `active` link already exists for (`cuidador_id`, `paciente_id`), THEN THE SYSTEM SHALL NOT
  create a duplicate row (`ux_link_active`).
- WHEN a link is revoked, THE SYSTEM SHALL set `status = 'revoked'` and `revogado_em = now()` and
  SHALL NOT hard-delete the row (audit invariant #7).

**Cross-schema references (PS.003)**
- `cuidador.tenant_id` is a **logical FK** to `neuroassist_global.tenant.id`; no physical cross-schema
  FK — application must validate same-tenant invariant programmatically.
- `caregiver_patient_link.paciente_id` is a **logical FK** to PAC's `Paciente`; validated at link time
  via `PacPatientResolvePort`, never a DB constraint.

**Index hot paths**
- `ix_link_paciente` (partial, `status = 'active'`) SHALL back the emergency routing query
  `GET /api/v1/acs/directory/patients/{pid}/caregivers` (indexed lookup, not a table scan).
- `ix_link_cuidador` SHALL back the per-caregiver link list `GET /api/v1/acs/caregivers/{id}/links`.
- `ix_cuidador_papel` SHALL back the coordinator-override in directory queries
  (include all `coordenador_clinica` of the tenant in routing results).
