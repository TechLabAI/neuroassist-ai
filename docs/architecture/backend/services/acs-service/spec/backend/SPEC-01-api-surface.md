## 1. Objective

Specify the complete REST API surface of `acs-service`: base path conventions, resource hierarchy, HTTP
verb/status semantics, header protocol, error model, and scope enforcement. This SPEC is the binding
contract for controller annotations, OpenAPI generation, and API-gateway routing rules.

---

## 2. Scope

**In scope:**
- Base paths `/oauth2` (auth surface) and `/api/v1/acs` (admin + directory)
- Auth surface: `/oauth2/token`, `/oauth2/jwks`
- Admin surface: tenants, caregivers, links
- Directory surface: tenant validity, routing targets, data scope
- HTTP status codes (success and error) per endpoint
- OAuth2 authority enforcement per endpoint
- Mandatory headers (`Authorization`, `X-Correlation-Id`, `X-Empresa-Id`)
- Error model (RFC 7807 ProblemDetail) — all error types

**Out of scope:**
- Implementation of JWT signing/rotation — see SPEC-03
- Tenant provisioning saga mechanics — see SPEC-02
- Data model DDL — see SPEC-04
- Caregiver-patient linkage invariants — see SPEC-05
- Security configuration (HTTPS, CORS, key storage) — see SPEC-06
- Observability endpoints — see SPEC-07

---

## 3. Technical decisions

- ADR-004: ACS is the tenant provisioning authority; tenant is `active` only after MIG confirms the schema.
- ADR-005: ACS is the OAuth2 authorization server; short-TTL JWT; no server-side session store in MVP.
- ADR-006: Caregiver-patient link is the single source of routing (EVNT) and data-scope (DASH/PAC/HIST).

## 4. Resource hierarchy

```
/oauth2/
├── token                         POST (authenticate → JWT) — public
└── jwks                          GET (public JWK set) — public

/api/v1/acs/
├── tenants                       POST (provision)
│   └── {id}                      GET
│       └── provisioning:retry    POST (idempotent retry)
├── caregivers                    POST (create), GET (list)
│   └── {id}                      GET
│       ├── deactivation          POST (soft deactivate)
│       └── links                 POST (link to patient), GET (list links)
│           └── {linkId}          DELETE (revoke)
└── directory/
    ├── tenants/{tenantId}         GET (validity)
    ├── patients/{pid}/caregivers  GET (routing targets for EVNT)
    └── caregivers/{id}            GET (role/authorities)
        └── patient-scope          GET (data-scope for DASH/PAC/HIST)
```

## 5. EARS invariants — API surface

**Headers**
- WHEN a request omits `X-Correlation-Id`, THE SYSTEM SHALL generate one and return it in the response header.
- THE SYSTEM SHALL derive the acting tenant exclusively from the JWT `tenant` claim on the admin surface and SHALL NOT accept a tenant id from the request body, query, or path for write operations.
- IF a request body carries a `tenantId` field that differs from the JWT `tenant` claim, THEN THE SYSTEM SHALL reject with `403 Forbidden` (`type: /errors/tenant-mismatch`).

**Authentication**
- THE SYSTEM SHALL require a valid OAuth2 Bearer JWT on every endpoint except `/oauth2/token`, `/oauth2/jwks`, and health probes.
- IF the Bearer token is absent, expired, or malformed on a protected endpoint, THEN THE SYSTEM SHALL respond `401 Unauthorized` (`type: /errors/unauthenticated`).

**Authorization**
- WHERE the caller's JWT lacks the required authority for the endpoint, THE SYSTEM SHALL respond `403 Forbidden` (`type: /errors/insufficient-authority`).
- THE SYSTEM SHALL treat the `papel → authorities` map as total: every `papel` SHALL resolve to a defined non-empty authority set (invariant #4).

**Content & versioning**
- THE SYSTEM SHALL produce `application/json` on success and `application/problem+json` on errors (RFC 7807).
- THE SYSTEM SHALL include the `correlationId` (from `X-Correlation-Id`) in every ProblemDetail response body.
- THE SYSTEM SHALL route all admin/directory requests through GWY (registered in REG/Eureka) and SHALL NOT expose `acs-service` ports directly to clients.
