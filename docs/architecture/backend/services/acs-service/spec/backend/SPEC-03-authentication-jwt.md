# SPEC-03 — Authentication & JWT (`acs-service`)

> Module: **ACS** · Service: `acs-service` · Package: `com.neuroassist.acs`
> Contract source: `contracts/api-contract.md §2`, `contracts/api-contract.md §7`
> EARS guide: `docs/architecture/backend/standards/ears-notation.md`
> Generated by `/be-architect-specs neuroassist-ai ACS` · 2026-07-29

---

## 1. Objective

Specify the authentication mechanics of `acs-service` (ADR-005): credential validation, JWT issuance,
JWK set publication, key lifecycle, and the role-to-authorities mapping. ACS is the platform's
**OAuth2 authorization server**; all other services are resource servers that validate ACS-issued JWTs
without calling back to ACS (stateless validation against the JWK set).

---

## 2. Scope

**In scope:**
- Credential validation (`POST /oauth2/token`, resource-owner password grant)
- JWT structure: claims, `exp`, `iss`, `kid`, authorities
- `role → authorities` total mapping (ADR-005)
- JWK set endpoint (`GET /oauth2/jwks`): key publication and `Cache-Control`
- Signing-key lifecycle: `active` + recently-retired keys in JWK set
- `AutenticacaoRealizada` / `AutenticacaoFalhou` fact recording to HIST
- JWT TTL and residual-window on deactivation (no server-side session in MVP)

**Out of scope:**
- Social login, MFA, MSAL, external IdP (deferred — ADR-005)
- Tenant provisioning — see SPEC-02
- HTTP security configuration (HTTPS, CORS) — see SPEC-06
- Key storage encryption at rest (doc 05 §Keys)

---

## 3. Technical decisions

- **ADR-005:** ACS issues RS256 JWTs; short `exp` (default 900s) compensates for the absence of a session
  store (deactivation takes effect on the next token lifecycle).
- **No user enumeration:** login failure responses do not distinguish between unknown login, wrong password,
  or inactive account/tenant — all return the same `401 invalid-credentials`.
- **JWK set caching:** peers set `Cache-Control: max-age=300`; they must support multiple keys in the set
  to handle key rotation without downtime.

---

## 4. JWT structure

```json
{
  "iss": "acs-service",
  "sub": "<cuidadorId (uuid)>",
  "tenant": "<tenantId>",
  "papel": "cuidadora | coordenador_clinica",
  "authorities": ["acs.cuidador.read", "acs.directory.read", "evnt.read", "evnt.confirm"],
  "iat": 1753740000,
  "exp": 1753740900,
  "kid": "acs-2026-07"
}
```

## 5. Role → authorities (total map, ADR-005)

| `papel` | Authorities |
|---|---|
| `coordenador_clinica` | `acs.cuidador.criar`, `acs.cuidador.read`, `acs.cuidador.desativar`, `acs.vinculo.criar`, `acs.vinculo.revogar`, `acs.directory.read`, `evnt.read`, `evnt.manage`, `pac.read`, `pac.manage`, `dash.read`, `hist.read` |
| `cuidadora` | `acs.cuidador.read` (self), `acs.directory.read` (self-scope), `evnt.read`, `evnt.confirm`, `dash.read` |

- THE SYSTEM SHALL derive authorities **deterministically** from `papel` at token issuance time.
- THE SYSTEM SHALL treat this map as **total**: any `papel` value SHALL resolve to a non-empty authority set; an unrecognised `papel` SHALL cause a `500 Internal Server Error` (pre-empted by the DB enum constraint).

## 6. EARS invariants — authentication

**Login**
- WHEN valid credentials (matching `login`, correct password, `status = active` caregiver, `active` tenant)
  are presented, THE SYSTEM SHALL respond `200 OK` with a signed JWT whose claims match §4 and whose `exp`
  is ≤ 900s from issuance.
- THE SYSTEM SHALL sign the JWT with the current `active` signing key (`signing_key.status = 'active'`),
  setting `kid` to `signing_key.kid`.
- THE SYSTEM SHALL never return, log, or include the raw password in any response, log line, or error body.
- IF the login is unknown, the password does not match, the caregiver `status = inactive`, or the tenant
  `status ≠ active`, THEN THE SYSTEM SHALL respond `401 Unauthorized` (`type: /errors/invalid-credentials`)
  with a body that does **not** distinguish which condition failed (no user enumeration).
- WHEN a login attempt completes (success or failure), THE SYSTEM SHALL record the corresponding fact
  (`AutenticacaoRealizada` / `AutenticacaoFalhou`) to HIST asynchronously/best-effort; HIST unavailability
  SHALL NOT delay the token response.

**JWK set**
- THE SYSTEM SHALL publish the `public_jwk` of the `active` signing key plus every `retired` key whose
  `retired_at` is within the maximum JWT TTL (900s) of `now()`, so in-flight tokens remain validatable
  across a key rotation.
- THE SYSTEM SHALL expose only the **public** component (`n`, `e`, `kid`) at `/oauth2/jwks` and SHALL
  never expose `private_key_enc` through any API, log, or error response.
- THE SYSTEM SHALL set `Cache-Control: max-age=300` on `/oauth2/jwks` responses.
- THE SYSTEM SHALL keep at most one `status = 'active'` signing key at a time (DB constraint
  `ux_signing_key_single_active`).

**Residual-window note (MVP known gap)**
- WHEN a caregiver is deactivated (§4.4 api-contract), THE SYSTEM SHALL **not** invalidate in-flight tokens
  (no server-side session store in MVP — ADR-005). The caregiver's access ends on the **next token
  expiry** (≤ 900s). Operators must be informed of this residual window; token TTL is the control.
