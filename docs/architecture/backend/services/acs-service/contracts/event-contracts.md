# ACS — Event & Integration Contracts (`acs-service`)

> Module: **ACS — Cuidadores e Acesso** · Service: `acs-service` · Package: `com.neuroassist.acs`
> Project: NeuroAssist AI · **Messaging: DISABLED** (`stack.messaging.enabled = false`)
> Generated by `/be-architect-specs neuroassist-ai ACS` · 2026-07-29
> ADR refs: ADR-004 (tenant-identity-provisioning-authority), ADR-005 (authentication-rbac-authority-model),
> ADR-006 (caregiver-patient-linkage-data-scope).

## 0. Messaging status — N/A (no broker in the MVP)

There is **no message broker / event bus** in the NeuroAssist AI MVP. ACS **publishes no asynchronous
events and consumes none.** All inter-service interactions are **synchronous REST**, routed through the
API Gateway (GWY) and discovered via the Service Registry (REG/Eureka). This document therefore has no
Kafka/Artemis/RabbitMQ topic definitions; instead it freezes:

1. The **domain facts ACS records to HIST** (audit trail for identity/access events).
2. The **outbound REST integrations** ACS depends on (MIG, PAC), as ports.
3. The **inbound read surface** ACS provides to downstream services (EVNT, EDGE, DASH, HIST, PAC).

Reevaluation trigger: if tenant count or caregiver volume grows significantly, link/role events are the
first candidates to move behind a broker — a known future decision, **not** MVP work.

## 1. Domain facts (recorded synchronously to HIST, not published to a bus)

ACS owns the identity and access lifecycle and produces six audit-worthy **domain facts**. With messaging
disabled these are **not** bus events — ACS records them to **HIST** (`hist-service`) via a synchronous
REST call at the end of the successful transaction, carrying the correlation id.

| Domain fact | Emitted when | Delivery |
|---|---|---|
| `TenantProvisionado` | Tenant transitions to `active` (§3.1 api-contract) | Synchronous REST to HIST, best-effort-with-retry |
| `CuidadorRegistrado` | Caregiver created (§4.1) | Synchronous REST to HIST |
| `CuidadorDesativado` | Caregiver deactivated (§4.4) | Synchronous REST to HIST |
| `CuidadorVinculadoAoPaciente` | Link created (§5.1) — the **anchor event** | Synchronous REST to HIST |
| `CuidadorDesvinculado` | Link revoked (§5.3) | Synchronous REST to HIST |
| `AutenticacaoRealizada` / `AutenticacaoFalhou` | Login attempt (§2.1) — success/failure | Synchronous REST to HIST, best-effort |

**Fact payload (all facts carry this envelope):**
```json
{
  "fact": "CuidadorVinculadoAoPaciente",
  "empresaId": "t_0f8a…",
  "actorId": "5c1a…",
  "correlationId": "3b9f…",
  "occurredAt": "2026-07-29T14:10:00Z",
  "payload": {
    "cuidadorId": "5c1a…",
    "pacienteId": "p_9a3f…",
    "linkId": "lnk_71b2…"
  }
}
```

**EARS — fact recording**
- WHEN an identity/access lifecycle transition (tenant provision, caregiver create/deactivate, link
  create/revoke) commits, THE SYSTEM SHALL record the corresponding domain fact to HIST synchronously
  with the same `correlationId` as the request.
- IF HIST is unreachable at fact time, THEN THE SYSTEM SHALL NOT roll back the already-committed
  transition; it SHALL enqueue the fact to a local retry outbox and retry with bounded back-off (the
  access state is authoritative; the audit trail is eventually consistent — a lost fact is a monitoring
  alert, not a data corruption).
- THE SYSTEM SHALL record login attempts (`AutenticacaoRealizada` / `AutenticacaoFalhou`) on a
  **best-effort, non-blocking basis** — HIST unavailability SHALL NOT delay the token response.
- THE SYSTEM SHALL include only identity/access metadata in facts; it SHALL NOT include biometric,
  clinical, or raw credential data in any fact payload (LGPD hard rule).

## 2. Outbound REST integrations (ports)

All outbound calls are **synchronous** dependencies implemented as REST-client adapters in the
`infrastructure` package (doc 04). `X-Correlation-Id` and `X-Empresa-Id` propagate on every call.

### 2.1 `MigProvisioningPort` → MIG (`neuroassist-ai-migrations`) — **critical, fail-closed**

| Operation | REST shape | Used by |
|---|---|---|
| `requestTenantSchema(tenantId, schemaName)` | `POST /api/mig/v1/tenants/{tenantId}/schemas` → `{schemaName, status}` | Tenant provisioning saga (ADR-004) |
| `getTenantSchemaStatus(tenantId)` | `GET /api/mig/v1/tenants/{tenantId}/schemas/status` → `{status}` | Provisioning retry (§3.3) |

**EARS — provisioning saga (ADR-004)**
- WHEN a `Tenant` is created, THE SYSTEM SHALL call `MigProvisioningPort.requestTenantSchema`
  synchronously and ONLY transition the tenant to `active` on a `2xx` response.
- IF MIG returns an error or times out, THEN THE SYSTEM SHALL leave the tenant in `status =
  provisioning` and respond `202 Accepted`; it SHALL NOT write `active` (fail-closed — invariant #8).
- WHILE the provisioning saga is in-flight, THE SYSTEM SHALL allow idempotent retries via
  `POST /api/v1/acs/tenants/{id}/provisioning:retry`.
- **Resilience:** connect/read timeout ≤ 5s (schema creation); circuit breaker OPEN → fail-closed
  (respond `202 provisioning` rather than hanging).

### 2.2 `PacPatientResolvePort` → PAC (`pac-service`) — **critical on link write, fail-closed**

| Operation | REST shape | Used by |
|---|---|---|
| `resolvePatient(pacienteId, tenantId)` | `GET /api/pac/v1/pacientes/{pacienteId}` → `{id, tenantId, valid}` | Link creation (§5.1), same-tenant validation |

**EARS — link write validation**
- WHEN a caregiver-patient link is requested, THE SYSTEM SHALL resolve `pacienteId` against PAC and
  validate that the patient belongs to the **same tenant** before writing the link.
- IF PAC returns `404` or the tenant mismatches, THEN THE SYSTEM SHALL respond `422 Unprocessable
  Entity` (`type: /errors/unknown-patient` or `cross-tenant-link`).
- WHILE PAC is unreachable within the timeout, THE SYSTEM SHALL respond `502`/`504`
  (`type: /errors/upstream-unavailable`) rather than writing an unvalidated link (fail-closed).
- **Resilience:** timeout ≤ 2s; one retry with exponential back-off; circuit breaker OPEN → fail-closed
  for link writes (a caregiver linked to a non-existent patient is a routing error, not a safe default).

## 3. Inbound integration (directory read surface, pull-based)

ACS is **read by** every other module for authentication and access decisions. No push; consumers call
synchronously. (Full endpoint shapes in `api-contract.md` §6.)

| Consumer | Reads | Endpoint | Purpose |
|---|---|---|---|
| All services | JWT validation | `GET /oauth2/jwks` | Resource-server token validation (`jwk-set-uri` via REG) |
| EVNT | Routing targets | `GET /api/v1/acs/directory/patients/{pid}/caregivers` | Who receives this patient's alarm |
| PAC, DASH, HIST | Data scope | `GET /api/v1/acs/directory/caregivers/{id}/patient-scope` | Which patients this caregiver may see |
| PAC, EVNT | Tenant validity | `GET /api/v1/acs/directory/tenants/{tenantId}` | Is this tenant active? |
| EVNT, DASH | Caregiver role | `GET /api/v1/acs/directory/caregivers/{id}` | Role and authorities resolution |
| EDGE | Auth/RBAC | JWT (validated via JWK set) + directory reads | Device pairing auth (EDGE-INT-002) |

**EARS — inbound directory**
- THE SYSTEM SHALL treat the directory surface as read-only, idempotent, and cacheable at the caller's
  discretion (responses are consistent with the state at read time; no optimistic locking on reads).
- WHEN no active caregiver resolves for a patient (`responsibleCaregivers` = empty), THE SYSTEM SHALL
  return `200 OK` with an empty array; EVNT interprets this as a routing-failure condition, not a 404.
- THE SYSTEM SHALL set `Cache-Control: max-age=60` on directory reads (caregivers/links change
  infrequently; short TTL acceptable for routing; EVNT may cache and re-resolve on cache miss).
- THE SYSTEM SHALL set `Cache-Control: max-age=300` on `/oauth2/jwks` (key rotations are rare).

## 4. Idempotency & versioning (bus-less)

- **Tenant provisioning idempotency:** `POST /api/v1/acs/tenants/{id}/provisioning:retry` is
  idempotent — already-`active` returns `200 OK` (no MIG call); already-`suspended` returns `409`.
- **Caregiver creation:** `login` uniqueness per tenant enforces natural idempotency; a duplicate
  create returns `409 login-duplicate`, not a second account.
- **Link creation:** at most one `active` link per (`cuidadorId`, `pacienteId`) — a duplicate link
  request returns `200 OK` with the existing link (idempotent no-op), not `201 Created`.
- **Link revocation:** already-`revoked` returns `200 OK` (idempotent no-op).
- **Fact versioning (HIST):** each fact carries `occurredAt` and `correlationId`;
  HIST deduplicates on `(fact, actorId, correlationId)` for at-least-once delivery.
- **Payload evolution:** REST DTOs are versioned by base path (`/v1`); a breaking change opens `/v2`;
  no event schema registry (no broker).

## 5. Summary

| Concern | MVP answer |
|---|---|
| Async events published by ACS | **none** (messaging disabled) |
| Async events consumed by ACS | **none** |
| Audit facts | 6 domain facts → HIST, **synchronous REST** |
| Outbound deps | MIG (fail-closed provisioning saga), PAC (link validation) — synchronous REST |
| Inbound read surface | JWK set + directory (routing, data-scope, tenant validity) — pull-based, cacheable |
| Future | Broker if caregiver/link volume requires async notification (doc 04 reevaluation) |
