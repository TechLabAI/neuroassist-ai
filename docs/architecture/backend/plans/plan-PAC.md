## 0. Leitura executiva

### Papel do serviço
`pac-service` é o **system of record** para `Paciente` e `Comando` na plataforma NeuroAssist AI.
É o authoring source (ADR-004): a família define gestos e seus significados; GEST executa a detecção.
Nenhum outro serviço altera o catálogo — GEST, EVNT e DASH somente lêm.

### MVP scope
O MVP cobre: cadastro de paciente com referências a dispositivos EDGE e cuidadores ACS; ciclo
completo de vida de Comando (`drafted → validated → published → (recalibrated ↻) → retired`) com
o emergency eligibility gate; catálogo pull-based (`GET .../catalogo-ativo`) para GEST via ETag;
recording síncrono de 3 domain facts em HIST; multi-tenancy schema-per-empresa; OAuth2 resource
server com scopes por endpoint.

### Diagnóstico inicial
- Pontos de complexidade: (1) emergency gate fail-closed/advisory assimetria (SPEC-03); (2) schema
  routing multi-tenant (TenantSchemaResolver); (3) fatos síncronos HIST com outbox de retry
  (messaging desabilitado → fallback resilient); (4) `catalogoVersao` como ETag do catálogo (SPEC-02 §6).
- Riscos: GEST indisponível durante publish de emergência → user-facing 503 (design intencional);
  HIST indisponível → fato perdido até retry do outbox (aceitável: não crítico para segurança).

## 1. Estratégia geral

### Objetivo macro
Entregar um `pac-service` production-ready que: (1) exponha o contrato REST completo de SPEC-01;
(2) execute o estado machine de Comando com todos os guards (SPEC-02); (3) aplique o gate de
emergência (SPEC-03) de forma segura; (4) forneça o catálogo pull-based para GEST; (5) seja
multi-tenant por schema; (6) seja observável e testado com BDD.

### Ordem das prioridades

| P | Título | Motivo |
|---|---|---|
| P1 | Scaffold + contratos mínimos | Base sem a qual nada compila |
| P2 | Paciente CRUD golden path | Unblocks P4 (Comando precisa de Paciente) |
| P3 | Persistence + migrations + tenant routing | Unblocks integração JPA real |
| P4 | Comando authoring draft + ACS/EDGE clients | Golden path base de Comando |
| P5 | Lifecycle core: validate/publish/retire + gate + GEST client | Feature central de segurança |
| P6 | Recalibrate + catalogoVersao + catálogo-ativo + HIST client | Completa o ciclo |
| P7 | Security OAuth2 + error handling | Gate de produção |
| P8 | Idempotency + test infra WireMock | Robustez de retentativas |
| P9 | Observability + BDD gate | Validação end-to-end (gate diferido M2.5) |

## 2. Plano por prioridade

### Prioridade 1 — Scaffold + contratos mínimos
Status: pendente

#### Objetivo / Resultado esperado
Subprojeto Gradle compilável com todos os DTOs, port interfaces e entidades JPA declaradas.
`./gradlew :pac-service:compileJava` verde.

#### Issues vinculadas
- PAC-001 (Gradle subproject)
- PAC-002 (DTOs)
- PAC-003 (port interfaces)
- PAC-004 (JPA entities)

#### Specs cobertas
- SPEC-01 (DTOs derivados da API surface)
- SPEC-04 (entidades derivadas do data-model)
- SPEC-10 (port interfaces derivadas de integrations)

#### Sequência de execução
1. PAC-001: build.gradle.kts + application.yml + PacServiceApplication
2. PAC-003: port interfaces (nenhuma dep de infra)
3. PAC-002: DTOs (referencia enums das ports)
4. PAC-004: entidades JPA (referencia enums)

#### Critérios de aceite
- `./gradlew :pac-service:compileJava` sem erros
- Nenhuma port interface importa classe Spring/JPA/HTTP
- Bean Validation rejeita `CreateComandoRequest` com timing inválido antes de chegar ao service

#### Riscos
- Versão de Spring Boot / Spring Cloud pode conflitar com Resilience4j — alinhar no BOM

#### Instrução para implementador
Começar pelo `PacServiceApplication` mínimo (sem security ainda). Definir todos os enums
(`Sensibilidade`, `Urgencia`, `EstadoComando`) no package `domain` antes de qualquer entidade.
NÃO configurar datasource nesta prioridade — apenas compilar.

### Prioridade 5 — Lifecycle core: validate/publish/retire + emergency gate + GEST client
Status: pendente

#### Objetivo / Resultado esperado
Transições `:validate`, `:publish`, `:retire` funcionando com emergency gate seguro (fail-closed
para emergência). GEST client com Resilience4j CB configurado.

#### Issues vinculadas
- PAC-014 (ComandoLifecycleService.validate)
- PAC-015 (ComandoLifecycleService.publish)
- PAC-016 (ComandoLifecycleService.retire)
- PAC-017 (EmergencyEligibilityGate)
- INT-PAC-001 (GestDetectabilityClient + Resilience4j CB)

#### Specs cobertas
- SPEC-02 §5.2–§5.5 (lifecycle transitions)
- SPEC-03 (emergency gate — full spec)
- SPEC-10 §4 (GestDetectabilityPort resilience)

#### Sequência de execução
1. INT-PAC-001: GestDetectabilityClient + Resilience4j CB
2. PAC-017: EmergencyEligibilityGate (depende do client)
3. PAC-014: ComandoLifecycleService.validate
4. PAC-015: ComandoLifecycleService.publish (depende do gate)
5. PAC-016: ComandoLifecycleService.retire

#### Critérios de aceite
- Emergency publish com GEST retornando `supported=false` → `422 emergency-not-detectable`
- Emergency publish com GEST timeout → `503 eligibility-gate-unavailable` + `Retry-After: 30`
- Routine publish com GEST indisponível → `200` com `warnings[]` (advisory)
- `:retire` em comando `retired` → `409 invalid-lifecycle-transition`
- Linha retirada permanece no banco (ADR-006)

#### Riscos
- **Safety-critical:** gate fail-closed é a proteção de Márcio Amaral. Testar exaustivamente o
  caso timeout/CB OPEN antes de passar para P6.

### Prioridade 6 — Recalibrate + catalogoVersao + catálogo-ativo + HIST client

atomicamente. `GET .../catalogo-ativo` retorna apenas `published` com ETag e 304. HIST recebe

#### Issues vinculadas
- PAC-018 (ComandoLifecycleService.recalibrate)
- PAC-019 (PacienteVersionBumper)
- PAC-020 (CatalogoAtivoController + Service)
- INT-PAC-004 (HistFactClient + outbox)

#### Specs cobertas
- SPEC-02 §5.4 (recalibrate), §6 (catalogoVersao)
- `contracts/api-contract.md` §5 (catalogo-ativo)
- `contracts/event-contracts.md` §1 (domain facts)

#### Sequência de execução
1. PAC-019: PacienteVersionBumper + V0005 migration
2. INT-PAC-004: HistFactClient + outbox (configurar antes de publish usar)
3. PAC-018: ComandoLifecycleService.recalibrate
4. PAC-020: CatalogoAtivoController + CatalogoAtivoService

#### Critérios de aceite
- `:recalibrate` lowering urgência de emergência → gate NÃO re-executado

- `GET .../catalogo-ativo` com ETag correto → `304` sem body
- HIST indisponível: lifecycle commitado, fato no outbox (sem rollback)

## 4. Restrições arquiteturais

- ArchUnit RULE-01..08: camadas hexagonais (api/application/domain/infrastructure)
- `@Transactional` somente em `application.service` — nunca em `api` ou `infrastructure`
- Nenhuma entidade JPA exposta diretamente ao controller — apenas DTOs
- Cross-service refs (`primitivo_*_id`, `dispositivo_edge_id`, `cuidador_responsavel_id`) são
  UUIDs simples — **sem FK no banco** (SPEC-04 §3)
- PAC **não** roda Flyway embarcado — migrations entregues ao MIG (SPEC-04 §5)
- Emergency gate: qualquer dúvida sobre detectabilidade = fail-closed para `urgencia=emergencia`
  (ADR-005 — requisito de segurança de Márcio Amaral)
- ADR-006: nenhum `Comando` é hard-deleted — `retired` é terminal e permanente
