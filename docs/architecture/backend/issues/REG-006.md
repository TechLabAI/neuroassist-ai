# REG-006 -- Configurar liveness e metricas de self-preservation como sinal de operador

**Status:** INTACT -- gerado 2026-07-27

## Contexto
SPEC-03 exige que o estado de self-preservation seja exposto como metrica/sinal observavel para o operador de forma que ele possa diagnosticar situacoes de frota com renewal rate abaixo do threshold. SPEC-07 requer liveness separado do readiness -- liveness reflete "servidor no ar", readiness reflete "registry aceitando registros". Esses dois grupos devem ser endpoints independentes no Actuator.

## Spec de referencia
- SPEC-03, SPEC-07

## Escopo
- [ ] implementar `backend/services/neuroassist-ai-service-registry/src/main/resources/application.yml`
- [ ] Garantir que `/actuator/health` (liveness) reporta UP independentemente do estado de self-preservation ou readiness
- [ ] Criar gauge `eureka.self.preservation.active` (0 = normal, 1 = self-preservation ativo) via `MeterRegistry`
- [ ] Adicionar comentario no `application.yml` indicando como interpretar a metrica de self-preservation em producao
- [ ] Configurar grupos de Actuator: `management.endpoint.health.group.liveness.include=livenessState`, `management.endpoint.health.group.readiness.include=readinessState,registryReadiness`

## Criterios de aceite
- [ ] `GET /actuator/health` retorna UP mesmo com self-preservation ativo (metrica = 1)
- [ ] `GET /actuator/prometheus` contem `eureka_self_preservation_active` como gauge
- [ ] `GET /actuator/health/liveness` e `GET /actuator/health/readiness` sao endpoints independentes com semanticas distintas
