**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.3

## Contexto

`MigProvisioningClient` é uma interface vazia e `MigProvisioningAdapter` traz, nas linhas 33 e 53:

```java
// TODO (ACS-009/P3): call migProvisioningClient.requestSchema(tenantId, schemaName)
// TODO (ACS-009/P3): call migProvisioningClient.getSchemaStatus(tenantId)
```

Provisionar um tenant **não cria schema nenhum**. O adapter devolve sucesso, o
`ProvisionTenantUseCase` grava a linha em `neuroassist_global.tenant` com `schema_nome`
preenchido, e o schema não existe.

As 6 sessões de E2E rodaram contra o tenant seedado (`t_emp_dev`), então este caminho **nunca foi
exercitado**. É o passo 1 do Flow-01 (E2E-009) e é a diferença entre "o sistema tem
multi-tenancy" e "o sistema tem um tenant".

ACS-009 está marcada DONE — ela cobria os adapters JPA do schema global, não a integração com MIG.

## Escopo

- Definir a superfície do `neuroassist-ai-migrations` como serviço. Hoje ele é um job de container,
  não um serviço com API: ou ganha `POST /schemas` + `GET /schemas/{tenantId}`, ou o ACS aplica
  Flyway programaticamente contra o tenant recém-criado.
- A decisão precede a implementação — as duas opções têm consequências operacionais distintas
  (um serviço a mais no compose × o ACS ganhar credencial DDL).
- Provisionamento é assíncrono por natureza: o tenant precisa de estado
  (`provisioning` → `ready` → `failed`).

## Implementado em 2026-08-23

**A decisão de ADR já estava tomada nos documentos** — `plan-MIG` §0 ("provisionamento de tenant
determinístico e idempotente … invocado sincronamente por ACS"), P1 ("API surface — job dispatch +
HTTP interno") e `api-contract` §1.1. Não havia escolha a fazer, havia contrato a implementar.

| Peça | Onde |
|---|---|
| Face HTTP interna | `TenantProvisioningController` — `PUT/GET /internal/migrations/tenants/{tenantId}` |
| Orquestração | `TenantSchemaProvisioningService` + ports `SchemaMigrationPort` / `TenantCatalogPort` |
| Flyway programático | `FlywaySchemaMigrationAdapter` |
| Registro global | `JdbcTenantCatalogAdapter` (JDBC puro, tabela qualificada) |
| Segurança | `ApiSecurityConfig` — resource server, `migrations:internal`, união `scope` + `authorities` |
| Consumidor | `MigProvisioningClient` + `MigProvisioningAdapter` (identidade de serviço sem claim de tenant) |
| Infra | `migrations-api` no compose; `MIG_SERVICE_URL` no acs-service |

### As duas faces do MIG não podem se misturar

O jar é o mesmo; o que separa é o profile `api`. O `application.yml` mantém
`web-application-type: none` e só o profile o promove a servlet. **Se o starter web promovesse o
processo a servidor por padrão, os contêineres `migrations-global` e `migrations-empresa` nunca
terminariam** — e o `depends_on: service_completed_successfully` travaria a subida do stack
inteiro. O profile também desliga o Flyway de startup: esta face migra um schema diferente por
requisição.

### Três defeitos encontrados ao implementar

1. **A transação do ACS escondia o próprio tenant do MIG.** `TenantService` é `@Transactional` no
   nível da classe, então o INSERT do passo 1 só ficava visível no commit — depois da chamada ao
   MIG. O MIG, lendo pela sua própria conexão, respondia `422 invalid-tenant-id` para um tenant
   que o ACS acabara de criar. É a mesma família da armadilha de vinculação de tenant registrada
   em CLAUDE.md: trabalho que uma **segunda** conexão precisa enxergar não pode viver dentro da
   transação da primeira. Corrigido com `PROPAGATION_REQUIRES_NEW` no passo 1 — "persistir a
   intenção e depois agir" só significa algo quando a intenção é durável antes do ato.
2. **O lock de advisory vazaria pelo pool.** Um advisory lock do Postgres pertence à *sessão*;
   tomá-lo por um `JdbcTemplate` travaria numa conexão e liberaria em outra, deixando o lock preso
   e o unlock silencioso — a segunda chamada do mesmo tenant responderia 409 para sempre. Lock,
   trabalho e unlock compartilham uma conexão explícita.
3. **A regra ArchUnit RULE-05 do MIG apontava para o alvo errado.** `..api..` também casa com
   `org.flywaydb.core.api`: no momento em que um adapter de infraestrutura tocou a API pública do
   Flyway, a regra acusou 16 violações que nada tinham a ver com fronteira hexagonal. Ancorada em
   `com.neuroassist.mig.api..`. Uma regra que dispara no alvo errado é silenciada, e regra
   silenciada não protege nada.

### Validação no stack real

| Passo | Resultado |
|---|---|
| `migrations-api` sobe e os jobs continuam terminando | `migrations-empresa Exited (0)`, API `UP` na 8091 |
| `POST /api/v1/acs/tenants` | **201 ACTIVE** com `schemaNome` preenchido |
| O schema existe? | sim — **30 tabelas**, `flyway_schema_history` em **0800**, idêntico ao `t_emp_dev` seedado |
| Retry de tenant que ficou `PROVISIONING` | 200 ACTIVE, schema criado — 22 migrations aplicadas |
| Tenants no ambiente de dev ao final | 4, todos com schema real de 30 tabelas |

Gates: MIG 22 testes (9 unitários + 5 IT com Testcontainers + ArchUnit), 0 falhas. ACS `test` +
`architectureCheck` verdes.

### O que a validação revelou e esta issue não resolve

**[E2E-029](E2E-029.md) (C-48) — um tenant novo nasce vazio e ninguém consegue entrar nele.**
Criar o primeiro cuidador do tenant novo responde `403 acs.tenant.mismatch`, e corretamente: um
coordenador da clínica A não pode criar pessoas na clínica B. Só que esse é o único caminho que
existe, e o tenant recém-criado não tem nenhum cuidador de quem partir. O schema fica perfeito e
inalcançável. O seed resolve isso para `t_emp_dev` inserindo linhas direto no banco — que é
exatamente por que as seis sessões anteriores nunca esbarraram nisto.

Portanto: **o schema passou a ser criado de verdade — que era o defeito desta issue — mas o
onboarding de uma empresa nova ainda não fecha.**
