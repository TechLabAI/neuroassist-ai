# E2E-016 — ACS não provisiona schema de tenant: `MigProvisioningAdapter` é no-op

**Módulo:** E2E Cross-Service (ACS + MIG)
**Fase:** F9 — Flow-01 (passo 1)
**Prioridade:** P1
**Status:** OPEN
**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.3

---

## Contexto

`MigProvisioningClient` é uma interface vazia e `MigProvisioningAdapter` traz, nas linhas 33 e 53:

```java
// TODO (ACS-009/P3): call migProvisioningClient.requestSchema(tenantId, schemaName)
// TODO (ACS-009/P3): call migProvisioningClient.getSchemaStatus(tenantId)
```

Provisionar um tenant **não cria schema nenhum**. O adapter devolve sucesso, o
`ProvisionTenantUseCase` grava a linha em `neuroassist_global.tenant` com `schema_nome`
preenchido, e o schema não existe.

As 6 sessões de E2E rodaram contra o tenant seedado (`t_emp_dev`), então este caminho **nunca foi
exercitado**. É o passo 1 do Flow-01 (E2E-009) e é a diferença entre "o sistema tem
multi-tenancy" e "o sistema tem um tenant".

ACS-009 está marcada DONE — ela cobria os adapters JPA do schema global, não a integração com MIG.

## Escopo

- Definir a superfície do `neuroassist-ai-migrations` como serviço. Hoje ele é um job de container,
  não um serviço com API: ou ganha `POST /schemas` + `GET /schemas/{tenantId}`, ou o ACS aplica
  Flyway programaticamente contra o tenant recém-criado.
- A decisão precede a implementação — as duas opções têm consequências operacionais distintas
  (um serviço a mais no compose × o ACS ganhar credencial DDL).
- Provisionamento é assíncrono por natureza: o tenant precisa de estado
  (`provisioning` → `ready` → `failed`).

## Checklist

- [ ] ADR: MIG como serviço com API × Flyway programático no ACS
- [ ] Contrato `requestSchema` / `getSchemaStatus` escrito a partir do produtor, nunca da suposição do consumidor
- [ ] `MigProvisioningClient` implementado + adapter chamando de verdade
- [ ] Estado de provisionamento em `neuroassist_global.tenant`
- [ ] Flow-01 executado ponta a ponta com um tenant **novo**, não o seedado
- [ ] Falha de provisionamento não deixa tenant meio-criado utilizável

## Critério de aceite

`POST /api/v1/acs/tenants` com um tenant novo → esperar `ready` → login → criar paciente nesse
tenant, tudo sem tocar em `docker compose up migrations-empresa`.
