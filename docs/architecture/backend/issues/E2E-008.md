## Objetivo

Verificar que o DASH lê a timeline de histórico do HIST com escopo correto por papel (`hist:read` vs `hist:read:all`), e que o poll de liveness do EDGE reflete o estado real do dispositivo com suporte a ETag/304.

## Cenários de Validação

### Timeline (DASH → HIST)

| ID | Cenário | Critério |
|---|---|---|
| DSH-01 | Cuidador lê timeline dos seus pacientes | apenas fatos dos pacientes vinculados ao cuidador retornados |
| DSH-02 | Coordenador lê timeline completa | fatos de todos os pacientes do tenant (`hist:read:all`) |

### Liveness (DASH → EDGE)

| ID | Cenário | Critério |
|---|---|---|
| DSH-03 | Liveness de dispositivo online | `GET /api/v1/edge/devices/{id}/liveness` → `status=online` dentro do staleness window |
| DSH-04 | Liveness de dispositivo offline | heartbeat parado > `stalenessThresholdSeconds` → `status=offline` derivado em tempo de leitura |
| DSH-05 | ETag / 304 em liveness sem mudança | dois polls consecutivos sem mudança de status → `304 Not Modified` no segundo |

## Invariantes (dos contratos)

- Liveness `status` é derivado em read-time — não é cacheado no EDGE (ADR-006 R2)
- ETag keyed no "derived-status bucket" → `online→offline` sempre invalida o cache mesmo sem novo heartbeat
- Cuidador com `hist:read` NUNCA vê dados de pacientes fora do seu escopo (HIST fail-closed via ACS)

## Checklist

- [ ] DSH-01: cuidador vê apenas seus pacientes
- [ ] DSH-02: coordenador vê todos sem chamar ACS
- [ ] DSH-03: `status=online` dentro do threshold
- [ ] DSH-04: `status=offline` derivado corretamente após inatividade
- [ ] DSH-05: `304` retornado no segundo poll sem mudança de status
