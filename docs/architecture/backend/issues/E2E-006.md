# E2E-006 — PAC ↔ EDGE: validação de dispositivo ao registrar paciente

**Módulo:** E2E Cross-Service  
**Fase:** F6 — PAC ↔ EDGE  
**Prioridade:** P2  
**Status:** OPEN  
**Criado em:** 2026-08-20  
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md)

---

## Objetivo

Verificar que PAC valida a referência `dispositivo_edge_id` no EDGE ao registrar ou atualizar um paciente — garantindo a integridade referencial cross-service (framing invariant #5: um `200` de EDGE significa que o dispositivo está registrado e pareado ao paciente).

## Fluxo

```
PUT /api/v1/pac/patients/{id} (com dispositivo_edge_id)
    → PAC chama EDGE: GET /api/v1/edge/patients/{pacienteId}/device
    → 200: dispositivo válido e pareado → PAC aceita
    → 404: dispositivo ausente ou não pareado → PAC rejeita com 422
```

## Cenários de Validação

| ID | Cenário | Critério |
|---|---|---|
| DEV-01 | Paciente com dispositivo pareado válido | PAC aceita → `200` |
| DEV-02 | `dispositivo_edge_id` não registrado no EDGE | PAC rejeita → `422` com referência inválida |
| DEV-03 | Dispositivo registrado mas não pareado ao paciente | EDGE retorna `404 patient-not-paired` → PAC `422` |
| DEV-04 | EDGE indisponível ao registrar paciente | comportamento documentado: fail-open (aceita) ou fail-closed (rejeita) — validar conforme implementação PAC |

## Invariantes (dos contratos)

- PAC não mantém FK para EDGE — validação é por chamada (cross-service reference, ADR-005)
- EDGE não recebe dados de paciente além do `id` na URL
- DEV-04: verificar e documentar a política de fallback real do PAC (não assumir)

## Checklist

- [ ] DEV-01: dispositivo pareado → PAC aceita registro
- [ ] DEV-02: device fantasma → PAC rejeita com `422`
- [ ] DEV-03: device não pareado → PAC rejeita com `422`
- [ ] DEV-04: comportamento de EDGE down documentado e testado
