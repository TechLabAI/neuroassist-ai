**Fechado em:** 2026-08-23

## Contexto

`permission-catalogue.arch.json` declarava códigos granulares para o EDGE
(`edge.device-registration.criar`, `edge.pairing.criar`, `edge.liveness.read`, …) que **não
existiam no código**. O código usa códigos coarse: `edge.manage`, `edge.read`, `edge.device`,
`edge.internal`.

O `CrossAspectArchTest` do EDGE deveria guardar essa sincronia. Ele não guardava: o catálogo estava
**pinado inline no próprio teste, contendo as duas famílias**. O teste que existia para detectar a
divergência aceitava os dois lados dela.

---

## Decisão: alinhar ao código (coarse)

**Opções consideradas:**

| Opção | Custo | Risco |
|-------|-------|-------|
| Manter granular (spec) | Alto — exige mexer em `RoleAuthorityPolicy` (ACS) e em todos os `@PreAuthorize` do EDGE | ACS está sendo modificado em paralelo por outra frente; janela de merge conflict é real |
| Alinhar ao código (coarse) | Baixo — só o catálogo e o ArchUnit | Nenhum — é o estado que já roda em produção |

**Decisão: coarse**, pelas razões abaixo:

1. O que roda é o que conta. `edge.manage`, `edge.device`, `edge.read`, `edge.internal` são as
   authorities verificadas em cada `@PreAuthorize` e em `SecurityConfig`. Granular é intenção de
   design, não realidade de runtime.
2. Migração para granular requer coordenação multi-serviço: ACS precisa emitir os códigos novos
   no JWT (`authorities`), `RoleAuthorityPolicy` precisa ser atualizado, e todo endpoint do EDGE
   precisa ser reescrito. Isso é uma iteração futura, não este PR.
3. Um catálogo que lista authorities que nunca foram verificadas em nenhum endpoint é pior do que
   inútil: dá falsa sensação de granularidade enquanto qualquer papel com `edge.manage` faz tudo.

**Família coarse adotada:**
- `edge.manage` — operações destrutivas (registrar, retirar, parear, revogar pareamento)
- `edge.device` — heartbeat (tokens de dispositivo)
- `edge.read` — consultas (liveness, lista de pareamentos)
- `edge.internal` — endpoints service-to-service

## Controle negativo

Introduzido temporariamente `@PreAuthorize("hasAuthority('edge.nonexistent')")` em
`LivenessController.getLivenessForPatient`. Resultado:

```
CrossAspectArchTest > cra01_preauthorize_in_catalogue FAILED
    java.lang.AssertionError at ArchRule.java:94

5 tests completed, 1 failed
```

Confirmado: o guard falha quando uma authority fora do catálogo é introduzida. Após remover a
anotação de teste, todos os 5 testes do `CrossAspectArchTest` passam novamente.

## Auditoria dos outros 6 serviços

**Todos os 6 serviços têm o mesmo padrão de catálogo pinado inline:**

| Serviço | Linha 38–39 do CrossAspectArchTest |
|---------|-----------------------------------|
| `acs-service` | `Set.of(…)` inline |
| `dash-service` | `Set.of(…)` inline |
| `evnt-service` | `Set.of(…)` inline |
| `gest-service` | `Set.of(…)` inline |
| `hist-service` | `Set.of(…)` inline |
| `pac-service` | `Set.of(…)` inline |

Cada um deles tem o mesmo risco: uma divergência entre o código e o catálogo inline pode
existir sem que o teste detecte, porque o teste é a sua própria referência. Não foram corrigidos
aqui — essa issue cobre apenas o EDGE. Os outros devem receber o mesmo tratamento em issues
separadas.
