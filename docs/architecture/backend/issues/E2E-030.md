# E2E-030 — Tenant provisionado pela API congela na versão do template e nunca mais migra (C-50)

**Módulo:** MIG (+ infra)
**Fase:** F1 — Infra
**Prioridade:** P1
**Status:** ✅ DONE (2026-08-23) — leque implementado e frota convergida no stack
**Criado em:** 2026-08-23 — descoberto ao validar E2E-017 contra o stack real
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2 · [plan-MIG.md](../plans/plan-MIG.md) P2

---

## Contexto

E2E-016 fez o `POST /tenants` criar o schema do tenant e aplicar o template de empresa **até o
head do momento**. O que não existe é o que acontece depois: quando uma migration nova de tenant
entra (foi o caso de `V0501__evnt_hist_outbox.sql`, desta mesma sessão), **nada a aplica aos
schemas já provisionados**.

Estado observado no ambiente de dev logo após a V0501 entrar:

```
t_emp_dev                            evnt_hist_outbox = 1   ← migrado pelo job
t_c1a272310b25405397ecb2c27ebec965   evnt_hist_outbox = 0
t_b7249d26702149c2b2d9211ad1d6e427   evnt_hist_outbox = 0
t_3446bf9620f14c4d8e8fe1afefeb562a   evnt_hist_outbox = 0
t_70ea0372ad984a4b8031e1f786e55b5d   evnt_hist_outbox = 0
```

E o sintoma, uma vez por tick do sweeper, por tenant:

```
Audit outbox drain failed for tenant 7ad262d8-… :
  ERROR: relation "evnt_hist_outbox" does not exist
```

## Causa

O contêiner `migrations-empresa` migra **um schema fixo**:

```yaml
FLYWAY_SCHEMAS: t_emp_dev
```

Isso bastava enquanto existia um tenant só — e existia um tenant só justamente porque o
provisionamento era um stub (E2E-016). Assim que criar empresas passou a funcionar, o job de
deploy virou o gargalo: ele conhece um schema, e a plataforma tem N.

`plan-MIG` P2 e o `api-contract` §2 já preveem a peça que falta — o modo `migrate-all`, cujo alvo
é *"`neuroassist_global` + every existing tenant schema"*. Ele nunca foi implementado.

## Por que é P1

Não é degradação parcial: um tenant que perde uma migration passa a rodar contra um schema que o
código não espera. Aqui foi um outbox de auditoria e o sintoma é barulhento. Fosse uma coluna nova
numa tabela de alarme, o sintoma seria um alarme que não grava — e o log estaria num sweeper que
ninguém lê.

## Escopo

- Modo `migrate-all` do job: enumera os tenants do catálogo global e migra cada schema, em ordem
  determinística, fail-fast por schema (plan-MIG P2, riscos R2/R5)
- O contêiner `migrations-empresa` passa a usar esse modo em vez de `FLYWAY_SCHEMAS` fixo
- Um schema falhado não pode impedir os demais de convergirem, e o run report tem de dizer quais
  ficaram para trás (exit code 2 = frota em versões mistas, api-contract §3)
- Endpoint de status por tenant para responder "quem está atrasado" sem abrir o banco
- Regularizar os 4 tenants de dev listados acima

## Checklist

- [x] `--mode=migrate-all` implementado com fan-out por tenant
- [x] `migrations-empresa` migrado para o novo modo
- [x] Falha de um schema não interrompe os outros; run report lista os divergentes
- [x] `GET /internal/migrations/status` (api-contract §1.2) reporta a versão de cada tenant —
      sem o parâmetro `scope`, que só faz sentido quando a frota for grande demais para listar
- [x] Teste: provisionar tenant, adicionar migration nova, rodar `migrate-all`, os dois convergem
- [x] Tenants órfãos do ambiente de dev regularizados

## Critério de aceite

Adicionar uma migration de tenant e, após o passo de deploy, **todo** schema de tenant estar na
mesma versão — verificável sem consultar o banco.

## Dependência

E2E-016 (implementada — é ela que torna N tenants possíveis)

## Implementado em 2026-08-23

| Peça | Onde |
|---|---|
| Leque | `MigrateAllUseCase` + `MigrateAllService` |
| Dispatcher de `--mode` + exit codes | `MigrationJobRunner` |
| Cede o controle do Flyway ao runner | `JobModeFlywayConfig` |
| Migrations globais programáticas | `FlywaySchemaMigrationAdapter.migrateGlobalToHead` |
| Enumeração de schemas | `JdbcTenantCatalogAdapter.allTenantSchemas` |
| Status da frota | `MigrationStatusController` |
| Job de deploy | `migrations-empresa` → `--neuroassist.mig.mode=migrate-all` |

### O modo não pode existir por default

`MigrationJobRunner` é `@ConditionalOnProperty(name = "neuroassist.mig.mode")` e o modo chega por
**argumento**, não pelo `application.yml`. Declarado lá com default vazio, a chave passaria a
existir sempre e a condição casaria mesmo sem modo — o `migrations-global`, que ainda depende do
comportamento antigo (Flyway do Spring migrando o que `FLYWAY_SCHEMAS` nomeia), passaria a rodar
outro caminho sem ninguém pedir.

Pela mesma razão o controle do Flyway é cedido por um `FlywayMigrationStrategy` no-op e não por
`spring.flyway.enabled: false`: a escolha fica expressa **uma vez**, junto do modo, em vez de
virar uma segunda variável de ambiente que alguém teria de manter de acordo com a primeira.

### Três estados de falha, não um

Um `migrate-all` que responde só "falhou" não serve a um pipeline. Os códigos separam o que o
operador faz a seguir: **1** invocação errada (nada rodou), **2** um ou mais schemas falharam —
**a frota está em versões mistas, não faça rollout** —, **3** pré-flight (o catálogo estava
ilegível, nada foi tentado, nada ficou pela metade). E o run report **nomeia** os schemas
divergentes: "2 de 9 falharam" sem dizer quais devolve o operador ao banco, que é exatamente o
que este relatório substitui.

### Um defeito meu, encontrado ao validar

O `GET /internal/migrations/status` nasceu guardado por `migrations:internal` — a identidade que
o **acs-service** usa para chamar o MIG. O token do `platform-ops` levou **403** na primeira
tentativa de usá-lo: eu tinha criado um endpoint de operador cuja authority nenhum operador
consegue obter. O `api-contract` §1.4 já previa `migrations:admin` para operadores, e é ela que o
`platform-ops` passou a carregar.

### Validação no stack real

| Antes | Depois |
|---|---|
| 4 dos 5 schemas sem `evnt_hist_outbox` | 5 de 5, todos com **23 migrations** |
| `migrations-empresa` migrava `t_emp_dev` | `Fanning out to 5 tenant schema(s)` → `All 6 schema(s) converged`, exit 0 |
| Sweeper do EVNT: `relation "evnt_hist_outbox" does not exist` a cada tick | zero erros na janela seguinte |
| "quem está atrasado?" só abrindo o banco | `GET /internal/migrations/status` lista global + cada tenant |

Gates: MIG 30 testes (unitários + 2 ITs com Testcontainers + ArchUnit), 0 falhas.

### O que ficou de fora

- **`--dry-run` recusa em vez de fingir.** O `api-contract` §2 o prevê; até existir, pedi-lo
  responde exit 1 com o motivo, em vez de migrar como se o flag não estivesse lá.
- **`provision-tenant` e `info` como modos de job** — a API interna já cobre o primeiro, e o
  segundo é o endpoint de status. Ficam para quando houver operação por linha de comando.
- **`POST /internal/migrations/run`** (api-contract §1.3) não existe: disparar migração por HTTP
  é poder diferente de consultá-la, e não foi preciso para fechar esta issue.
