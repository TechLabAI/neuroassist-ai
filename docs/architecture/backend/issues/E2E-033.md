## Contexto

O `GET /gest-service/detection-profile/active` diz **quais** gestos estão ativos. Não diz **com
que sensibilidade** detectá-los. Os limiares EAR/BRI são constantes de código no agente de borda,
iguais para todo paciente.

Do outro lado da fronteira, o PAC tem a calibração por paciente inteira:

```sql
CREATE TABLE comando (
    paciente_id             uuid NOT NULL,
    primitivo_principal_id  uuid NOT NULL,   -- → tipo_gesto do GEST
    sensibilidade           text NOT NULL,   -- baixa | media | alta
    tempo_min_gesto_ms      integer NOT NULL,
    tempo_max_gesto_ms      integer NOT NULL,
    ...
```

`sensibilidade`, o mínimo e o máximo de duração — tudo por comando, por paciente. E nada disso
chega ao agente. ALS afeta cada pessoa de forma diferente; um espasmo involuntário numa pessoa é o
gesto voluntário de outra. A cuidadora escolhe "alta" na tela e não acontece absolutamente nada.

## O que existe hoje, e por que não serve

`DetectionProfile` tem `classificationParams`, um `Map<String,Object>` livre. O comentário da
coluna promete o que ninguém entrega:

```sql
COMMENT ON COLUMN detection_profile.classification_params IS
  'jsonb: confidenceThreshold, minWindowMs, maxWindowMs, compositeMaxGapMs.';
```

Nenhuma dessas quatro chaves é escrita em lugar nenhum do código. Nenhuma é lida. O mapa é um
`Map<String,Object>` sem validação: publicar `{"earClose": "muito"}` é aceito, persistido e servido.
Existe transporte, e ele nunca transportou nada.

## O obstáculo estrutural (por que isto nunca foi plugado)

```sql
CREATE UNIQUE INDEX ux_profile_single_active ON detection_profile (active) WHERE active = true;
```

**Um perfil ativo por empresa.** A sensibilidade é por paciente. Não foi esquecimento de fiação —
o modelo atual não consegue expressar "o limiar deste paciente". Ligar o `comando.sensibilidade`
do PAC ponta a ponta exige romper esse invariante, resolver `device → paciente` (o GEST hoje só
resolve `device → tenant`) e trazer o dado do PAC. É uma mudança de modelo, não uma correção.

## Decisão de escopo

**Fazer o transporte tipado agora; a rota por paciente fica para uma issue própria.**

Esta issue entrega o cano e a validação. Continua por empresa. Com o cano no lugar, ligar a
sensibilidade por paciente vira escolher uma faixa — não redesenhar o contrato.

## O que muda

1. **`classificationParams` (mapa livre) → `thresholds` (tabela tipada e validada).** Três faixas,
   cada uma com o conjunto completo de limiares EAR/BRI. Persistida no mesmo `jsonb`.

2. **`media` reproduz exatamente o comportamento de hoje.** Adotar o perfil não muda nada até
   alguém escolher outra faixa. Essa é a propriedade que torna a mudança segura.

3. **Cada primitivo publicado carrega sua faixa** (`sensibilidade`), snapshotada no publish. Default
   `media`.

4. **O `/active` passa a devolver os primitivos.** Hoje eles são persistidos e nunca devolvidos —
   ver o defeito abaixo.

5. **O agente lê do perfil**, com as constantes de código como fallback declarado (offline, ou
   perfil sem limiares).

## Direção da sensibilidade — invariante que o código passa a garantir

Sensibilidade **alta** = dispara mais fácil. Para o EAR isso é um limiar **maior** (`ear_avg <
EAR_CLOSE` acusa fecho antes), e menos frames de sustentação. Para o BRI é um limiar **menor**
(`bri > BRI_RAISE_ON`).

| | baixa | media | alta |
|---|---|---|---|
| `earClose` | 0.19 | **0.22** | 0.25 |
| `earOpen` | 0.24 | **0.27** | 0.30 |
| `earOtherMax` | 0.27 | **0.30** | 0.33 |
| `blinkMinFrames` | 3 | **2** | 2 |
| `doubleBlinkWindowMs` | 1500 | **2000** | 2500 |
| `briRaiseOn` | 0.34 | **0.30** | 0.26 |
| `briRaiseOff` | 0.26 | **0.22** | 0.18 |
| `briOtherMax` | 0.29 | **0.25** | 0.21 |
| `browMinFrames` | 7 | **5** | 3 |

A coluna `media` em negrito é, valor por valor, o que está hoje em `edge_agent_core.py`.

Um perfil onde "alta" detecta menos que "baixa" é um perfil sem sentido, então a monotonicidade
entre faixas passa a ser validada, não só a coerência dentro de cada faixa.

## Defeito vivo encontrado no caminho

`DetectionProfileResponse` **não tem campo `primitives`**. O agente sempre-ligado faz:

```python
primitives = data.get("primitives", [])
if not primitives:
    print("\n[ERRO] Perfil ativo não possui primitivos. Publique o perfil na UI.")
    sys.exit(1)
```

Contra um GEST real ele **sempre** aborta na partida. Sai junto nesta issue.

## Validação (2026-08-24)

### Critério de aceite — no stack rodando

Migration aplicada de verdade (`bootJar` + containers), **5 schemas de tenant convergidos** pelo
`migrate-all` da E2E-030:

```
t_3446bf96… t_70ea0372… t_b7249d26… t_c1a27231… t_emp_dev   → applied=["0401"]
All 6 schema(s) converged
```

Perfil publicado com o primitivo em `alta`, e o `/active` real alimentando `edge_agent_core`:

```
perfil v1 contrato v1.1.0 — 1 primitivo(s)
  Piscar prolongado E2E      faixa=alta  earClose=0.25 browMinFrames=3 janela=2.5s
  (gesto fora do perfil)     faixa=media earClose=0.22
```

Um gesto em `alta` e outro na faixa padrão, no mesmo perfil, sem tocar em código. Persistido:
`Piscar prolongado E2E -> alta`.

### O backfill, provado — porque o dev não o provaria

O `dev` tinha **zero** perfis publicados, então a migration rodou verde sem executar o `UPDATE`.
Verde ali não significa nada. Provado num schema descartável, com as duas formas que os perfis
antigos de fato carregam (`{}` e `{"confidenceThreshold":0.85,"minWindowMs":100}`):

```
antes:  2 perfil(is), 0 com faixas
UPDATE 2
depois: 2 perfil(is), 2 com as tres faixas
        media.earClose = 0.22 | alta.browMinFrames = 3
constraint aceita as linhas backfilladas: sim
```

### Validação recusa perfil incoerente — com o motivo

| Publicado | Resposta |
|---|---|
| `alta.earClose` menor que `baixa` | 400 — *"earClose deveria crescer de baixa para alta (recebido 0.25 / 0.22 / 0.19) — nessa métrica, valor maior detecta mais fácil"* |
| `earOpen < earClose` na `media` | 400 — *"earClose deve ser > 0 e < earOpen (valor recebido: 0.3)"* |
| `sensibilidade: "turbo"` | 400 |
| JSON malformado | 400 — *"Failed to read request"* (genérica, de propósito) |

**Defeito encontrado e corrigido durante essa checagem:** as três primeiras respondiam
`"Failed to read request"`. A validação vive no construtor compacto do record e portanto dispara
dentro do Jackson; o Spring embrulha tudo em `HttpMessageNotReadableException` e a mensagem útil
morria na causa. Eu tinha escrito mensagens de erro cuidadosas que ninguém veria. Handler
dedicado em `GlobalExceptionHandler` expõe **só** a causa `IllegalArgumentException` — texto de
parser não ajuda quem chamou e pode vazar estrutura interna.

### Guardas

`check_edge_agent_drift.py` passou a comparar **quatro** lados, não dois — curar a duplicação em
Python e criar duas cópias novas em Java e SQL teria sido trocar de doença:

```
17 limiares/indices e 3 funcoes alinhados entre a fonte e o artefato congelado;
3 faixas x 9 campos identicas em python/java/sql;
a faixa 'media' reproduz as constantes historicas;
edge-agent-ws.py importa da fonte sem redefinir nada.
```

**Controle negativo — quatro mutações, quatro vermelhos:**

| Mutação | Saída |
|---|---|
| Java `alta.earClose` 0.25 → 0.28 | `alta.earClose: python=0.25 != java=0.28` |
| SQL `media.browMinFrames` 5 → 6 | `media.browMinFrames: python=5 != sql=6.0` |
| Python `media.earClose` 0.22 → 0.23 | `a faixa padrao (0.23) nao reproduz a constante historica (0.22)` |
| SQL: janela em segundos onde é ms | `media.doubleBlinkWindowMs: python=2000 != sql=2.0` |

`test_edge_agent_core.py` — 14 casos, asserts puros (não há pytest no repositório). Cobre o
sentido da sensibilidade nos dois eixos, a conversão ms→s, e cinco formas de perfil quebrado que
precisam **degradar** para a faixa padrão em vez de parar de detectar: o agente roda na casa do
paciente. Controle negativo: `alta.browMinFrames` 3 → 9 reprova em `alta exige menos sustentacao`.

## Fica aberto

- **Sensibilidade por paciente.** `comando.sensibilidade` (PAC) → agente. Exige romper
  `ux_profile_single_active` e resolver `device → paciente`.
- **A ponte recebe o perfil do navegador**, não o busca: o `start_session` aceita `profile`, e o
  `hello` anuncia `acceptsProfile`. É a tela de calibração que já está autenticada no GEST; esta
  ponte de localhost não tem credencial nenhuma (ver a nota PROVISIONAL no topo dela). Falta o
  lado FE mandar — issue de frontend.
- **7 falhas de `integrationTest` no gest-service**, pré-existentes.
- **Três stubs vivos** encontrados no caminho, sinalizados no ES: `findForDevice()` e
  `findByVersion()` devolvem `Optional.empty()` sempre — e é `findForDevice` que o EDGE chama.
