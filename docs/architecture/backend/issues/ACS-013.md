## Contexto

`TenantController` expõe a superfície de provisionamento de tenant (`/api/v1/acs/tenants`).
Requer autoridade `acs.tenant.provisionar`. Produz `201 Created` (ativo) ou `202 Accepted`
(saga pendente). Retry é idempotente.

## Spec de referência

- SPEC-01 §6 (endpoint × status matrix — POST /tenants, GET /tenants/{id}, POST provisioning:retry)
- SPEC-02 (provisioning saga, EARS invariants completos)

## Escopo

- [ ] criar `TenantController` em `api/controller/` com:
      `POST /api/v1/acs/tenants` → `TenantProvisioningService.provision()` → `201` ou `202`
      `GET /api/v1/acs/tenants/{id}` → `TenantJpaAdapter.findById()` → `200` ou `404`
      `POST /api/v1/acs/tenants/{id}/provisioning:retry` → `TenantProvisioningService.retryProvisioning()` → `200` ou `202` ou `409`
- [ ] anotar cada método com `@PreAuthorize("hasAuthority('acs.tenant.provisionar')")`
- [ ] criar `TenantRequest` (nome, tipo) e `TenantResponse` DTOs; validar com Bean Validation (`@NotBlank`, `@Pattern(tipo)`)
- [ ] registrar `GlobalExceptionHandler` mappings: `MigUnavailableException` → `202`, `TenantSuspendedException` → `409`, `TenantNotFoundException` → `404`

## Critérios de aceite

- [ ] POST sem autoridade → `403 insufficient-authority`
- [ ] POST `tipo=desconhecido` → `400 validation`
- [ ] POST MIG OK → `201` com `status=active`
- [ ] POST MIG timeout → `202` com `status=provisioning`
- [ ] GET id desconhecido → `404 tenant-not-found`
