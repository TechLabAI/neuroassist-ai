# E2E-027 — Não existe CI: nenhum gate roda sem alguém digitar o comando

**Módulo:** Infraestrutura
**Fase:** Infraestrutura de Testes
**Prioridade:** P1
**Status:** ⛔ REABERTA — os workflows existem e estão DESATIVADOS (2026-08-25)
**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.4

---

## Contexto

O repositório não tem pipeline de CI. Todo gate — `test`, `architectureCheck`, `integrationTest` —
depende de alguém rodar localmente e reportar. Duas consequências já observadas:

1. **61 dos 62 `application/port/out/*.java` ficaram fora do versionamento** e ninguém percebeu:
   `out/` no `.gitignore`, sem barra inicial, casa em qualquer profundidade. O Gradle compila o
   **diretório de trabalho**, não o índice do git — nenhum gate local podia detectar, e não havia
   CI para compilar o que estava no repositório.
2. `:test` não roda `integrationTest`, então um `*IT` quebrado convive com gate verde.

Sem CI, "os 7 módulos estão verdes" é uma afirmação sobre a última vez que alguém rodou, não sobre
o estado do repositório.

## Escopo

- Workflow que faz **clone limpo** (é o que teria pego o defeito do `.gitignore`) e roda
  `build` + `architectureCheck` nos 7 serviços
- `integrationTest` com Docker disponível no runner
- E2E-013 (suíte automatizada) plugada quando existir
- Gate obrigatório no PR para `dev`

## Checklist

- [x] Workflow de build + `architectureCheck` (clone limpo) — `.github/workflows/ci-backend.yml`
- [x] `integrationTest` com serviço Docker no runner — job `integration-test` (gest-service Testcontainers)
- [x] Cache de dependências Gradle — cache `actions/cache@v4` por hash dos `.gradle.kts`
- [ ] Branch protection em `dev`, `release`, `prod` — **requer permissão administrativa no GitHub** (ver `docs/ci.md` — instruções para o dono do repo)
- [x] Frontend: `nx affected:test` + `affected:lint` — `.github/workflows/ci-frontend.yml`
- [x] Verificação de que arquivo novo em `application/port/out/` chega ao índice do git — job `gitignore-guard` (canary + `git check-ignore`)

## Critério de aceite

Abrir PR com um teste quebrado, ou com um arquivo que existe só no disco, e o PR ficar vermelho.

## ⛔ Regressão — os workflows foram DESATIVADOS em 2026-08-25

Verificado agora:

```
$ gh workflow list --all
CI — Backend     disabled_manually
CI — Frontend    disabled_manually
```

**Decisão do dono do produto**, tomada durante a sessão de 25/08: *"não quero deixar o CI ativo,
podemos desativar e pular por agora"*. Não foi acidente nem falha — está registrado aqui para que a
issue não descreva um estado que deixou de valer.

### O que isso significa na prática

O checklist acima continua verdadeiro: os workflows **existem**, com clone limpo, `integrationTest`
com Docker, cache do Gradle e o `gitignore-guard`. Mas **nada disso executa**. O critério de aceite
— "o PR fica vermelho" — não pode ser satisfeito enquanto estiverem desativados.

Ou seja, o problema que esta issue descreve **está de volta**, inclusive o caso concreto do §Contexto:
os 61 de 62 `application/port/out/*.java` fora do versionamento. O Gradle compila o diretório de
trabalho, não o índice do git — nenhum gate local pode detectar isso, e o gate que podia está
desligado.

### Consequência que se acumulou desde então

- **`GEST-INT-008`** (guarda de drift dos limiares do browser × backend) nasceu já nesta condição:
  o guarda foi escrito, conferido por mutação, e **não roda**. Está anotado na própria issue.
- Todo gate desta sessão — 1.363 unitários do frontend, 192 do edge-service, `architectureCheck`,
  `spotless`, `integrationTest` — passou porque **alguém digitou o comando**. É exatamente a
  afirmação que o §Contexto desta issue diz não valer: "os módulos estão verdes" descreve a última
  vez que alguém rodou, não o estado do repositório.

### Para religar

```bash
gh workflow enable "CI — Backend"
gh workflow enable "CI — Frontend"
```

A pendência administrativa do checklist (branch protection em `dev`/`release`/`prod`) segue de pé e
é independente disto — sem ela, mesmo com os workflows ligados o PR vermelho não bloqueia o merge.

### Por que não fechar a issue como "wontfix"

Porque a decisão foi **"pular por agora"**, não "não faremos". Fechar apagaria o rastro de que o
repositório está sem rede de proteção automática — que é justamente o que esta issue existe para
tornar visível.
