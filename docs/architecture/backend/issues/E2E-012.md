# E2E-012 — Flow-04: LGPD erasure + chain integrity pós-erasure

## Objetivo

Verificar que o crypto-shredding LGPD (AES-256-GCM per-patient key erasure, implementado em HIST P10) funciona corretamente no contexto cross-service: após a remoção de um paciente, os dados PII ficam inacessíveis mas os metadados de auditoria e a cadeia de hash continuam íntegros e verificáveis.

## Contexto

HIST implementa LGPD crypto-shredding: cada paciente tem uma chave AES-256-GCM no banco. Ao apagar a chave, os campos PII tornam-se indecifráveis sem deletar os fatos (chain preservada). PAC é o owner do `Patient` lifecycle — a deleção começa em PAC.

## Fluxo Completo

```
1. [Pré-condição] Paciente com N fatos auditados no HIST
      → EventoCriado, ComandoPublicado, DispositivoPareado, etc.
      
2. DELETE /api/v1/pac/patients/{id}
      → PAC: remove paciente do catálogo
      → PAC → HIST: notifica erasure (ou HIST reage via evento)
      → HIST: apaga chave AES do paciente (crypto-shredding)
      
3. GET /api/v1/hist/history?patientId={id}
      → HIST: fatos existem mas campos PII são [REDACTED] / ilegíveis
      → metadados (factId, occurredAt, factType, correlationId) ainda presentes
      
4. GET /api/v1/hist/history/{id}/verify-chain
      → HIST: hash chain verificada como íntegra (erasure não quebra a cadeia)
      
5. GET /api/v1/pac/patients/{id}
      → PAC: 404 (paciente removido)
```

## Critério de Sucesso (Gate)

- Passo 2: deleção bem-sucedida em PAC
- Passo 3: fatos existem em HIST; campos PII ilegíveis/redactados; `factId`, `occurredAt`, `factType` presentes
- Passo 4: chain integrity verificada — mesmo após erasure
- Passo 5: PAC retorna `404`

## Notas

- O mecanismo exato de disparo do erasure em HIST (chamada PAC → HIST, ou HIST polling, ou event) deve ser verificado na implementação antes de executar este cenário
- Verificar que coordenadores com `hist:read:all` também não veem PII após erasure (erasure é incondicional)
