# E2E-014 — GWY: normalizar rotas de API para `/api/v1/<svc>/**` (RewritePath)

**Módulo:** E2E Cross-Service
**Fase:** F1 — Infra & Discovery (extensão de E2E-001)
**Prioridade:** P1 (bloqueante para o frontend)
**Status:** ✅ DONE (2026-08-21) — RWT-01..09 verdes
**Criado em:** 2026-08-20
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md)

---

## Objetivo

Fazer as rotas de API do GWY **alcançarem os controllers** dos 7 serviços, adotando a
normalização `/api/v1/<svc>/**` como superfície pública única, via `RewritePath`.

Hoje 4 das 7 rotas casam o predicado no gateway e entregam `404` no serviço.

## Contexto — o achado (G8)

O `application-docker.yml` criou rotas de API `/api/v1/<svc>/**` para os 7 serviços,
**sem filtro de rewrite**. O gateway encaminha o path inalterado, então ele precisa
coincidir com o `@RequestMapping` do serviço:

| Serviço | Rota no GWY | `@RequestMapping` real | Alcança |
|---|---|---|---|
| ACS | `/api/v1/acs/**` | `/api/v1/acs/{tenants,caregivers,directory}` | ✅ |
| HIST | `/api/v1/hist/**` | `/api/v1/hist/*` | ✅ |
| EDGE | `/api/v1/edge/**` | `/api/v1/edge/{devices,heartbeat}` | ✅ |
| PAC | `/api/v1/pac/**` | `/api/pac/v1/pacientes` | ❌ 404 |
| EVNT | `/api/v1/evnt/**` | `/api/v1/events`, `/api/v1/reports` | ❌ 404 |
| DASH | `/api/v1/dash/**` | `/panel`, `/internal/notifications` | ❌ 404 |
| GEST | `/api/v1/gest/**` | `/gest-service/*` | ❌ 404 |

Nenhum dos 7 declara `server.servlet.context-path` (verificado), logo não há prefixo
implícito que reconcilie a diferença.

### Por que `INF-02` passou mesmo assim

`E2E-001` validou `INF-02` com `GET /api/v1/<svc>/actuator/health` → `200` nos 7. Essas são
as rotas de **health**, que têm `StripPrefix=3`: `/api/v1/pac/actuator/health` vira
`/actuator/health` e responde. O check prova que o GWY resolve o serviço no Eureka — **não**
que as rotas de API alcançam os controllers. São predicados diferentes.

Isso não invalida `E2E-001` (que está corretamente DONE); apenas delimita o escopo dele.
Este issue cobre o que ficou de fora.

## Decisão: (a) Normalizar

> Registrada como **[ADR-008 — Superfície pública normalizada em `/api/v1/<svc>/**` no GWY]
> (../adr/ADR-008-public-api-surface-normalization.md)**. Este issue é a implementação e a
> verificação dessa decisão.

Avaliadas duas saídas:

- **(a) Normalizar** — o GWY reescreve `/api/v1/<svc>/**` para o path real do controller.
  O FE passa a chamar `/api/v1/<svc>/...` em tudo.
- **(b) Espelhar** — o GWY ganha rotas com os paths reais (`/api/pac/v1/**`, `/panel/**`,
  `/gest-service/**`, …) e o FE não muda nada.

**Decisão: (a).** Justificativa:

1. **É a intenção já expressa.** O `application-docker.yml` escreveu `/api/v1/<svc>/**` para
   os 7 e health com `StripPrefix=3`. Falta apenas o rewrite. (b) desfaria essa direção.

2. **(b) exporia superfície interna.** O projeto tem convenção consistente de nomes:

   | Convenção | Uso | Exemplos |
   |---|---|---|
   | `/api/...` | público | `/api/v1/acs/tenants`, `/api/v1/hist/history` |
   | `/<svc>-service/...`, `/internal/...` | serviço-a-serviço | `/edge-service/profile-pointer`, `/evnt-service/notification-orchestration`, `/internal/notifications` |

   Publicar `/gest-service/**` no gateway exporia `detection-contract`, `detection-profile`
   e `tipo-gesto` junto com `eligibility`. Publicar `/panel/**` é seguro, mas deixa
   `/internal/notifications` a um descuido de distância. Em (a) o `RewritePath` age como
   allow-list: `/api/v1/dash/**` → `/panel/**` torna `/internal/**` inalcançável de fora.

3. **Acoplamento.** Em (b) o path do controller **é** o contrato público: refatorar um
   controller quebra o browser. Em (a) o gateway absorve a mudança.

4. **Custo real é baixo dos dois lados.** (b) economiza ~6 constantes no FE; (a) custa ~8
   linhas de YAML a mais que (b) no gateway. (b) não é "de graça".

5. **Proxy do frontend.** Em (a) o `proxy.conf.json` precisa de 2 prefixos (`/api/v1/**`,
   `/oauth2/**`); em (b), de 9.

**Não muda em nenhuma das duas:** os `@RequestMapping` dos serviços ficam intocados, então a
comunicação serviço-a-serviço (Feign via `lb://` no Eureka, que não passa pelo gateway) não é
afetada. A decisão é exclusivamente sobre a borda pública.

## Regras de rewrite

```yaml
# PAC — /api/v1/pac/pacientes → /api/pac/v1/pacientes
- id: pac-service-route
  uri: lb://pac-service
  predicates:
    - Path=/api/v1/pac/**
  filters:
    - RewritePath=/api/v1/pac/(?<segment>.*), /api/pac/v1/${segment}

# EVNT — /api/v1/evnt/events → /api/v1/events ; /api/v1/evnt/reports → /api/v1/reports
- id: evnt-service-route
  uri: lb://evnt-service
  predicates:
    - Path=/api/v1/evnt/**
  filters:
    - RewritePath=/api/v1/evnt/(?<segment>.*), /api/v1/${segment}

# DASH — /api/v1/dash/summary → /panel/summary
#        (/internal/** permanece inalcançável de fora, por construção)
- id: dash-service-route
  uri: lb://dash-service
  predicates:
    - Path=/api/v1/dash/**
  filters:
    - RewritePath=/api/v1/dash/(?<segment>.*), /panel/${segment}
```

### GEST — allow-list por endpoint, **não** wildcard

O `gest-service` não tem superfície pública: os 4 mappings são `/gest-service/{eligibility,
tipo-gesto,detection-profile,detection-contract}`, todos na convenção interna.

O frontend consome dele exatamente **dois** endpoints:

| Endpoint | Consumidor no FE |
|---|---|
| `/gest-service/eligibility` | `libs/gest/.../eligibility-http.adapter.ts` |
| `/gest-service/tipo-gesto` | `libs/pac/.../tipos-gesto-read-http.adapter.ts` |

`detection-profile` é consumido pelo EDGE (profile pointer por heartbeat) e
`detection-contract` é interno — **nenhum dos dois deve ser publicado**.

Um `RewritePath=/api/v1/gest/(?<s>.*), /gest-service/${s}` genérico publicaria os quatro.
Usar predicados por endpoint:

```yaml
- id: gest-eligibility-route
  uri: lb://gest-service
  predicates:
    - Path=/api/v1/gest/eligibility/**
  filters:
    - RewritePath=/api/v1/gest/(?<segment>.*), /gest-service/${segment}

- id: gest-tipo-gesto-route
  uri: lb://gest-service
  predicates:
    - Path=/api/v1/gest/tipo-gesto/**
  filters:
    - RewritePath=/api/v1/gest/(?<segment>.*), /gest-service/${segment}
```

> Esta é a diferença entre (a) bem feita e (a) descuidada: a normalização só entrega o
> benefício de allow-list se o predicado for específico onde a superfície interna é ampla.

## Bugs colaterais descobertos (corrigir junto)

1. **`/api/gest/v1/tipos-gesto` não corresponde a nada.** O adapter
   `libs/pac/src/lib/api/tipos-gesto-read-http.adapter.ts` usa esse path; o `gest-service`
   serve `/gest-service/tipo-gesto` (singular, prefixo diferente). Está quebrado hoje,
   independentemente desta decisão. Passa a `/api/v1/gest/tipo-gesto` — escopo do FE
   (`FE-E2E-004`), registrado aqui para rastreio.

2. **Mocks do `pac-e2e` desalinhados.** Interceptam `**/api/v1/pacientes**` enquanto o adapter
   chama `/api/pac/v1/pacientes` — não casam. Como o app roda em `adapter: 'mock'`, nenhuma
   requisição é emitida e os `page.route` nunca disparam; os 12 testes passam com os dados em
   memória. É código morto que parece cobertura. Escopo do FE (`FE-E2E-007`/`FE-E2E-001`).

## Cenários de Validação

O critério é responder **≠ `404`** (`200`, `401` ou `403` são todos aceitáveis — provam que a
request chegou ao controller). `/actuator/health` **não conta**: usa outro predicado.

```bash
GWY=http://localhost:${GWY_PORT:-18080}
curl -si $GWY/api/v1/acs/tenants/x        # ACS   — já OK
curl -si $GWY/api/v1/hist/history         # HIST  — já OK
curl -si $GWY/api/v1/edge/devices         # EDGE  — já OK
curl -si $GWY/api/v1/pac/pacientes        # PAC   — hoje 404
curl -si $GWY/api/v1/evnt/events          # EVNT  — hoje 404
curl -si $GWY/api/v1/dash/summary         # DASH  — hoje 404
curl -si $GWY/api/v1/gest/eligibility     # GEST  — hoje 404
curl -si $GWY/api/v1/gest/tipo-gesto      # GEST  — hoje 404
```

| ID | Cenário | Critério |
|---|---|---|
| RWT-01 | PAC alcança o controller via GWY | `/api/v1/pac/pacientes` ≠ `404` |
| RWT-02 | EVNT alcança events e reports | `/api/v1/evnt/{events,reports}` ≠ `404` |
| RWT-03 | DASH alcança o painel | `/api/v1/dash/summary` ≠ `404` |
| RWT-04 | GEST alcança eligibility e tipo-gesto | ambos ≠ `404` |
| RWT-05 | ACS/HIST/EDGE não regridem | os 3 continuam ≠ `404` |
| RWT-06 | Health continua verde nos 7 | `/api/v1/<svc>/actuator/health` → `200` |
| RWT-07 | **`/internal/**` inalcançável pelo GWY** | `/api/v1/dash/internal/notifications` → não atinge `/internal/notifications` |
| RWT-08 | **Superfície interna do GEST não exposta** | `/api/v1/gest/detection-contract` e `/api/v1/gest/detection-profile` → `404` no gateway |
| RWT-09 | S2S não afetado | Feign PAC→GEST, EDGE→GEST, EVNT→ACS, *→HIST seguem OK |

## Verificação executada (2026-08-21)

Stack docker no ar, token de coordenador.

**RWT-01..05 — alcançabilidade (critério: ≠ 404)**

```
/api/v1/pac/pacientes        -> 200      /api/v1/acs/directory/tenants/{id} -> 200
/api/v1/evnt/events/active   -> 500      /api/v1/hist/history               -> 200
/api/v1/evnt/reports         -> 405      /api/v1/edge/devices               -> 200
/api/v1/dash/summary         -> 503
/api/v1/gest/tipo-gesto      -> 200
```

Os três não-2xx **alcançam o controller** e falham por razão interna, não de roteamento:
EVNT 500 é o modo PoC (tenant hardcoded `"poc"`, C-17); EVNT `reports` 405 é POST-only;
DASH 503 é a dependência do EVNT. Nenhum é 404 — o critério do RWT.

**RWT-06 — health nos 7:** todos `200`.

**RWT-07/08 — superfície interna não exposta (critério: 404)**

```
/api/v1/dash/internal/notifications  -> 404
/api/v1/gest/detection-contract      -> 404
/api/v1/gest/detection-profile       -> 404
/api/v1/gest/detection-profile/active-> 404
```

O `RewritePath` do DASH mapeia para `/panel/**`, então `/internal/**` é inalcançável **por
construção**. O GEST tem rota só para os dois endpoints públicos, então `detection-profile`
(consumido pelo EDGE) e `detection-contract` (interno) não têm rota no gateway.

**RWT-09 — S2S sem regressão:** Flow-01 **15/15**, exercitando PAC→GEST (eligibility e
lookup de primitiva), PAC→HIST (audit facts com identidade de serviço) e HIST→ACS
(patient-scope).

## Notas de Implementação

### Divergência entre `application.yml` e `application-docker.yml`

O `application.yml` base declara **apenas** `edge-service-route`; as 7 rotas + health estão
só no perfil `docker`. Consequência: o GWY iniciado fora do compose roteia diferente do GWY
dentro do compose. Vale consolidar — o mesmo problema já existe com o `issuer-uri`, cujo
default aponta para um Keycloak inexistente e só é corrigido pelo env do compose.

### Higiene relacionada (não bloqueante)

`KEYCLOAK_ISSUER_URI` → `ACS_ISSUER_URI`, com default apontando para o ACS. O nome atual
sugere um Keycloak que não existe neste stack.
