## Contexto

Score atual após P1-P6: 72/100 (Consistente). Esta issue cobre os três gaps restantes para atingir ≥ 95/100 (Maduro):

1. **Signing key transiente** — `JwtEncoderConfig` gera RSA-2048 em memória a cada boot. A tabela `neuroassist_global.signing_key` existe mas nunca é usada para persistir/recuperar a chave ativa. Cada restart invalida todos os tokens emitidos anteriormente.
2. **Refresh token stub** — `AutenticacaoService.refresh()` emite novo token sem validar o JWT de refresh recebido (assinatura, expiração, tipo).
3. **Soft completeness** — RULE-07 ausente em `TenantService`, observação distribuída (Micrometer Observation) faltando em 2 services, docs/spec do serviço possivelmente desatualizados.

## Escopo

### Item 1 — Persistência e rotação da signing key

- [ ] Criar `SigningKeyService.java` em `application/service/` com:
  - `getOrCreateActiveKey()`: busca chave ACTIVE via `SigningKeyRepositoryPort.findActiveKey()`; se ausente, gera RSA-2048, persiste criptografada (`privateKeyEnc` via AES-256 com segredo de `${acs.signing-key.encryption-secret}`), retorna par
  - `rotateIfExpired()`: verifica `notBefore` > 7 dias → gera nova chave ACTIVE, marca anterior como RETIRED
  - `getPublicKeys()`: delega para `SigningKeyRepositoryPort.findPublicKeys()`
- [ ] Adaptar `JwtEncoderConfig` (ou criar `SigningKeyInitializer implements ApplicationRunner`): ao subir, chamar `SigningKeyService.getOrCreateActiveKey()` e usar o par RSA retornado para construir `JwtEncoder` e `JwtDecoder` beans
- [ ] Adicionar propriedade `acs.signing-key.encryption-secret` em `application.yml` (referência a variável `${ACS_SIGNING_KEY_SECRET}`)
- [ ] Atualizar `SigningKeyPortAdapter` para usar a chave persistida em vez de par gerado em memória
- [ ] Criar teste unitário `SigningKeyServiceTest`

### Item 2 — Refresh token real

- [ ] Validar JWT do refresh token em `AutenticacaoService.refresh()`:
  - Verificar assinatura com `JwtDecoder`
  - Verificar claim `token_type == "refresh"`
  - Verificar que não está expirado
- [ ] Implementar sliding window sem armazenamento de estado: ao validar, emitir novo access token (TTL 900s) + novo refresh token (TTL 7 dias) com `jti` único
- [ ] Adicionar claim `token_type` na emissão em `TokenIssuer` (`token_type: "access"` para access, `token_type: "refresh"` para refresh com TTL mais longo)
- [ ] Atualizar `AutenticacaoResponse` se necessário
- [ ] Criar / atualizar `AutenticacaoServiceTest` para cobrir cenários de refresh válido, expirado e tipo errado
