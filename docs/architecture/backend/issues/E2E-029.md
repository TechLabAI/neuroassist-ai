# E2E-029 — Um tenant novo nasce vazio e ninguém consegue entrar nele (C-48)

**Módulo:** E2E Cross-Service (ACS)
**Fase:** F9 — Flow-01 (onboarding)
**Prioridade:** P1
**Status:** ✅ DONE (2026-08-23) — Flow-01 fecha ponta a ponta numa empresa nova
**Criado em:** 2026-08-23 — descoberto ao validar E2E-016 contra o stack real
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2

---

## Contexto

Com E2E-016 no ar, `POST /api/v1/acs/tenants` cria o schema de verdade e devolve o tenant
`ACTIVE`. O passo seguinte não existe: **não há como criar o primeiro cuidador desse tenant.**

```
POST /api/v1/acs/caregivers?tenantId=<tenant-novo>
  → 403 acs.tenant.mismatch
    "Caregiver does not belong to the requested tenant"
    actualTenantId: <tenant de quem chamou>   requestedTenantId: <tenant novo>
```

O 403 está **correto**: um coordenador da clínica A não pode criar pessoas na clínica B, e esse
isolamento é o que impede vazamento entre empresas. O problema é que ele fecha o único caminho
existente, e não há nenhum outro:

- todo token é emitido para um cuidador, e todo cuidador pertence a um tenant;
- o tenant recém-criado não tem cuidador nenhum;
- logo, nenhum token pode agir dentro dele.

O tenant fica com schema perfeito, 30 tabelas migradas, e inalcançável. O seed
(`V0102__acs_dev_seed.sql`) resolve isso para `t_emp_dev` inserindo linhas direto no banco — que
é exatamente por que as seis sessões de E2E nunca esbarraram nisto.

## O que falta decidir

| Opção | Consequência |
|---|---|
| Ator de plataforma (papel acima do tenant) com autoridade para semear o primeiro cuidador | Cria um papel que atravessa empresas — precisa de trilha de auditoria à altura |
| `POST /tenants` aceita o primeiro coordenador no mesmo payload, criado atomicamente | Onboarding vira uma operação só; o tenant nunca existe sem ninguém dentro |
| Endpoint de bootstrap de uso único por tenant, com token de convite | Mais partes móveis; o convite vira credencial a proteger |

A segunda é a mais simples de defender: um tenant sem nenhum cuidador não é um estado
que o negócio queira, então não deveria ser representável.

## Implementado em 2026-08-23

**Decisão (do usuário): o primeiro coordenador entra no payload de `POST /tenants`, criado
atomicamente.** Das três opções, é a única que não cria autoridade capaz de atravessar empresas:
não há papel novo enxergando todas as clínicas, nem convite a proteger. E torna "empresa sem
ninguém dentro" um estado **não representável** — que é a forma mais barata de nunca mais ter
este defeito.

**Decisão (do usuário): corrigir junto o `acs.tenant.*` no papel de clínica.**

| Peça | Onde |
|---|---|
| Primeiro coordenador no payload | `TenantRequest.PrimeiroCoordenador` |
| Semeadura | `CaregiverUseCase.seedFirstCoordinator` + `CaregiverService` |
| Invariante de uso único | `TenantAlreadySeededException` |
| Onboarding atômico | `TenantService.createTenant` |
| Cliente de plataforma | `acs.service-clients.platform-ops`, `tenantless: true` |
| Token sem tenant por HTTP | `ServiceClientProperties.tenantless` + `ServiceTokenService` |
| Papel de clínica sem `acs.tenant.*` | `RoleAuthorityPolicy` |

### Por que o bootstrap não relaxa a checagem de tenant

`CaregiverService.create` compara o tenant do request com o do JWT e rejeita divergência — é isso
que impede a clínica A de criar gente na clínica B. Uma empresa recém-criada não tem ninguém para
ser esse chamador, então a checagem é **insatisfazível**, não incômoda.

Relaxá-la abriria criação cross-tenant em **toda** chamada, para resolver um caso que acontece uma
vez por empresa. O que a substitui é uma invariante mais estreita: `seedFirstCoordinator` recusa se
o tenant já tiver qualquer cuidador. Roda uma vez por empresa e nunca mais.

### O token sem tenant é exceção declarada por cliente

`ServiceTokenRequest.tenantId` era obrigatório por um bom motivo — os serviços roteiam o
`search_path` pelo claim de tenant, e um token sem tenant chegaria ao schema errado. Criar uma
empresa acontece **antes** dessa empresa existir, então não há tenant a que escopar.

A exceção é `tenantless: true` **por cliente**, não uma flexibilização global: todo cliente cujas
chamadas roteiam por schema continua obrigado a informar o tenant, e um cliente tenant-less que
peça token escopado é recusado — configuração errada não vira privilégio silencioso.

### `acs.tenant.*` saiu do COORDENADOR_CLINICA

O coordenador da clínica A podia criar e reprocessar a clínica B. Não era o modelo pretendido; era
o único caminho existente, e foi só por isso que a validação de E2E-016 conseguiu criar tenants.
As três autoridades vivem agora em `platform-ops`.

Consequência: `findById` e `retryProvisioning` deixaram de chamar `TenantContextHolder.require()`.
A tabela `tenant` é o registro **global**, não dado de empresa — nenhum `search_path` se aplica a
ela, e exigir contexto ali só seria satisfazível por um cuidador de alguma empresa não relacionada,
que é exatamente o poder que esta issue removeu. É a mesma exceção documentada que `createTenant`
já usava.

### Validação no stack real

| Passo | Resultado |
|---|---|
| Coordenador de clínica tenta criar empresa | **403** — a autoridade saiu do papel |
| `POST /oauth2/token/service` do `platform-ops` sem tenant | token com `tenant_id: null` e as três `acs.tenant.*` |
| `POST /tenants` com primeiro coordenador | **201 ACTIVE**, schema real |
| Login da coordenadora semeada | **200**, `tenant_id` = empresa nova, papel `COORDENADOR_CLINICA` |
| `POST /pacientes` com o token dela | **201** |
| Propagação do vínculo (E2E-015) na empresa nova | `directory_outbox` → `sent`; directory do ACS devolve a cuidadora |

**Flow-01 fecha ponta a ponta numa empresa criada do zero, sem inserir uma linha no banco à mão.**
