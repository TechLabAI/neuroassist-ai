## Contexto

O mesmo valor viaja com três nomes no token e dois no header:

| Camada | Nomes em uso | Canônico |
|---|---|---|
| Claim JWT | `tenant_id`, `tenant`, `empresaId` | `tenant_id` |
| Header HTTP | `X-Empresa-Id` (PAC, rejeita 400 sem ele), `X-Tenant-Id` (demais) | `X-Tenant-Id` |

Os aliases foram um shim de compatibilidade durante a integração. Cada um é um lugar a mais onde
um serviço novo pode ler o nome errado e resolver o tenant como nulo — e resolver tenant errado,
neste sistema, é vazar dado clínico entre empresas.

Relacionado: o gateway não injeta header de tenant nenhum (`grep -i "tenant|empresa"` no `src/main`
do api-gateway retorna zero), então cada serviço extrai do JWT por conta própria.

## Escopo

1. Todos os resource servers passam a ler `tenant_id` (mantendo a leitura dos aliases)
2. `TokenIssuer` para de emitir `tenant`/`empresaId`
3. PAC aceita `X-Tenant-Id`, mantendo `X-Empresa-Id` por uma versão
4. Remoção dos aliases dos dois lados

Ordem importa: emitir só o canônico antes de todos lerem o canônico quebra tudo de uma vez.

## Checklist

- [x] Passo 1 (leitura canônica em todos) verde no E2E
- [x] Passo 2 (emissão só do canônico)
- [x] Passo 3 (header canônico no PAC)
- [x] Passo 4 (remoção dos aliases) + teste negativo: token só com alias antigo é rejeitado
- [x] Decidir se o gateway passa a injetar o header (hoje não injeta)

## Inventário (2026-08-24) — o que a auditoria encontrou

A issue dizia "3 claims e 2 headers". O que estava em jogo era maior: **quatro serviços liam
apenas um alias**, e nenhum lia o canônico.

| Serviço | Claim que lia | Header |
|---|---|---|
| acs, edge, hist*, dash* | `tenant_id` ✓ | `X-Tenant-Id` ✓ |
| evnt | união dos três | — |
| **gest** | **`tenant`** (só o alias) | `X-Tenant-Id` |
| **pac** | **`empresaId`** (só o alias) | **`X-Empresa-Id`** (só) |
| **hist** — 4 controllers | **`tenant`** (fora do filtro) | — |
| **dash** — 2 proxies | **`details.get("tenant")`** | — |

\* o filtro lia o canônico; os controllers, não.

Ou seja: o passo 2 do plano original desta issue — "TokenIssuer para de emitir `tenant`/`empresaId`"
— teria quebrado **gest e pac inteiros** e as consultas de auditoria do hist. O próprio comentário
no `TokenIssuer` já dizia: *"gest-service and the hist-service controllers read 'tenant',
pac-service reads 'empresaId'"*.

## O achado que reenquadra a issue: os 7 filtros falhavam ABERTO

Todos os sete tinham a mesma forma:

```java
if (tenantId != null) {  ...liga o tenant...  }
// e se for null? segue em frente. Sem 400, sem 403, sem tenant ligado.
```

**Verifiquei até onde isso vai, e não é vazamento.** O `TenantIdentifierResolver` de todos os seis
serviços com Hibernate cai em `neuroassist_global`, e esse schema **não tem** as tabelas de negócio
(`comando`, `paciente` — confirmado no banco: zero). A requisição morre com `relation ... does not
exist`, ou seja, um 500.

Isso é melhor do que eu supus ao começar, e vale dizer com precisão: **não há vazamento entre
empresas.** Mas há três problemas reais:

1. A segurança depende de uma **coincidência** — que o schema de fallback não contenha tabela de
   negócio. Uma migration que colocasse uma lá transformaria isto em leitura cross-tenant
   silenciosa.
2. O chamador recebe 500 em vez de saber o que faltava.
3. **É o que tornava perigoso remover os aliases.** Sem fechar isto, parar de emitir `empresaId`
   faria o PAC processar toda requisição sem tenant — e falhar do jeito mais confuso possível.

Por isso o fail-closed vem **antes** da remoção, e não depois.

### A exceção que quase quebrou tudo

Existe token de serviço **legitimamente sem tenant** (`ServiceTokenService`: o cliente que cria
empresas não tem empresa a que se escopar — E2E-029, e o ACS só concede a clientes marcados como
tenant-less). Um "fail closed" cego teria quebrado a criação de empresa inteira. A regra
implementada é:

- sem JWT → passa (quem decide é o `SecurityConfig`);
- `token_type=service` sem tenant → passa sem tenant ligado (capacidade concedida, não descuido);
- qualquer outro token autenticado sem `tenant_id` → **403 `tenant_claim_missing`**.

## Decisão sobre o gateway

**Não injetar header de tenant.** Confirmado que hoje não injeta (`grep -i "tenant|empresa"` no
`src/main` do api-gateway: zero resultados), e deve continuar assim.

O JWT é assinado e já carrega o tenant. Um header injetado pelo gateway seria uma **segunda fonte
de verdade** que os serviços teriam de decidir se confiam — e a única razão de hoje ser seguro é
que nenhum deles confia: os sete usam o header apenas como **conferência**, e respondem 403 se
divergir do claim. Introduzir uma fonte que dispensasse essa conferência trocaria uma verificação
por uma suposição, exatamente onde o custo do erro é dado clínico da empresa errada.

## Dois stubs vivos encontrados no caminho

- **`dash-service`** — `extractTenantId` nos dois proxies lia `auth.getDetails()` como um `Map`.
  `JwtAuthenticationToken.getDetails()` é um `WebAuthenticationDetails`, nunca um `Map`: o método
  devolvia **string vazia, sempre**. O comentário admitia — *"Por ora, retorna vazio; substituir
  quando SecurityConfig estiver completo"*. Corrigido aqui.
- **`hist-service`** — `AuditRecordQueryController.extractTenantId` ainda caía no literal
  `"stub-tenant"`. Os outros três controllers já haviam sido corrigidos (C-35) e este ficou para
  trás; um resultado vazio sob um tenant inexistente é indistinguível de "esta empresa não tem
  fatos". Corrigido aqui.

## Fica aberto

- **`X-Empresa-Id` no PAC** — aceito por esta versão, com log de depreciação a cada uso. Remover

- **Janela de tokens em voo.** Um token emitido antes deste deploy carrega os aliases mas também o

  vez de morrer com 500 adiante, que é a melhora pretendida.

## Por que a exceção do token sem tenant existe — e por que não é uma brecha

Um fail-closed cego teria quebrado dois fluxos, e os dois têm a mesma forma.

**1. Enroll de dispositivo.** Em `POST /oauth2/token/device` o aparelho apresenta só
`clientId`/`clientSecret`. Para emitir o token dele, o ACS precisa perguntar ao EDGE de que empresa
o aparelho é — **o tenant é exatamente o que a chamada está tentando descobrir.** O
`EdgeInternalTokenProvider` registra as três opções consideradas: pegar o tenant do corpo (recusado
— quem chama ainda está não autenticado, logo o valor é controlado por quem ataca), cair num tenant
padrão (recusado — default silencioso é como começa bug cross-tenant), ou emitir sem tenant
(escolhido).

**2. Criação de empresa** (E2E-029). A empresa não existe ainda; não há tenant a que escopar.

O que torna as duas seguras é **para onde a chamada vai**: `verify-credential` resolve o tenant
pelo índice global `device_directory`, e a criação de empresa escreve em
`neuroassist_global.tenant`. Nenhuma das duas toca schema de empresa — não haveria `search_path` a
rotear mesmo que houvesse tenant.

Daí o princípio: **token sem tenant vale exatamente quando a operação acontece fora de qualquer
empresa e lê só do catálogo global.** E não é dispensa geral — é `tenantless: true` declarado por
cliente, e o ACS recusa nos dois sentidos (cliente não marcado não recebe token sem tenant; cliente
marcado não recebe token com tenant).

## Fixtures que representavam tokens inexistentes

Duas suítes quebraram com o fail-closed, e em ambas o teste é que estava errado:

- **PAC** — `TestJwtHelper` e `SecurityConfigTest` forjavam o claim `empresaId`. Como o ACS deixou
  de emiti-lo, a suíte passou a testar um token que o sistema não produz.
- **EDGE** — `SecurityConfigTest` usava `jwt()` puro, **sem claim nenhum**. O caso do
  `verify-credential` era o mais enganoso: ele espelha a chamada real do ACS, que carrega
  `token_type=service`; a fixture não carregava, então testava um token que nunca existiu.

Nos dois casos a correção foi tornar a fixture fiel, não afrouxar o filtro — afrouxar seria deixar
o teste mandar na produção.
