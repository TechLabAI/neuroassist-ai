# E2E-017 — EVNT perde fato de auditoria: `AuditTrailFeignAdapter` é fail-open sem outbox

**Módulo:** E2E Cross-Service (EVNT → HIST)
**Fase:** F4 — Audit Trail
**Prioridade:** P1
**Status:** OPEN
**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2

---

## Contexto

`AuditTrailFeignAdapter` (evnt-service, linha 55) loga exatamente o que faz:

```
Audit fact {} ({}) was NOT recorded and is lost — evnt-service has no outbox
```

Fail-open é a decisão correta (AUD-10: criar o alarme não pode depender do HIST), mas **sem
durabilidade**. Um `evento.criado` ou `evento.confirmado` produzido durante uma indisponibilidade
do hist-service está perdido para sempre — e são justamente os fatos de um alarme, o registro que
mais importa numa auditoria clínica.

O PAC resolveu o mesmo problema com `hist_outbox` + `factId` cunhado uma vez (C-5) e dreno
agendado (C-44). O padrão a copiar existe inteiro, incluindo o `TenantCatalogPort` e a armadilha
de vincular tenant fora da transação.

## Escopo

Espelhar o PAC no EVNT: tabela `hist_outbox` na faixa V0500-V0599, escrita na mesma transação do
evento, dreno agendado por tenant com identidade de serviço (`hist:write`, já concedida ao
`evnt-service` em `acs.service-clients`).

## Checklist

- [ ] Migration `hist_outbox` no schema do tenant (faixa V0500-V0599) — `status` como varchar + CHECK, nunca ENUM (C-12)
- [ ] `HistOutboxPort` + entity/repository/adapter
- [ ] `AuditTrailFeignAdapter` grava no outbox quando a entrega direta falha
- [ ] `factId` cunhado **uma vez** e reenviado idêntico (dedupe do HIST — HIST ADR-005)
- [ ] Dreno agendado + estado terminal `failed` após `max-retries`
- [ ] Teste: hist-service fora → fato pendente → hist-service volta → fato entregue no tick seguinte

## Critério de aceite

Derrubar o hist-service, criar e confirmar um evento, subir o hist-service: os dois fatos
aparecem na timeline sem intervenção, com `sequenceNo` contíguo.
