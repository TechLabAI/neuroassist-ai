# E2E-017 — EVNT perde fato de auditoria: `AuditTrailFeignAdapter` é fail-open sem outbox

**Módulo:** E2E Cross-Service (EVNT → HIST)
**Fase:** F4 — Audit Trail
**Prioridade:** P1
**Status:** ✅ DONE (2026-08-23) — fato sobrevive a indisponibilidade do HIST, validado no stack
**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2

---

## Contexto

`AuditTrailFeignAdapter` (evnt-service, linha 55) loga exatamente o que faz:

```
Audit fact {} ({}) was NOT recorded and is lost — evnt-service has no outbox
```

Fail-open é a decisão correta (AUD-10: criar o alarme não pode depender do HIST), mas **sem
durabilidade**. Um `evento.criado` ou `evento.confirmado` produzido durante uma indisponibilidade
do hist-service está perdido para sempre — e são justamente os fatos de um alarme, o registro que
mais importa numa auditoria clínica.

O PAC resolveu o mesmo problema com `hist_outbox` + `factId` cunhado uma vez (C-5) e dreno
agendado (C-44). O padrão a copiar existe inteiro, incluindo o `TenantCatalogPort` e a armadilha
de vincular tenant fora da transação.

## Escopo

Espelhar o PAC no EVNT: tabela `hist_outbox` na faixa V0500-V0599, escrita na mesma transação do
evento, dreno agendado por tenant com identidade de serviço (`hist:write`, já concedida ao
`evnt-service` em `acs.service-clients`).

## Checklist

- [x] Migration `hist_outbox` no schema do tenant (faixa V0500-V0599) — `status` como varchar + CHECK, nunca ENUM (C-12)
- [x] `HistOutboxPort` + entity/repository/adapter
- [x] `AuditTrailFeignAdapter` grava no outbox quando a entrega direta falha
- [x] `factId` cunhado **uma vez** e reenviado idêntico (dedupe do HIST — HIST ADR-005)
- [x] Dreno agendado + estado terminal `failed` após `max-retries`
- [x] Teste: hist-service fora → fato pendente → hist-service volta → fato entregue no tick seguinte

## Critério de aceite

Derrubar o hist-service, criar e confirmar um evento, subir o hist-service: os dois fatos
aparecem na timeline sem intervenção, com `sequenceNo` contíguo.

### A tabela NÃO pôde se chamar `hist_outbox`

O PAC já tem uma `hist_outbox` **no mesmo schema de tenant** (V0205), com outra forma — sem
`fact_id`, sem `last_error`. A convenção de faixas de V separa os **números** por módulo; os
serviços compartilham o schema, então o espaço de **nomes** é único.

Escrita primeiro como `CREATE TABLE IF NOT EXISTS hist_outbox`, a migration teria feito
silenciosamente nada e o evnt-service passaria a mapear a tabela do PAC. Daí o nome
`evnt_hist_outbox` e o `CREATE TABLE` **sem** `IF NOT EXISTS`: uma colisão futura tem de falhar
alto, não se acomodar na tabela alheia.

**A suíte não pegou isso** — e o motivo é [E2E-022](E2E-022.md) acontecendo ao vivo. O
`HistOutboxIT` roda contra PostgreSQL real, mas com `ddl-auto=create-drop`: quem desenha o schema
nos testes é o Hibernate, a partir da entity. A tabela do PAC não existe lá, então não havia
colisão a detectar. Só a aplicação do Flyway contra o banco de dev revelou.

### Também encontrado: o `ObjectMapper` cru perdia o fato

Um `new ObjectMapper()` sem `JavaTimeModule` falha ao serializar o `Instant` de `occurredAt`. A
exceção é capturada em `enqueueForRetry` e o fato se perde — com um log diferente do antigo, mas
igualmente perdido. Em produção o mapper é o do Spring, que registra o módulo; o teste passou a
usar um equivalente, para não exercitar um caminho que produção não percorre.

### Validação no stack real

| Passo | Resultado |
|---|---|
| `docker stop hist-service`, confirmar um evento | **200** — a operação de negócio não falhou (AUD-10) |
| Estado do evento | `feedback=REAL`, `confirmado_at` preenchido |
| `evnt_hist_outbox` | 1 linha `pending`, `last_error = hist-service unavailable` |
| `docker start hist-service` | fato entregue no tick seguinte → `sent` |
| Ledger do HIST | `evento.confirmado` gravado com `sequence_no` e `record_hash` |

Antes desta issue, esse mesmo fato teria produzido apenas
`"was NOT recorded and is lost — evnt-service has no outbox"`.

Gates: EVNT 81 testes (unitários + IT com Testcontainers), `architectureCheck` verde.

### O que a validação revelou e esta issue não resolve

**[E2E-030](E2E-030.md) (C-50) — tenant provisionado pela API congela na versão do template.** Os
4 tenants criados durante as validações de E2E-016/E2E-029 não receberam a V0501: o contêiner
`migrations-empresa` migra um schema fixo (`FLYWAY_SCHEMAS: t_emp_dev`). O sweeper agora reclama
uma vez por tick por tenant — `relation "evnt_hist_outbox" does not exist`. É o modo `migrate-all`
do `plan-MIG` P2, que nunca foi implementado, e que só passou a ser necessário quando criar
empresas deixou de ser um stub.
