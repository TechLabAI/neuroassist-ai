## Objetivo

Criar uma suíte de testes E2E automatizada que execute os fluxos dos issues E2E-001 a E2E-012 de forma repetível em CI, sem intervenção manual. A suíte deve poder rodar contra o stack local (docker-compose) e futuramente contra um ambiente de staging.

## Opções de Implementação

### Opção A — REST Assured (Java, integrado ao Gradle)

- Módulo Gradle: `backend/services/e2e-tests/` (novo módulo, não um microserviço)
- Depende de todos os serviços rodando (via docker-compose ou Testcontainers)
- Usa Spring Boot Test + RestAssured para chamadas REST
- Execução: `./gradlew :services:e2e-tests:test`

### Opção B — Newman / Postman Collection

- Arquivo: `docs/e2e/neuroassist-e2e.postman_collection.json`
- Environments: `local.postman_environment.json`, `staging.postman_environment.json`
- Execução: `newman run neuroassist-e2e.postman_collection.json -e local.postman_environment.json`
- Mais fácil de criar manualmente; menos integrado ao Gradle

### Recomendação

**Opção A** para integração com CI/CD Gradle existente. **Opção B** para prototipagem rápida e validação manual durante o desenvolvimento.

## Decisões de design

| Decisão | Porquê |
|---|---|
| Não é microserviço: sem `src/main`, sem plugin do Spring Boot | A suíte é um cliente HTTP externo. Subir contexto Spring reintroduziria a possibilidade de testar contra beans em processo — exatamente o que o gate de módulo já faz e que falhou em detectar 16 defeitos |
| Segregação por tag JUnit `e2e` (`test` exclui, `e2eTest` inclui) | `./gradlew build` de quem não tem Docker precisa continuar verde. A tag é herdada de `E2ETestBase`, então nenhuma classe pode esquecê-la |
| `StackPreflight` com banner ERROR antes do primeiro teste | "Connection refused" na primeira asserção não diz qual serviço caiu nem o que fazer. O preflight lista as portas fora do ar e o comando para levantá-las |
| Skip por default, falha com `-De2e.requireStack=true` | No CI, "pulei porque o ambiente não subiu" é o resultado que não se pode aceitar em silêncio; localmente, é o resultado correto |
| Nenhum valor absoluto de versão nas asserções | `calibracaoVersao`/`catalogoVersao` são monótonos e sobem a cada execução de FLOW-01. Congelar `"1-2"` faria a suíte quebrar na segunda rodada |

## Fora do escopo, e por quê

Um cenário deixado de fora e declarado vale mais que um teste frágil que passa por acidente.

- **Fixture factory com ciclo de vida próprio.** A suíte lê dados semeados (`DevFixtures`) em vez de
  criar paciente/comando/dispositivo/pareamento por execução. Um teardown que falha pela metade em 4
  serviços degrada o ambiente de dev a cada rodada. Custo assumido: apagar essas linhas do banco
  quebra os testes que as usam.
- **AUD — auditoria (E2E-004).** A escrita de fatos no hist-service é assíncrona via JMS e a resposta
  HTTP não expõe um identificador correlacionável ao fato. `sleep` + "existe algum fato recente"
  passaria por acidente sob qualquer tráfego concorrente.
- **HB (E2E-005) e NTF/DSH (E2E-007/008).** Exigem device token e evento com destinatário
  determinístico — ambos dependem da fixture factory ausente.
- **Flow-04 — apagamento LGPD.** Destrutivo e irreversível num ambiente de dev compartilhado.
- **Token autenticado sem `tenant_id` → 403 `tenant_claim_missing` (E2E-021).** Não reproduzível por
  HTTP: o ACS sempre emite o claim, e forjar o token exigiria a chave privada do issuer. Coberto no
  gate unitário de cada serviço.
- **Opção B (Newman).** Descartada: manteria o mesmo contrato duplicado em JSON, fora do compilador.

## Defeitos encontrados durante a implementação

1. **`evnt-service` não cruza header vs. claim de tenant.** Com `X-Tenant-Id` divergente, os outros 6
   serviços respondem 403 `tenant-mismatch`; o EVNT responde 200 e ignora o header
   (`TenantContextFilter` lê só o claim). **Não há vazamento** — o tenant vem do claim assinado — mas
   é divergência de política entre serviços. ISO-07 documenta o comportamento real em vez de asserir
   um 403 que não acontece. Corrigir exige tocar o evnt-service e não foi feito aqui.
2. **`POST /oauth2/token` com credencial inválida devolve ProblemDetail mal rotulado.** Status é 401
   (correto), mas o corpo traz `"title":"Internal Server Error"` e `"error.category":"internal_error"`
   para `acs.auth.invalid-credentials`. AUTH-04 asserta o `error.code`, que é o contrato estável, e
   não o `title`.
