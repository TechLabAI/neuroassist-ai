# E2E-031 — ACS perde fato de autenticação: fail-open sem outbox (C-52)

**Módulo:** E2E Cross-Service (ACS → HIST)
**Fase:** F4 — Audit Trail
**Prioridade:** P2
**Status:** ✅ DONE (2026-08-23) — fato sobrevive ao HIST fora do ar, validado no stack
**Criado em:** 2026-08-23 — pendência declarada ao fechar E2E-019
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2

## Contexto

[E2E-019](E2E-019.md) fez o acs-service produzir `autenticacao.realizada` e `autenticacao.falhou`
de verdade. O que ficou faltando é a durabilidade: `HistAuditAdapter` é fail-open — correto, uma
cuidadora não pode ser impedida de entrar no painel porque o hist-service caiu — mas **sem
outbox**. O adapter registra a própria perda:

```
Audit fact autenticacao.realizada NAO gravado e perdido — acs-service nao tem outbox
```

É a terceira vez que este projeto encontra a mesma forma. O PAC tinha a tabela e nada a lia
(C-44); o EVNT não tinha tabela nenhuma ([E2E-017](E2E-017.md)); o ACS está no segundo estado.

## Por que importa mais aqui do que parece

Um fato de auditoria de comando perdido é uma lacuna no histórico clínico. Um fato de
**autenticação** perdido é uma lacuna em "quem entrou e quando" — o registro que uma auditoria
LGPD pede primeiro, e o único que responde à pergunta "alguém acessou esses dados durante a
janela do incidente?".

E o momento em que se perde é o pior possível: uma indisponibilidade do hist-service é exatamente
quando há mais motivo para alguém querer olhar a trilha depois.

## O que muda em relação a PAC e EVNT

Nos dois, `hist_outbox` vive no schema do tenant e o dreno **vincula o tenant antes de abrir a
transação** — sem isso a consulta cairia no schema global, não acharia a tabela, e o sweeper
reportaria sucesso.

No ACS não é assim: `tenant`, `signing_key` e companhia são qualificadas em
`neuroassist_global`, e é lá que a tabela deste outbox precisa ficar — o ACS grava fatos de
**várias** empresas e o dreno roda sem tenant vinculado. Consequência: o tenant vira **coluna**
em vez de ser herdado do schema, e o dreno fica mais simples que os outros dois (sem
`TenantCatalogPort`, sem iteração por tenant, sem a armadilha do `search_path`).

Em compensação, cada linha carrega o tenant a que pertence, e a entrega precisa usar **esse**
tenant para escopar o token de serviço — não um qualquer.

## Checklist

- [x] Migration na faixa global (V0100-V0199), tabela qualificada em `neuroassist_global`
- [x] `status` como varchar + CHECK, nunca ENUM nativo (C-12)
- [x] `HistAuditOutboxPort` + entity/repository/adapter
- [x] `HistAuditAdapter` grava no outbox quando a entrega direta falha
- [x] `factId` cunhado **uma vez** e reenviado idêntico (dedupe do HIST — ADR-005, C-5)
- [x] Dreno agendado + estado terminal `failed` com o motivo registrado
- [x] Cada entrega usa o token escopado ao tenant **da linha**
- [x] Teste: HIST fora → fato pendente → HIST volta → fato entregue no tick seguinte

## Critério de aceite

Derrubar o hist-service, autenticar, subir o hist-service: o fato aparece na trilha sem
intervenção, com o mesmo `factId` da tentativa original.

## Implementado em 2026-08-23

| Peça | Onde |
|---|---|
| Tabela global | `V0103__acs_hist_outbox.sql` — `neuroassist_global.acs_hist_outbox` |
| Outbox | `HistAuditOutboxPort` / `HistAuditOutboxJpaEntity` / `HistAuditOutboxAdapter` |
| Enfileiramento no caminho de falha | `HistAuditAdapter` |
| Reentrega | `HistAuditRedeliveryPort` / `HistAuditRedeliveryAdapter` |
| Dreno | `HistAuditOutboxDrainService` + `HistAuditOutboxScheduler` |
| **`@EnableScheduling`** | `SchedulingConfig` — **não existia no ACS** |

### O `@EnableScheduling` faltava, e isso teria sido o mesmo defeito um nível acima

O acs-service não tinha agendamento ligado. Sem ele o método `@Scheduled` **nunca é invocado**: o
bean é criado, o contexto sobe, nada falha — e o outbox acumula em silêncio. Seria exatamente a
classe de defeito que esta issue existe para eliminar, só que uma camada acima: uma fila durável
que ninguém drena, que foi o C-44 no PAC.

### Por que este outbox é global e os outros dois não

| | PAC / EVNT | ACS |
|---|---|---|
| Onde vive | schema do tenant | `neuroassist_global`, qualificado |
| Como sabe o tenant | herda do `search_path` | **coluna** `tenant_id` |
| O que o dreno faz antes | vincula o tenant **fora** da transação | nada |
| Onde o tenant volta a importar | — | escopa o **token** de cada entrega |

O acs-service grava fatos de várias empresas e o dreno roda sem tenant vinculado, então herdar do
schema não funcionaria. Em troca, o sweeper fica mais simples que os outros dois: sem
`TenantCatalogPort`, sem iteração por tenant, sem a armadilha do `search_path`.

O preço é uma responsabilidade nova: **cada linha tem de ser entregue com o token da sua empresa**.
Entregar o fato de uma com o token de outra o gravaria na trilha errada — vazamento entre
empresas, não apenas um dado fora de lugar. É a propriedade que `HistAuditOutboxDrainServiceTest`
verifica explicitamente.

### Validação no stack real

| Passo | Resultado |
|---|---|
| `docker stop hist-service` + login | **200** — ninguém foi impedido de autenticar |
| `acs_hist_outbox` | 1 linha `pending`, com o `tenant_id` correto |
| Tick com o HIST ainda fora | `attempted=1 delivered=0` |
| `docker start hist-service`, tick seguinte | `attempted=1 delivered=1` → `sent`, `retry_count=1` |
| Ledger do HIST | `autenticacao.realizada` em `sequence_no=2`, com `record_hash` |

Antes desta issue, esse mesmo fato teria produzido só
`"NAO gravado e perdido — acs-service nao tem outbox"`.

Gates: ACS `test` + `architectureCheck` verdes.

### Fecha o ciclo dos três outbox

`hist_outbox` (PAC, C-44) · `evnt_hist_outbox` (EVNT, E2E-017) · `acs_hist_outbox` (ACS, esta).
Os três produtores de fato de auditoria da plataforma têm agora durabilidade. O EDGE não produz
fato próprio; o DASH é BFF e não produz nada.
