# E2E-022 — Nenhum teste valida o schema real: suítes usam `ddl-auto=create-drop`, produção usa Flyway

**Módulo:** E2E Cross-Service (todos os 7)
**Fase:** Infraestrutura de Testes
**Prioridade:** P2
**Status:** 🟡 PARCIAL — piloto no PAC fechado e validado; rollout em andamento
**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2

---

## Contexto

As suítes dos módulos rodam com `ddl-auto=create-drop`: **o Hibernate desenha o schema nos testes
enquanto o Flyway desenha o schema em produção**. Qualquer divergência entre uma migration e um
mapeamento JPA é invisível até o runtime.

Custo já pago: C-12 — `hist_outbox.status` era um `ENUM` nativo no Flyway e um `String` na entity.
O Postgres não faz coerção implícita de varchar para ENUM em INSERT, então **toda gravação no
outbox falhava** em produção. Nos testes a coluna nascia varchar e o ENUM nunca entrava em cena.

Enquanto essa divergência for possível, cada migration nova é uma aposta.

## Escopo

- Testcontainers das suítes de integração passam a aplicar **Flyway** e rodar com
  `ddl-auto=validate`
- Um teste por serviço que falha se migration e mapeamento divergirem
- Avaliar `flyway.out-of-order: true` no ambiente de teste (a convenção de faixa por módulo o exige)

## Critério de aceite

Mudar o tipo de uma coluna numa migration sem mudar a entity faz um teste ficar vermelho.

## Dependência

Nenhuma. Habilita E2E-027 (CI) a ter valor real.

## Piloto no PAC — 2026-08-23

| Peça | Onde |
|---|---|
| Migrations reais no container | `SchemaMigrations` + bloco estático de `BaseIntegrationTest` |
| `ddl-auto: validate` | `application-test.yml` |
| Flyway como dep de teste | `build.gradle.kts` |

O teste passou a fazer **o que produção faz**: migrations antes de o serviço subir. Global primeiro,
depois o template de empresa em cada schema de tenant que os testes usam (`empresa-abc`,
`empresa-xyz`, `t_emp_test`).

### O controle positivo não precisou ser inventado

A ideia era introduzir uma divergência artificial para provar que o gate a detecta. Não foi
preciso: **ao ligar o `validate`, uma divergência real apareceu sozinha**.

O cenário `Catalog returns only published commands` criava quatro comandos do mesmo paciente em
estados diferentes, todos com a mesma primitiva e a mesma necessidade. O schema real proíbe:
`ux_comando_active_mapping` é um índice único **parcial** sobre (paciente, primitiva principal,
primitiva secundária, necessidade) para todo estado `<> 'retired'` (ADR-006).

O Hibernate nunca criava esse índice, então a fixture descrevia um estado que produção **rejeita** —
e a suíte ficava verde. Corrigiu-se a **fixture**, não a migration: aqueles cenários são sobre ciclo
de vida, não sobre unicidade de mapeamento, e a primitiva é irrelevante para eles desde que
distinta.

### Quatro detalhes que custaram tempo

1. A URL do Testcontainers já vem com query string (`?loggerLevel=OFF`) — um segundo `?` faz o
   driver ignorar o parâmetro em silêncio.
2. `currentSchema` precisa ter um schema de tenant à frente do global, senão o `validate` reprova
   por não achar as tabelas em vez de por divergência de mapeamento.
3. O placeholder `hist_service_role` precisa ser o usuário do container.
4. `outOfOrder(true)` é obrigatório pela convenção de faixas por módulo.

Todos documentados em `standards/testing-conventions.md` §4.1, para que o rollout não os redescubra.
