# E2E-015 — Vínculo cuidador↔paciente não chega ao directory do ACS (C-30 / C-42 / C-43)

**Módulo:** E2E Cross-Service (PAC + ACS)
**Fase:** F3 — Directory
**Prioridade:** P1
**Status:** ✅ DONE (2026-08-23) — critério de aceite fechado contra o stack real
**Criado em:** 2026-08-23
**Plano:** [plan-e2e-integration.md](../plans/plan-e2e-integration.md) §11.2

---

## Contexto

O vínculo cuidador↔paciente vive em **duas tabelas, em dois schemas, sem nada entre elas**:

| Escritor | Tabela | Schema | Leitor |
|---|---|---|---|
| PAC (`PacienteService.create/update`) | `paciente_cuidador` | tenant | só o próprio PAC |
| ACS (`CaregiverPatientLinkService`) | `caregiver_patient_link` | **global** (C-42) | `DirectoryService` — EVNT, HIST |

Consequência direta: **todo paciente criado pelo PAC nasce com directory vazio no ACS**, e o
alarme gerado para esse paciente não tem destinatário. O Flow-03 (E2E-011) só passou porque o
roteiro chamou `POST /api/v1/acs/caregivers/{c}/patients/{p}/link` explicitamente — um passo que
nenhum cliente real executa.

O gate unitário do PAC não pega porque o PAC nunca precisou do directory; o do ACS não pega
porque o directory é populado pelos próprios testes.

## Decisão de arquitetura

**O ACS é o dono do vínculo como fato de controle de acesso** — é ele que responde `patient-scope`
e roteamento de alarme. O `paciente_cuidador` do PAC continua existindo como projeção tenant-local
(participa do contrato de `Paciente.cuidadorResponsavelIds` e do erasure LGPD, V0208), mas passa a
**propagar** para o ACS.

Propagação por **outbox**, não por chamada síncrona:

- síncrona antes do commit → criar paciente falha quando o ACS está fora (fail-closed num caminho
  que não precisa ser);
- síncrona depois do commit → divergência silenciosa, exatamente a de hoje;
- outbox → durável, não bloqueia o PAC, e **o padrão já existe pronto no repo** (`hist_outbox` +
  `HistOutboxDrainService` + `TenantCatalogPort`, C-5/C-44).

## Escopo

- `directory_outbox` no schema do tenant, escrita na **mesma transação** que `paciente_cuidador`
- dreno agendado por tenant, com identidade de serviço (`acs.vinculo.criar` / `acs.vinculo.revogar`)
- backfill dos vínculos já existentes (todo paciente criado antes desta issue)
- `409 last-active-link` no UNLINK é **terminal**, não transitório — invariante de cobertura do ACS (D-204)

## Critério de aceite

Criar um paciente pelo PAC com `cuidadorResponsavelIds` e, **sem nenhuma chamada extra**,
`GET /api/v1/acs/directory/patients/{id}/caregivers` retornar esse cuidador.

## Dependência

E2E-003 (directory), E2E-009 (Flow-01). Relacionada: E2E-021 (shim de tenant).

`architectureCheck` verdes.

### Três decisões que valem registro

1. **`update` propaga a diferença, não o resultado.** O PAC reescreve `paciente_cuidador` com
   delete-all + insert-all. Propagar isso literalmente revogaria e recriaria todo vínculo a cada
   edição — e um paciente com uma única cuidadora bateria na invariante de cobertura do ACS
   (D-204, 409) toda vez.
2. **O dreno para no primeiro erro transitório.** Não é só cortesia com o ACS: preserva a ordem
   entre um LINK e o UNLINK seguinte do mesmo par. Entregues fora de ordem, o directory fica com
   um vínculo que o PAC já removeu.
3. **`tenantId` viaja como `String`, embora o controller do ACS declare `UUID`.** Dentro do PAC o
   tenant é `String` em todo lugar; converter só para serializar de volta em texto criaria um modo
   de falha que se comporta diferente na suíte (tenants são apelidos como `empresa-abc`) e em
   produção (UUIDs) — exatamente a divergência teste/produção que este projeto já pagou caro.

### O que esta issue NÃO resolveu

- **C-42 continua de pé.** O ACS grava e lê `caregiver_patient_link` no schema global enquanto a
  migration cria a mesma tabela no schema do tenant, que segue vazia e morta. O isolamento entre
  empresas depende do filtro por `tenant_id`, não do `search_path`.
- ~~Critério de aceite não executado contra o stack real~~ — **fechado em 2026-08-23**, ver abaixo.
- **Erasure LGPD não desfaz vínculos.** Um paciente com `erased_at` mantém os links no directory.
  O backfill exclui esses pacientes, mas o `erasePersonalData` não enfileira UNLINK. Decisão
  pendente: um paciente apagado não gera alarme, então o vínculo é inerte — mas é dado residual.

## Validação no stack real (2026-08-23)

Stack docker-compose completo, jars reconstruídos, `migrations-empresa` executado antes.

| Passo | Resultado |
|---|---|
| Migration | `Migrating schema "t_emp_dev" to version "0209 - pac directory outbox" [out of order]` → `Successfully applied 1 migration` |
| Backfill | **9 vínculos** enfileirados — nove pacientes do tenant de dev que nunca haviam chegado ao directory do ACS. O tamanho do backfill é a medida do defeito. |
| Primeiro tick do dreno | `attempted=9 delivered=9 givenUp=0` |
| `POST /api/pac/v1/pacientes` com `cuidadorResponsavelIds` | 201 |
| Directory **antes** do tick | `{"responsibleCaregivers": []}` — o defeito reproduzido |
| Directory **depois** do tick, sem nenhuma chamada extra | a cuidadora, com papel e authorities |
| Entrada de outbox | `status=sent`, `retry_count=0` |

**Critério de aceite atendido.**

### O caminho de UNLINK também foi exercitado — e achou um defeito novo

`PUT` removendo a única cuidadora: PAC responde **200**, o UNLINK propagado leva **409**
`acs.link.last-caregiver-link` do ACS (invariante de cobertura D-204). A entrada foi para `failed`
com `last_error = refused by acs-service`, sem retry, e o log registrou
`The two sides of this link now disagree`.

A propagação se comportou como projetada. O que apareceu foi a invariante existir **em um lado
só** — registrado como **[E2E-028](E2E-028.md)** (C-47). Não foi introduzido por esta issue; era
invisível enquanto os dois lados não se falavam.

O paciente de teste foi restaurado com a cuidadora, realinhando os dois lados.
